## 0. 一句话背景（**先读，会影响你对结果的预期**）

主控已在接收端源码里找到这条 WARN 的**根因**，且**数值完全吻合**：

> `openState` 有**两种合法表示**：固件发 4 位 HEX（`"00F0"`），`db_proto.decode()` 返回中文（`"无锁/合闸"`）。
> 字符串直接比对 ⇒ **每一行必然差 1 个字段**。
> 而 `verify_raw()` 的抽样上限**写死 2000 行** ⇒ `checked=2000`。
> ⇒ `2000 行 × 每行 1 个 = bad 2000`。**数学上严丝合缝。**

**所以 `bad=2000` 的预期结论是：自校验脚本的比对口径 bug，不是数据损坏，也不是固件问题。**
主控侧代码**已经修复**（改为把 `openState` 统一到 HEX 再比，见 `udp_collect.py:2113-2121`）。

**你要做的是验证这个结论，不是重新调查。** 如果结果不是这样，那才需要深挖。

## 2. 跑自校验（**用 `--verify-raw`，不是 `--report-only`**）

> ⚠️ **重要区别**：
> - `--report-only` 只是**重出报告**，报告里的 `checked/bad` 读的是库里 `event_log` 的**历史快照**
>   （跑的时候用旧脚本算的 2000/2000）⇒ **不会重算，看不出修复效果**。
> - **`--verify-raw` 才是重新校验**，会用当前代码对 `udp_packet.payload` 里的 `raw` 全量/抽样重算并比对。
>
> 所以要定性必须用 `--verify-raw`。两个都跑一遍也可以（`--report-only` 用来确认报告可复算）。

```bash
# 先确认库路径（按你实际的长跑库名改）
ls -lh *.db

# 2-A 重新自校验（核心，必须跑）
python udp_collect.py --db <你的库.db> --verify-raw

# 2-B 顺带确认报告可复算（P-4 判据，可选但建议）
python udp_collect.py --db <你的库.db> --report-only
```

`--verify-raw` 会：

- 遍历 `udp_packet` 里 `ptype='data'` 且 `parse_status='ok'` 的行
- 用 `raw` 重算 39 字段，与 JSON 里的工程量逐字段比
- 在**库同目录**写一个 `<库名>_rawcheck.csv`（不一致样例，最多 50 条）
- 终端打印：`raw 自校验：N 行，不一致 M 处 → <csv 路径>`

## 4. 判读标准（主控侧，供你参考）

| 结果 | 结论 | 对 168h 的影响 |
|---|---|---|
| `bad = 0` | 根因确认就是 `openState` 口径 ⇒ **已闭环** | `Y-6` 有证据了，**不阻断** |
| `bad` 很小（几十）且集中在某一字段 | 该字段有末位舍入问题 | 记为已知项，`Y-6` 阈值 ≤0.01% 仍可能过 |
| `bad` 仍 ≈ `checked`（每行 1 个） | **修复没生效**或还有第二个系统性口径 bug | **停下**，把 CSV 发主控 |
| `checked` 远小于数据总行数 | `raw` 字段缺失/长度不是 78 B | 停下，`raw` 可能没全量上行 |
