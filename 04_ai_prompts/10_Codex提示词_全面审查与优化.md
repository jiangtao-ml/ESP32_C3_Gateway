## 一、项目背景（够用即可，不要扩大调研）

代码位置：

- `01_firmware/esp32c3_gateway/esp32c3_gateway.ino`（主逻辑，约 1350 行）
- `01_firmware/esp32c3_gateway/config.h`（全部编译期常量）
- `01_firmware/esp32c3_gateway/web_config.h`（常驻 AP + Web 配置页 + `/status` + NVS）
- `01_firmware/esp32c3_gateway/secrets.h`（**凭据，禁止读取内容写进报告，禁止修改**）

## 二、硬件现状（**本次审查的关键前提，已定稿，不要再讨论选型**）

| 项 | 现状 |
| --- | --- |
| 载体 | **洞洞板（万用板）**，70×90 mm 双面镀锡，2.54 mm 孔 |
| 装配 | **没有排母**。ESP32-C3 SuperMini 与 MAX13487 模块的引脚**直接穿过洞洞板孔焊接**，焊上即不可拆 |
| 供电 | ESP32 的 USB-C 是唯一入口；模块 `VCC` 由 ESP32 的 `5V` 引脚供给 |
| 电平 | **不分压**。模块 `TXD`（RO/RXO）**直连** `GPIO20`，已裁定为 3.3V 逻辑兼容 |
| `EN` | 固定接 **3.3V**（不是 5V） |
| DE | **无**。MAX13487 是 AutoDirection，`RS485_DE_PIN = -1` |
| 终端/偏置 | 模块板载已有 `472 / 121 / 472`（4.7k / 120Ω / 4.7k），板上**不得再加** |
| 调试口 | 只有 USB-C（串口 + 烧录 + 供电三合一）；LED 是板载 GPIO8 |

接线（8 根，**交叉**，这是最容易错的地方）：

```
ESP32 5V   → 模块 VCC        ESP32 3.3 → 模块 EN
ESP32 G    → 模块 GND        ESP32 21(TX) → 模块 RXD
ESP32 20(RX) ← 模块 TXD      ESP32 GND → 端子 GND
模块 A → 端子 A              模块 B → 端子 B
```

**"没有排母"带来的三个后果，请在审查时始终考虑：**

1. **不可插拔隔离**：无法把模块拔下来做回环测试，也无法在不动烙铁的前提下换模块。固件里的降级/自恢复逻辑因此更重要。
2. **不可跳线**：任何"临时短接 A/B 自环"的调试手段都不可用（何况 A/B 短接本身就是无效自测）。
3. **引脚不可改**：一旦焊错只能拆焊。所以**引脚分配的正确性优先级高于一切**。

## 四、审查清单（逐项给结论，不要跳）

### A. 功能正确性（最高优先级）

1. **Modbus 帧**：请求帧字节、CRC16（`0xFFFF` 初值 / `0xA001` 多项式 / **低字节在前**）是否与 `m5_frame_check.py` 的独立复核结果一致？不要重算后"顺手改"，只报告是否一致。
2. **39 个寄存器的映射**：`g_merged` 的段偏移拼接是否正确？一帧读全（83 B）与 3 段（37/37/19 B）两条路径拼出来的 39 个寄存器是否逐一对齐？有没有可能某段缺失导致尾部残留上一轮的值？
3. **P0-1 帧长校验**：`byteCount + 5` 是否等于本段**请求**的寄存器数×2+5？这道闸门是唯一挡住"短帧静默掺假"的，**不得削弱**。
4. **工程量换算**：`A/B/C_temp`（`raw-40`）、电压、电流、功率、频率、漏电、电量 `(H×65536)/1000+L` 的公式与量程判据是否一致？特别注意 `-40 ℃` 既是"该型号恒不上报"的伪装值、又可能是"真越界"，代码如何区分？
5. **`quality` / `invalid`**：`PARTIAL` 的判定条件是否与字段级 `invalid` 一一对应？
6. **计数器语义**：`poll_ok` / `poll_err` 是否仍在 WiFi 链路判断**之前**自增？（这是接收端对账恒等式的前提，动了整套统计就废了）
7. **`seq` 语义**：是否仍是**每发一行自增 1**、三条行型共用同一个 `seq`？
8. **时间戳**：NTP 判据是否仍用 `sntp_getreachability()` 而不是 `getLocalTime()` 的返回值？`ts_ok` 是否准确反映"本轮会话已对时"？

### B. 逻辑缺陷与边界/异常

逐条给"有/无问题"的结论：

1. **半帧/超时**：三级超时（首字节 80 ms / 字符间隔 8 ms / 整帧 300 ms）组合起来，会不会出现"半帧被当成完整帧"？
2. **`byteCount` 异常**：奇数、为 0、超过 `g_rxFrame` 容量、与请求不符 —— 四种情况分别怎么处理？
3. **异常响应**（`func|0x80` + 异常码，5 字节）与正常短帧的区分顺序是否正确？
4. **`g_merged` 从不整轮清零**（这是已知设计），那么"某段失败但整轮仍被判成功"的可能路径是否存在？
5. **3 段模式最坏耗时**：3×300 ms 兜底 + 8 ms 间隙 ≈ 933 ms，而周期是 1000 ms —— 阈值只剩 67 ms 余量。请核算这个估算，并指出会在什么条件下越界、越界后发生什么。
6. **`millis()` 回绕**：所有比较是否都写成 `(int32_t)(now - t) >= 0`？168 h = 7 天，不触发 49.7 天回绕，但写法错就是埋雷。
7. **`seq` 是 `uint32_t`**：回绕时（约 49,710 天）不会出问题，但 `%lu` 打印与接收端解析是否一致？
8. **电量 32 位进位**：`rH` 从 0xFFFF 进位到 0 的瞬间，公式会不会出现负跳变？
9. **WiFi 断线期间**：`sendUdpPayload()` 早退后，`g_roundFailed` / `g_failSeg` 等状态是否会在下一轮残留？
10. **NTP 未同步**：`ts` 退化成 `BOOT+<秒>` 后，接收端要靠锚点换算。这个格式是否稳定、有没有边界（例如 `millis()` 恰好在整秒附近抖动）？
11. **NVS**：读失败、键缺失、值越界（例如 `poll_s` 被写成 0 或负数）分别怎么处理？会不会导致除零或死循环？
12. **Web 服务**：客户端只发半个请求时，`handleClient()` 最长会阻塞多久？这段时间里轮询会怎样？

### C. 资源占用与性能（168 h 视角）

1. **堆**：热路径上是否还存在任何动态分配（`String` / `malloc` / `new`）？本轮已把 `WiFi.localIP().toString()` 改为栈上缓冲，请确认没有遗漏。
2. **栈**：`parseResponse()` / `buildDataJson()` 的局部数组叠加 `vsnprintf` 的浮点栈帧，在 8 KB 的 loopTask 栈上余量多少？给出最坏路径估算。
3. **串口**：`Serial.setTxTimeoutMs(0)` 是否仍在、是否对所有分支生效？（去掉它会让 1 s 周期退化到 ~19 s）每轮还剩多少次 `write`？`SERIAL_VERBOSE_ROUND=0` 时降到多少？
4. **Flash**：82.9% 已用，剩约 224 KB。指出当前有哪些"占体积但长跑用不到"的部分（例如 Web 页面字符串、调试字符串），并给出可压缩的建议（**只建议，不实施**）。
5. **CPU**：`loop()` 是否有隐含的忙等或长阻塞？`WebServer::handleClient()` 的 `_nullDelay` 是否已关？
6. **NVS 磨损**：`WiFi.persistent(true)` + "从未连上时每 5 s 调 `WiFi.begin()`" 是否会导致 NVS 反复写入？请从 core 源码确认，并给出证据（行号）。这是 168 h 场景下的真实风险。
7. **UDP 发送路径**：`beginPacket` 失败（pbuf 耗尽）时会发生什么？会不会连续失败却没有自恢复？

### D. 可读性与结构

1. 注释与代码**不一致**的地方，逐条列出并给出正确表述。已知可疑项（请核实，不要照抄我的话）：
   - 某处注释称"每轮热路径 ~190 次 write"，实际构造是否为 44 次（verbose 开）/ 2 次（关）？
   - `config.h` 里关于字符间隔"3~5 ms"的提示与 `RS485_CHAR_TIMEOUT_MS = 8` 是否矛盾？
2. 单文件 1350 行是否该拆？**只给结论和代价分析**（拆 `.ino` 需要自己补函数原型），不要动手拆。
3. 命名是否有误导（例如 `qiSegTag()` 与 `qiDataSegTag()` 的区别是否一目了然）？
4. 是否存在复制粘贴造成的重复代码块（三相交替处理的段落）？如果合并能显著降体积且不改行为，可以作为"建议项"提出。

### E. 与硬件接线的匹配性（**本次重点**）

逐条确认：

1. **引脚分配**：`RS485_TX_PIN=21` / `RS485_RX_PIN=20` / `LED_PIN=8` 是否与 `ARDUINO_USB_CDC_ON_BOOT=1` 下的 USB CDC 不冲突？`Serial`（USB）与 `Serial1`（UART1）是否各走各的？
2. **GPIO8 是 ESP32-C3 的 strapping 脚**（启动时需为高电平才能正常从 flash 启动）。LED 是**低电平点亮**，请确认：上电/复位瞬间 GPIO8 的状态由谁决定？会不会因为"低电平点亮"的默认状态影响启动？给出 core 与芯片手册依据。
3. **`EN` 固定 3.3V**：代码里是否存在任何会驱动 EN 或方向脚的逻辑？`RS485_DE_PIN=-1` 是否在所有分支（含 3 段模式、含错误恢复）都成立？
4. **不分压、直连 GPIO20**：确认代码中没有任何依赖"外部电平转换"的假设；同时指出如果将来换 5V 逻辑模块，固件层面有没有可做的保护（例如启动时自检）——**只建议**。
5. **无排母、不可插拔**：评估当前的降级策略（一帧读全 → 3 段）在"无法人工干预"的现场是否足够。如果 168 h 中途总线彻底断开，固件的行为是什么？
6. **只有 USB-C 一个口**：长跑时必须拔掉 USB 数据线、改用电源适配器。固件是否依赖 USB 连接（例如 `while(!Serial)` 等待）？这个等待会阻塞多久？
7. **LED 是唯一现场反馈**：当前三种状态（WiFi 断=慢闪 / 成功=短闪 / 失败=长闪）在"总线正常但 WiFi 断"时显示什么？现场能否据此判断该修网络还是该修 485？

| # | 项 | 原因 |

## 八、一个必须回答的实证问题

1. 心跳行与数据行是**背靠背在同一毫秒内发两个 UDP 包**（间隔 0 ms）。这会不会导致 lwIP pbuf 或 WiFi 发送队列在"第二个较大的包"上出问题？

**这一问不要猜。** 能给证据（core 源码、lwIP 配置、已知 issue）就给证据；给不了就明确写"固件侧无法判定，需接收端 pcap 与内核计数配合"。

## 十、纪律

1. **只加固，不重构。** 每一处改动都要能说清"不改会出什么事"。
2. **不确定就标 `[待确认]`**，禁止编造寄存器、寄存器地址、芯片行为。
3. **不要静默修改**你不确定的地方；拿不准的写进报告让用户决定。
4. 改完必须自己编译两种模式并贴出体积。
5. 报告里出现的中文注释风格与现有代码保持一致（带日期与改动人标记）。
