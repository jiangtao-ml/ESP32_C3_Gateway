> 最后更新：2026-10-26 21:12 砚青
> **为什么单独出这一份**：操控端（本机 / 192.168.1.113）今晚会关机。**关机之后砚青就失联了**，
> 剩下的步骤必须能由旧电脑那边独立走完。本文件就是那份"照做就行"的清单。
> **执行方**：旧电脑（Win10，有线 `172.16.0.138`）＋ 用户本人。

## §0 一句话

**本机（192.168.1.113）关机之前，必须把 ESP32 的上报目标改成 `172.16.0.138`。**
改完之后 ESP32 就再也不往本机发了 —— 这是**目的**，不是故障。
**本机可以在"旧电脑控制台里 rx 已经涨起来"之后才关。**

---

## §1 三段硬顺序（不可调整）

| 阶段 | 在哪台机 | 要做什么 | 完成判据 |
|---|---|---|---|
| **S1** | ESP32 | USB 上电（旧电脑供电或 5V 适配器） | 能 ping 通 `192.168.1.200` |
| **S2** | **本机（关机前！）** | 把 ESP32 的 `udp_ip` 改成 `172.16.0.138` | `/status` 的 `server` 变成 `172.16.0.138` |
| **S3** | 旧电脑 | 换 v2 包 → env-check → 起跑 8h | 控制台 `rx` 持续增长 |
| **S4** | 本机 | **看到 S3 的 rx 增长之后**，才能关机 | — |

⚠️ **顺序错了的后果**
- 漏掉 S2 ⇒ ESP32 继续往 `192.168.1.113` 发，本机已关机 ⇒ **8 小时一条数据都没有**。
- S4 太早 ⇒ 万一 S3 起不来，没人能回去改 IP，只能等明天本机开机。

## §2 S2 的具体做法（本机上执行，需要板子在线）

```bat
cd /d C:\Users\17352\Desktop\ESP32_C3_Gateway
python .workbuddy\tmp\preflight_switch_target.py
```

它做四件事：读 `/status` → 改 `udp_ip` → 复核 → 监听 15 s 数包。
**最后一步在这个时点必然报"0 包"，这是正常的** —— 因为目标已经改到旧电脑去了，本机听不到了。
**只看前三步的输出**：
```

[✓] POST /save → HTTP 200  已保存并立即生效
[✓] 复核 server=172.16.0.138 port=8888
```

改不了时的兜底：浏览器打开 `http://192.168.1.200/`，表单里把 **服务器 / 目标 IP** 改成
`172.16.0.138`、端口 `8888`、周期 `1`，提交时账号 `admin` / 口令 **`485-20A4`**
（`485-` + MAC `30:ED:A0:5B:20:A4` 的第 5、6 字节即 `20` 与 `A4`。⚠️ 2026-10-26 21:22 实测更正：
此处原写 `485-5BA4` 是**把 MAC 下标数错了**，用它一定 401）。
（口令 = `485-` + MAC 后 4 位 HEX；本机 MAC `30:ED:A0:5B:20:A4`）

## §3 S3 起跑（旧电脑上执行）

**3.1 先确认包是 v2（这一步不能跳）**
```bat
cd /d "D:\Users\szj\Desktop\ESP32接收端_2026-10-26_v2\06_tests"
python udp_collect.py --env-check
```
必须看到这两行：
```
  [信息] 收包回调可调用
  [信息] 介质 = 本机固定盘（FIXED）
结论：通过
```
**没有「收包回调可调用」= 还是旧包 = 会在 Python 3.13 上恒收 0 包，直接停下换包。**

**3.2 起跑**
```bat
python udp_collect.py --db D:\esp32_collect\data\run8h.db --hours 8 --fw-ver 0.6.0-batch3
```

**3.3 起跑后 30 秒内必看**
控制台应每 10 秒打一行，形如：
```
[21:2x:xx] up 0:00:10 | rx 18 (d 9/h 9/e 0) | bad 0 | dup 0 | ... | db 18 行
```
- `d` / `h` 都在涨 ⇒ **正常**，可以通知本机关机。
- `rx 0` 持续 30 秒 ⇒ **别关本机**，回 §2 重查 IP。
- `d 0` 但 `h` 在涨 ⇒ 只收到心跳、数据行在失败 ⇒ 485 侧问题，起跑也全是 err 行。

## §4 中途检查点（无人值守时至少看三次）

| 时点 | 命令 | 判据 |
|---|---|---|
| +1 h | `dir D:\esp32_collect\data\run8h.db` | 文件在长大（约 60–70 MB/h） |
| +4 h | 看控制台最后一行 | `rx` 累计应为 ~14400 量级；`cs`（时钟回退）应 **0** |
| 结束 | Ctrl+C | 见 §5 |

控制台那行里几个缩写：`ss`=同秒撞车 `cs`=时钟回退 `oo`=乱序 `bad`=解析失败 `drop`=队列溢出。
**`cs > 0` 是本次长跑最需要警惕的一项**（意味着时钟被 NTP 往回拨了，会拉低 Y-4）。

## §5 停止

```
Ctrl + C
```
必须看到最后一行：
```
[RUN] 报告已写入 D:\esp32_collect\data\run8h_report.txt
```

**三条禁令**：不要点窗口 ✕ / 不要用任务管理器结束 / 不要直接断电。
（Windows 上 SIGTERM 投不进去，点 ✕ 等于硬杀 —— `stop_signal_at`、`ended_at` 都不会写，报告根本不生成。）

## §8 故障对照（无人值守时自己判）

| 现象 | 原因 | 处理 |
|---|---|---|
| `rx 0` 全程 | ESP32 目标 IP 没改 / 本机没执行 S2 / 防火墙 / WiFi 断 | 查 ESP32 的 `/status`（需在 402FBS 网内） |
| 有 `PARSE_EXC` 且 `rx 0` | 旧包 + Python 3.13 | 换 v2 包 |
| `d 0` `h` 正常 | 485 侧全失败 | 看 `err` 行的 `reason` |
| `cs > 0` | NTP 回拨（固件未修 P0-1） | **照实记录，别掩盖**；这是已知缺陷，明早如实上报 |
| `disk I/O error` | DB 放到了同步盘/网络盘 | 换到 `D:\esp32_collect\data\`（本机固定盘） |
| `[CLK] 本机时钟与固件差 xxx s` | 旧电脑时间不准 | 立刻停，`w32tm /resync` 后重跑 |

## §9 禁忌（每条都吃过亏）

1. **不要在 ESP32 带电时插拔任何 485 接线**（配电箱带电）。
2. **不要动 ESP32 的 WiFi 配置** —— 一旦改错，本机已关机，只能等明天。
3. **不要在本机确认旧电脑收到包之前关机。**
4. **不要点窗口 ✕ 停采集**。
5. **不要为了让数字好看而改判据** —— `cs`、`same_second` 照实记，报告才有价值。
