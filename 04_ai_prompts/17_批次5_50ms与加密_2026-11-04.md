## 0. 一句话与边界

**一批同时做两件事**：① 每轮 `hb` 与 `data/err` 之间插 50 ms 间隔；② UDP 载荷 AES-128-GCM 加密 + 运行时开关。

**为什么必须同批**：加密给每包加 **29 B**，而 15:1 的丢包不对称已经证明**大包更容易被空口丢**（`02_docs/22` §3.2）。分两批做，出问题时无法区分是"间隔的功劳/副作用"还是"加密的功劳/副作用"。同批做才能用 `data_lost/hb_lost` 比值把两个变量的影响分开看。

**明确不做**：
- 不动 Modbus 协议层（`0x04` 帧、CRC、寄存器读取一个字不改）
- 不动 `buildDataJson` / `buildHeartbeatJson` / `buildErrJson` 的字段与格式
- 不做密钥协商 / 轮换 / 前向保密（`22` §4.1 已定性为"对比实验能力"，**不得在报告里写成生产级安全方案**）

## 1. 三件必须先裁决的事（**主控已裁决，附依据，不要自行更改**）

### 1.1 帧格式：接收端实现与文档冲突 ⇒ **以 `22` §4.2 为准**

现状冲突：

| 项 | 接收端 `udp_collect.py:713` 现有实现 | `02_docs/22` §4.2 设计 |
| --- | --- | --- |
| 版本字节 | `data[0] != 1` ⇒ 字节值 **`0x01`** | `bit7=1` + 低 4 位协议版本 2 ⇒ **`0x82`** |
| AAD | `None`（无） | **版本字节本身**（防版本降级） |

**裁决：按文档实现，接收端改**。理由：
1. **判别更干净**：明文 JSON 首字节恒为 `0x7B`（`{`），密文首字节恒 ≥ `0x80`，**永不可能歧义**；而 `0x01` 这个判据只是"恰好不冲突"。
2. **AAD 是有意义的**：绑定版本字节后，攻击者把密文帧的版本字节改掉会导致 Tag 校验失败，而不是被当成另一个版本解析。

### 1.2 🔴 加密后 `udp_packet.payload` **必须存明文**（文档没写，但不改会打断证据链）

现状：`udp_collect.py:851` 是 `"payload": data` —— 存的是**原始 UDP 字节**。

一旦加密，入库的就是**密文**，后果：
- `--verify-raw`（拿 payload 逐字段重算比对）**直接失效** ⇒ **Y-6 唯一的证据链断掉**
- `raw_hex` 可重放能力丢失 ⇒ 这是本项目"公式可演进、历史可重算"的核心优势（D-10 就是靠这个救回来的）

**要求**：解密成功时 `payload` 存**解密后的明文 JSON 字节**，并用 `enc=1` 标记该行源自密文。
`payload_len` 保持为**原始 UDP 报文长度**（即密文长度）——这样"密文比明文多 29 B"仍可用 `payload_len` 校验。

**明说取舍**：密文原字节**不保留**。理由：明文已能完整重算（含 `raw`），密文对取证价值极低，而保留两份会让库体积近乎翻倍（1.2 GB → ~2.4 GB）。

### 1.3 包长与 IP 分片：**安全，但必须台架实测确认**

实测（`02_docs/22` §3.2 记录）：**data 行 892 B、心跳 213 B**（P0-2 加字段后约 312 B）。

⚠️ **但 892 B 不是上界**。`g_payload` 定义处（`esp32c3_gateway.ino:127`）写的是 **"含 raw 78B HEX 的最坏行 1106 B"** —— 那是按 `raw` 满长 + 所有字段取最坏算出来的。因此**分片判据必须用最坏值**：

| 项 | 明文 | 密文（+29 B） | 与 1472 的余量 |
| --- | ---: | ---: | ---: |
| data 行（常见值） | 892 | **921** | 551 |
| **data 行（最坏值 1106）** | **1106** | **1135** | **337** |
| 心跳（~312） | ~312 | ~341 | 1131 |

⇒ **即使最坏行也不触发 IP 分片**，但余量只有 337 B（不是 551）。**台架必须实测 `max(payload_len) < 1472`**——因为一旦分片，任一分片丢失即整包丢失，丢包率会凭空放大数倍，整个 A/B 结论作废。

同一张表也定了 `g_encbuf` 的下界：最坏 1135 B < **1280**（预留 145 B）⇒ §3.4 的 `QI_ENC_BUF_MAX 1280` 可用，但**不许再调小**。

## 2. 改动 A：50 ms 包间隔

### 2.1 现状

`stateTick()` 的 `case ST_SEND:` 调 `sendUdpPayload()`，后者在一次调用里**连续**发 `hb` 和 `data`（或 `err`），两包间隔 ≈ 0 ms。

### 2.2 目标时序

```
t=0ms    poll 完成
t=0      → 发 hb
t≈0      → 进入 ST_SEND_GAP（记录 g_gapStartMs = millis()）
t=50ms   → 发 data（成功轮）或 err（失败轮）
t≈50ms   → 轮末收尾（见 2.4 清单）
t=1000ms → 下一轮
```

**轮询周期仍为 1000 ms**（`g_pollIntervalMs` 不变），只是把同一轮的两行错开。

**精度说明（免得台架误判）**：`stateTick()` 在 `loop()` 里**不受节流**（`esp32c3_gateway.ino:1653`，紧接 `wdtFeed/ntpClampTick/wifiTick/ntpTick` 之后），所以 50 ms 能用 `millis()` 精确判到。但判据是"**到点或过点**"（`>= 50`），实际间隔 = 50 ms + 一个 loop 周期 ⇒ **实测中位数落在 50~60 ms 属正常**，不是实现错误。上界才是有意义的指标（p99 < 200 ms）。

### 2.3 实现要求：**必须非阻塞，禁止 `delay()`**

改动形态：把现有 `sendUdpPayload()`（`esp32c3_gateway.ino:1050`）**拆成两个函数**，
并新增状态 `ST_SEND_GAP`，由 `millis()` 驱动：

```c
// 第 1 段：轮次计数 + 链路检查 + 生成 ts + 发 hb
static void sendHeartbeatLine();

// 第 2 段：发 data（成功轮）或 err（失败轮）
static void sendSecondLine();

case ST_SEND:
    g_roundTsOk = buildTimestampIso(g_roundTs, sizeof(g_roundTs));  // 只生成一次
    sendHeartbeatLine();
    g_gapStartMs = millis();
    g_state = ST_SEND_GAP;
    break;

case ST_SEND_GAP:
    if ((uint32_t)(millis() - g_gapStartMs) < QI_TX_GAP_MS) break;   // 50
    sendSecondLine();
    roundFinish();                // 见 2.4 清单
    g_state = ST_IDLE;
    break;
```

`config.h` 新增 `#define QI_TX_GAP_MS 50`。

#### 2.3.1 🔴 `ts` 必须沿用同一个（拆函数最容易踩的坑）

现状 `sendUdpPayload()` 里 `buildTimestampIso(ts, ...)` **只调用一次**，hb 与 data 共用同一个 `ts`。
拆成两个函数后，如果第二段又调一次 `buildTimestampIso()`，因为相隔 50 ms，会出现：

- `data.ts` 比 `hb.ts` 大 **1 秒**（跨秒时）
- 更糟：若中间发生过时钟钳位，可能 `data.ts < hb.ts` ⇒ 直接触发 Y-4 的 `CLOCK_STEP` 误报

**要求**：`ts` 在第一段生成后**存进静态变量**（`g_roundTs[]` / `g_roundTsOk`），第二段**只读不重算**。
这样 `hb.ts == data.ts` **恒成立**，比"允许差 1 秒"干净得多。

#### 2.3.2 ⚠️ `!g_linkUp` 的早退语义会变

现状：WiFi 未连接时 `sendUdpPayload()` 在生成任何行**之前**就 `return` ⇒ 整轮跳过（一行不发）。

拆开后：若 WiFi 恰在这 50 ms 内断开，会出现"**hb 发了、data 没发**"的半轮。
**这是可以接受的**（接收端会记为"仅心跳丢失"的反向情况：hb 到了 data 没到，等价于 data 丢失，计入 `data_lost`），
但要求：
- `sendSecondLine()` 里保留同样的 `!g_linkUp` 检查与 5 s 节流日志
- **台架统计"半个轮次"的数量**，正常应 < 0.1%（WiFi 断连极少）

**为什么必须非阻塞（三条实质理由，不是洁癖）**：

1. **会削弱时钟钳位**：`ntpClampTick()` 刻意放在 `loop()` 里**不受 200 ms 节流**，为的是把"SNTP 已改钟 → 拉回"的漏网窗口压到单次迭代。`delay(50)` 每秒制造一个 50 ms 盲窗，直接削弱 P0-1 的保护，而 Y-4 正是靠它。
2. **会阻塞 `webTick()`**：配置页与 `/status` 每轮卡 50 ms，长跑期间巡检会明显变慢。
3. **会推迟 `wdtFeed()`**：单次 50 ms 不致命，但这是"以后再加个 delay 也没事"的口子，一旦被人扩大就是 `TASK_WDT`。

> 若实施方坚持用 `delay(50)`，必须在提交说明里逐条反驳上面三点，否则一律按非阻塞实现。

### 2.4 ⚠️ 最容易出错的地方：哪些语句必须**随第二行一起后移**

当前 `case ST_SEND:` 里 `sendUdpPayload()` 之后还有一串"轮末收尾"逻辑，**它们必须整体移到 `ST_SEND_GAP` 发完第二行之后**，否则语义全错：

| 语句 | 为什么必须后移 |
| --- | --- |
| 批次 2 的"一帧读全降级判定"（`g_readMode` / `g_fullConsecFail`） | 它读 `g_roundFailed`，而 `g_roundFailed` 由 data/err 行决定 ⇒ 提前跑会用到上一轮的值 |
| `ledPulse(g_roundFailed ? ...)` | 同上，LED 会亮错颜色 |
| `g_nextPollMs += g_pollIntervalMs` | 若提前推进，下一轮可能在第二行还没发时就到期 ⇒ 节拍漂移 |
| "落后一个周期以上重新对齐"判定（`[POLL][SKIP]` 分支） | 同上 |
| **本轮结果复位**：`g_roundFailed = false; g_failSeg = 0xFF; g_failReason = NULL;` | 🔴 **这条最容易漏，漏了就是静默错数据**：第二行靠 `g_roundFailed` 决定发 `data` 还是 `err`。若复位留在原处（先复位再发），**失败轮会发出 `data` 行**，把坏数据当好消息上报，对账恒等式照样闭合（因为 `udp_tx` 没错），`M1` 照样 100% —— **从外部指标完全看不出来** |
| `g_state = ST_...`（下一状态） | 提前跳走就不会再发第二行了 |

⚠️ **两处 `#if` 守卫不能搬丢**：`ledPulse(...)` 与复位块都包在 `#if !RS485_MODE_LOOPBACK_SELFTEST` 里（`g_roundFailed` 声明在该守卫内，见 P0-3 注释）。`roundFinish()` 内部必须原样保留这两个守卫，否则 `SELFTEST=1` 又编不过（批次 3.5 就栽过这个）。

**落地形态**：把上表**六条**（含复位块）**原样搬进**一个新函数 `roundFinish()`（顺序不变），由 `ST_SEND_GAP` 在 `sendSecondLine()` 之后调用。**不要求重排、不要求合并、不要求"顺便优化"** —— 搬移是零语义变更的操作，任何"改良"都会让 G5-2 的失败定位变难。

**验收方式**：改造后一轮内 `udp_tx` 必须**恰好 +2**（成功轮 hb+data）或 **+2**（失败轮 hb+err），且 `g_nextPollMs` 每轮只增一次。台架用串口逐轮打印 `seq/udp_tx/t0/t1` 核对。

> 注意 `!g_linkUp` 早退时（§2.3.2）本轮 `udp_tx` 增量为 **0**（两段都早退）或 **1**（半轮），这是**唯一允许**的非 +2 情况，须与"漏移语句"区分开。

### 2.5 ts 语义检查点

按 §2.3.1 的"共用同一个 ts"实现后，要求变成简单判据：

- **同轮 `hb.ts == data.ts` 恒成立（比例必须 = 100%）**
- **不得出现 `data.ts < hb.ts`**
- 若出现任何一条不满足 ⇒ 说明第二段自己重算了 ts，或递增护栏被绕过，**停下来查**

> 这条是拆分函数的"体检指标"：ts 一致就说明 `ts` 确实只在第一段生成了一次。

## 3. 改动 B：AES-128-GCM 加密

### 3.1 帧格式（严格按 `02_docs/22` §4.2）

```
偏移   长度    字段
0      1      版本字节 = 0x82（bit7=1 加密；低 4 位 = 协议版本 2）
1      12     nonce
13     n      密文（n = 明文 JSON 字节数，等长）
13+n   16     GCM Tag
────────────────────────────
总计   n + 29
```

- **AAD = 版本字节本身（1 B）** —— 接收端必须用同一个 AAD 解密
- **不需要长度字段**：UDP 保留报文边界，`len − 29` 即明文长度
- **明文/密文判别**：明文首字节恒 `0x7B`，密文首字节恒 `0x82`，不可能冲突

### 3.2 Nonce 构造（12 B）—— **不要自己发明**

```
nonce[0..3]  = CRC32(MAC 字符串) 低 32 位    启动算一次（设备维度）
nonce[4..7]  = boot_id                        NVS 持久化，每次启动 读→+1→立即 commit
nonce[8..11] = seq                            本行组装完成后的 g_seq
```

**唯一性论证（三段，缺一不可）**：
1. 同一 boot 内：`seq` 每行严格 +1 ⇒ 任意两条 nonce 不同
2. 跨 boot：`boot_id` 持久化且严格单调 ⇒ `nonce[4..7]` 不同
3. 回绕：`seq` 为 uint32，2 行/s 下约 68 年；`boot_id` 168 h 内为个位数

**必须否掉的错解**：`4B 设备ID + 4B seq + 4B millis()`。
`seq` 与 `millis()` **在重启时同时归零**，碰撞条件是"两次开机的第 N 条报文发送毫秒相同"——断电重启后 WiFi 连接耗时高度一致，落在同一毫秒的概率远高于 1/2³²。**毫秒字段对跨重启防重毫无贡献。**

**fail-closed 兜底**：若启动时 `boot_id` 读回校验失败（Flash 损毁/分区满），置 `enc_ready=false` 并**整体退回明文**，绝不允许用可能重复的 nonce 硬跑。

### 3.3 密钥与开关

| 项 | 要求 |
| --- | --- |
| 存放 | NVS `cfg485/aes_key`（16 B BLOB） |
| 写入 | Web 配置页 POST，**仅当键不存在时允许写**；页面只显示 `已配置 ****`，**绝不回显** |
| 编译默认 | `#define ENC_ENABLE_DEFAULT 0`（默认明文，便于 A/B） |
| 运行时开关 | NVS `cfg485/enc_on`（0/1），Web `/save` 可改，改完立即生效 |
| 不写 `secrets.h` | 会进 Git 历史，违反 `21` §7 凭据纪律 |

### 3.4 插入点与缓冲（最小侵入）

| 文件 | 改动 | 约束 |
| --- | --- | --- |
| `config.h` | 新增 `ENC_ENABLE_DEFAULT` / `NVS_KEY_AES_KEY` / `NVS_KEY_BOOT_ID` / `QI_ENC_BUF_MAX` / `QI_PROTO_VER` / `QI_TX_GAP_MS` | **不改任何既有宏的语义** |
| `.ino` | 只在 `udpSendLine()` 的 `g_udp.write()` 前插一层 `enc_pack()` | `buildDataJson/buildHeartbeatJson/buildErrJson` **一个字不动** |

**缓冲必须分开**：新增 `static uint8_t g_encbuf[QI_ENC_BUF_MAX];`（1280），**不复用 `g_payload`** —— mbedTLS 的输入输出缓冲重叠是未定义行为。

`udpSendLine()` 改造要点：
```c
const uint8_t *out = (const uint8_t *)g_payload;
size_t outLen = want;
if (g_encOn && g_encReady) {
  if (!enc_pack((const uint8_t *)g_payload, want, g_encbuf, sizeof(g_encbuf), &outLen)) {
    g_txFails++; return false;        // fail-closed：加密失败不发明文（否则静默降级）
  }
  out = g_encbuf;
}
```
- `udp_tx` 只在实际发出后 +1（语义不变）：**它数的是"发出去了几包"，与包长无关** ⇒ 加密前后 `udp_tx` 可直接对比
- **但 `payload_len` 语义变了**：加密后它记的是**密文长度 = 明文 + 29 B**。接收端入库的 `payload_len` 保持原始报文长度（§1.2），所以：
  - 台架核对包长时，加密轮与明文轮**不能直接比绝对值**，要看 `payload_len` 在两种模式下的差值是否**恒为 29 B**（G5-5）
  - 若某包差值是 0（=漏加版本字节）或 28/30（=nonce/Tag 长度算错），G5-5 立刻抓出来
- **绝不能"加密失败就发明文"** —— 那会让 A/B 对比悄悄失真，且 `payload_len` 变成 892/921 混杂，事后无法判断哪些是降级包

⚠️ **回环自测分支会连带被加密**：`RS485_MODE_LOOPBACK_SELFTEST=1` 走的是纯文本心跳 `"<ts> | HEARTBEAT"`（既有硬约束 6/13），它也过 `udpSendLine()` ⇒ 开 `enc_on` 会把它变成密文，接收端解出非 JSON 会记 `bad_json`。
**处置**：`enc_pack` 外面加 `#if !RS485_MODE_LOOPBACK_SELFTEST`（回环分支恒明文）。理由——回环模式验的是串口字节层，加密不是它的测试对象，混进来只会制造噪声，且回环模式从不上长跑。

### 3.5 密钥怎么产生、怎么保证两边一致（流程，不是代码）

代码之外最容易出错的一环：**钥匙配错 = 全盘 `decrypt_fail`，且现象和"加密实现有 bug"完全一样。** 按下面五步走，每步都有判据：

| 步 | 动作 | 判据 |
| --- | --- | --- |
| 1 | 在**旧电脑**生成：`python -c "import os;print(os.urandom(16).hex())"`（32 位 hex），存成 `key.hex`，**放仓库外**，权限仅当前用户 | 文件 32 字符、无换行污染（编辑器别加 BOM） |
| 2 | ESP32 配置页 POST 写入 → NVS `cfg485/aes_key` | 页面回显 `已配置 ****`，**不回显明文** |
| 3 | 接收端 `--key-file key.hex` | — |
| 4 | 先 `enc_on=0` 跑 5 min 确认链路通，再 `enc_on=1` 跑 5 min | `decrypt_fail=0` 且 `quality=OK` |
| 5 | 台架 G5-4/5 → A/B → 24h | 见 §6 |

**密钥打错了怎么办（必须有答案）**：`aes_key` 写入后**只许整体擦 NVS 重配**（走既有 `/reset`），代价是 WiFi/UDP/周期一起重填。**不要做"可覆盖"**——那等于留了个"谁都能换钥匙"的口子。所以**第 1 步的 hex 必须当场核对两遍**。

**密钥丢了不是灾难**：明文模式（`enc_on=0`）不依赖密钥，采集照样跑。只是那一段数据没有加密标记。

## 4. 接收端同步改动（3 处 + 回归自测，**必须与本批一起提交**）

### 4.1 `decrypt_frame()` 对齐文档格式（`udp_collect.py:713`）

```python
def decrypt_frame(data: bytes, key: bytes):
    """帧格式：1B 版本(0x82) + 12B nonce + ciphertext + 16B tag（AES-128-GCM）。
    AAD = 版本字节本身。失败一律返回 None（fail-closed）。"""
    if len(data) < 1 + 12 + 16 or data[0] != 0x82:
        return None
    try:
        from cryptography.hazmat.primitives.ciphers.aead import AESGCM
    except ImportError:
        raise SystemExit("使用加密需安装 cryptography：pip install cryptography")
    try:
        return AESGCM(key).decrypt(data[1:13], data[13:], data[0:1])   # AAD = 版本字节
    except Exception:
        return None
```

改动仅两处：`data[0] != 1` → `!= 0x82`；`None` → `data[0:1]`。

### 4.2 `payload` 存明文（`udp_collect.py:851`）

`_decode_payload()` 解密成功后，把 `recv["payload"]` 覆盖为明文字节；`recv["payload_len"]` 保持原始报文长度。见 §1.2。

### 4.3 新增 `--key-file`（避免密钥出现在命令行）

7 天长跑若用 `--key-hex`，密钥会出现在 `ps`/服务单元里。新增：
```
--key-file PATH   从文件读 32 位 hex（优先于 --key-hex；文件权限建议仅当前用户可读）
```
不加也行，但**长跑前必须用 `--key-file`**。

### 4.4 回归自测（改完必须全绿）

- `--selftest` 全绿
- 构造一个 `0x82` 帧做**加解密往返**：加密一段已知 JSON → `decrypt_frame` 应还原；改 1 B 密文应返回 `None`（Tag 校验）；改版本字节应返回 `None`
- `--env-check` 通过

## 6. 台架验证清单（**7 项全过才允许开长跑**）

| # | 项 | 判据 | 不过怎么办 |
| --- | --- | --- | --- |
| G5-1 | 50 ms 间隔真的存在 | 接收端按 `seq` 配对，`data.recv_mono − hb.recv_mono` 中位数 ≈ **0.050 s**、p99 < 0.2 s；改动前应 ≈0.000 | 查状态机是否提前跳走 |
| G5-2 | 节拍未漂移 + 失败轮标对 | 每轮 `udp_tx` **恰好 +2**；`g_nextPollMs` 每轮只增一次；连续 10 min 后 `poll_ok` 增量 ≈ 分钟数×60。**另做一次失败注入**（台架拔一下 485 `A` 线或断从站电源 2 秒）⇒ 那几轮必须上行 `type:"err"`，**不得出现 `data` 行**（查 §2.4 的复位块） | 查 §2.4 清单是否漏移/漏搬守卫 |
| G5-3 | ts 未倒退且同轮一致 | 同轮 `hb.ts == data.ts` **比例 = 100%**（§2.5 的硬判据，不是 ≥95%）；且**永不出现** `data.ts < hb.ts` | 说明第二段自己重算了 ts ⇒ 查 §2.3.1 |

| G5-5 | 无 IP 分片 | `max(payload_len)` **< 1472**（理论最坏 1135，余量 337）；且**逐包**满足 `密文 payload_len − 对应明文 payload_len == 29`（不是"平均 +29"） | 差值 ≠29 ⇒ 漏了版本字节 / nonce 或 Tag 长度算错 |
| G5-6 | 对账仍闭合 | `期望 = 收到 + 未发 + 丢`，残差 **= 0**；`M1` = 100% | 查 §2.4 |
| G5-7 | 明文/密文 A/B 可比 | 各跑 30 min，记录 `data_lost`/`hb_lost` 比值。**基线 15:1**；加密后若升到 **>20:1** ⇒ +29 B 有实质影响，须写进报告 | — |

## 7. 长跑方案（台架全过后）

**不要直接上 168h。** 按下面两步：

| 步 | 时长 | 目的 | 放行判据 |
| --- | --- | --- | --- |
| S1 | **24 h 昼夜**（起点选 **08:00**） | 验证新配置在白天高峰下的表现，与旧基线对比 | M2/M3 不低于旧基线；`decrypt_fail=0`；`q_drop=0`；对账残差 0 |
| S2 | **168 h** | 正式验收数据 | 34 条判据（`02_docs/24`，M3 按双条件 `02_docs/32` §8.6） |

**起点为什么选 08:00**：丢包集中在 09~17 点，08:00 起跑能让白天高峰落在 24 h 的中段，便于观察；若 22:00 起跑，高峰会被切在结束时。

**168h 期间必须带 `--key-file`**，并确认 `enc=1` 的数据行占 100%（若有 `enc=0`，说明开关没生效或退回明文了 → `--report-only` 的 `enc` 分布可直接看出来）。

## 8. 禁止事项（任一条违反即打回）

1. **禁止 `delay()` 实现 50 ms**（理由见 §2.3 三条）
2. **禁止复用 `g_payload` 做加解密缓冲**
3. **禁止用 `seq + millis()` 构造 nonce**
4. **禁止"加密失败就发明文"**（必须 fail-closed）
5. **禁止改动 `buildDataJson/buildHeartbeatJson/buildErrJson`** 的任何字段
6. **禁止在归档库上跑 `--repair` / `--verify-raw` 以外的写操作**；诊断前先 copy 副本
7. **禁止在台架 7 项未全过时启动 24 h**，更不许直接上 168 h
8. **禁止让回环自测分支进入加密路径**（`enc_pack` 必须在 `#if !RS485_MODE_LOOPBACK_SELFTEST` 内，见 §3.4 末）
9. **禁止把密钥写进 `secrets.h` / 提交说明 / 日志 / 串口打印**（连"前 8 位指纹"也不要打——"两边是不是同一把钥匙"用 G5-4 的 `decrypt_fail=0` 就能回答，不需要额外证据）

## 9. 建议执行顺序（给实施者）

1. 读 `02_docs/22` §4 全文 + 本文 §1~§4，先确认三处裁决无异议（有异议先提出，不要闷头改）
2. 接收端 4 处改动 + 自测（**先做接收端**：它没有编译链依赖，改完立刻能用合成帧验加解密往返）
3. 固件：50 ms 状态机（此时不加密，`ENC_ENABLE_DEFAULT 0`）→ 双模式编译 → 台架 G5-1/2/3/6
4. 固件：加密（`enc_pack` + nonce + NVS）→ 双模式编译 → 台架 G5-4/5
5. **按 §3.5 五步配密钥**（先生成 → Web 写入 → `--key-file` → 明文 5 min → 密文 5 min）。这一步**不要跳**：钥匙配错和加密写错的现象一模一样，跳了就是把两类故障混成一种
6. 明文/密文 A/B 各 30 min → G5-7 → 出结论
7. 24 h 昼夜 → 报告给主控 → 放行后才排 168 h
