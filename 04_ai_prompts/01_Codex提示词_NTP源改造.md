## 1. 背景（Codex 看不到对话，以下为完整上下文）

### 1.1 现状

`config.h` 当前 NTP 相关三行：

```c
#define NTP_SERVER           "ntp.aliyun.com"    // 主：域名（依赖 DNS）
#define NTP_SERVER_IP        "203.107.6.88"      // 备选：IP 直连
#define NTP_TZ_INFO          "CST-8"             // 东八区 UTC+8
```

`esp32c3_gateway.ino` 中用 `configTzTime(NTP_TZ_INFO, NTP_SERVER, NTP_SERVER_IP)` 对时，
调用点在 `ntpTick()`（首次连上 WiFi 后触发 / 未同步时每 60s 重试）。

### 1.2 新增事实：导师提供了校内 chrony 源

导师张振亚（2026-10-02）通知：**内网 `172.16.0.2` 上有 chrony 服务，可直接用于对时。**

### 1.3 我方实测（2026-10-04，工具 `06_tests/ntp_probe.py`）

| 源 | 可用 | stratum | 往返延迟 | 备注 |
| --- | --- | --- | --- | --- |
| **`172.16.0.2`** | ✅ | 2 | **3.4 ms** | 校内 chrony |
| `ntp.aliyun.com` | ✅ | 2 | 41.0 ms | 公网 |
| `203.107.6.88` | ✅ | 2 | 40.8 ms | 公网（IP 直连） |

- 三者报出的 UTC 时间**完全一致** ⇒ chrony 时间正确，且**确实开放 NTP 服务**（不是只做上游同步）。
- 电脑侧路由已确认：去 `172.16.0.2` 走 **WLAN → 192.168.1.1**（不是 VMware 虚拟网段），ping 3–5 ms。
- ⚠️ `172.16.0.0/12` 是私网段，与 ESP32 所在的 `192.168.1.0/24` **不同网段**，靠校园网路由打通 —— 因此 ESP32 侧**仍需实测确认**（见 §5 验收）。

## 2. 改动要求

### 2.1 `config.h` —— 拆成三个源

```c
// ---------------------------------------------------------------
// 时间同步（NTP / SNTP）—— 三源，按序尝试
// ---------------------------------------------------------------
#define NTP_SERVER_1         "172.16.0.2"        // 主：校内 chrony（导师提供）
                                                 //   实测 2026-10-04：stratum 2 / RTT 3.4ms
                                                 //   ⚠️ 仅在校园网内可达
#define NTP_SERVER_2         "ntp.aliyun.com"    // 备 1：公网域名
#define NTP_SERVER_3         "203.107.6.88"      // 备 2：公网 IP 直连（DNS 不可用时仍能对时）

// ⚠️ 必须写 "CST-8"，不可写 "<CST-8>"：POSIX TZ 中尖括号用于引用分区"名称"，
//    写成 "<CST-8>" 时整个 "CST-8" 被当成名称、偏移量缺省为 0 → 等效 UTC（曾导致时间差 8 小时）。
#define NTP_TZ_INFO          "CST-8"             // 东八区 UTC+8（CST = UTC+8 分区，POSIX TZ 串）
```

**为什么必须保留公网源（重要，不要"优化"掉）**：

> 项目的网络退路方案是**手机 2.4GHz 热点**（学校 WiFi 不可用时启用，见 `00_context.md` 网络环境与裁定）。
> 在手机热点下 `172.16.0.2` **必然不可达** ⇒ 若把它当作唯一源，退路一启用就会退回 `BOOT+xx` / `UNSYNCED`，时间戳全部失效。
> **主源 + 公网兜底是硬要求。**

**兼容性**：旧的 `NTP_SERVER` / `NTP_SERVER_IP` 宏若在别处被引用，一并改名；
**不得留下悬空引用，也不要保留无用的兼容宏**（本项目尚未发布，不需要向后兼容）。

### 2.2 `esp32c3_gateway.ino` —— 三源调用 + 日志

1. `configTzTime` 改为三源：
   ```c
   configTzTime(NTP_TZ_INFO, NTP_SERVER_1, NTP_SERVER_2, NTP_SERVER_3);
   ```
   （`ntpTick()` 内两处调用点都要改：首次连上触发的、以及 60s 重试触发的。）

2. 所有引用旧宏名的打印同步（`setup()` 与 `ntpTick()` 中各有一处）。

3. **【本次重点｜日志增强】让日志能看出实际生效的源。**

   现状：同步成功的日志只打印**配置名**，例如
   ```
   [NTP] 时间已同步：本地 2026-10-04 22:15:03 +0800（TZ=CST-8，源 ntp.aliyun.com / 备选 203.107.6.88）
   ```
   ⇒ **无法判断 NTP 到底走了内网还是落到了公网**。这是本次必须解决的观察盲区。

   要求：同步成功后，日志中要能看出**实际应答的那个服务器的 IP**。

   实现提示（**请先确认 API 在当前 core（arduino-esp32 3.3.10）中确实存在，不要凭记忆写**）：
   - 首选：ESP-IDF 的 SNTP 查询接口，如 `sntp_getserver(0)` / `esp_sntp_getserver(0)`，取回实际使用的服务器地址后打印其 IP。
   - 若该 API 在当前 core 不可用或不稳定：退一步打印 `configTzTime` 的**返回值**（`0` = 成功）作为辅助判据，并保留配置名打印。
   - 无论走哪条，**不得**为了这个日志引入新的第三方库。

   期望效果（示意）：
   ```
   [NTP] 时间已同步：本地 2026-10-04 22:15:03 +0800（TZ=CST-8）
   [NTP] 实际生效源：172.16.0.2（三源配置 主=172.16.0.2 / 备1=ntp.aliyun.com / 备2=203.107.6.88）
   ```

4. `setup()` 中的启动打印要能看出三源配置（主 / 备1 / 备2 各自的值）。
   **注意**：按现状，`setup()` 中**不调用** `configTzTime`（时序要求：必须等 WiFi 连上后再初始化 SNTP，
   由 `wifiTick()` 置 `g_ntpResyncPending` → `ntpTick()` 调用）。**这个时序不要改。**

## 3. 不要动的东西（硬约束，逐条确认）

| # | 约束 | 原因 |
| --- | --- | --- |
| 1 | `NTP_TZ_INFO` 的值保持 `"CST-8"`（不加尖括号） | 历史故障：加尖括号会差 8 小时 |
| 2 | `RS485_CHAR_TIMEOUT_MS` **保持 25**，**不得改回 4~8** | 那是 **M5 第一次烧录**时才做的动作；提前改会破坏 M4 验收记录（`02_docs/15`）的复现条件 |
| 3 | MODBUS 功能码**保持 `0x03`**、回环帧 `01 03 00 00 00 02 C4 0B` 不动 | `0x04` 是 M5 的改动 |
| 4 | `UDP_TARGET_IP` / `UDP_TARGET_PORT` / `UDP_LOCAL_PORT` 不动 | 与本次无关 |
| 5 | `RS485_DE_PIN` 保持 `-1`（MAX13487，EN 固定高电平） | 硬件安全红线 |
| 6 | 不得引入 `delay()`（`setup()` 内既有的 USB CDC 有界等待除外） | 非阻塞状态机约束 |
| 7 | 不得引入第三方库 | 全项目约束 |
| 8 | 不改 `02_docs/`、`README.md`、`04_ai_prompts/` | 职权边界 |

## 5. 验收标准（WorkBuddy 侧会在烧录后按此核对）

1. 编译通过，无遗留报错。
2. 串口启动日志能看出 **三源配置**（主 / 备1 / 备2）。
3. **「时间已同步」日志能看出实际生效的源 IP** —— 这是本次的核心交付。
4. §3 的 8 条硬约束逐条未被破坏（请在提交信息里逐条确认）。
5. 烧录后（由用户执行）：
   - 校园网下：应观察到实际生效源为 **172.16.0.2** ⇒ 验证 ESP32 侧确实可达内网 chrony（**这是本项目首次在设备侧确认该路径**）。
   - 若落到公网源：说明 ESP32 到 `172.16.0.2` 不通（可能被路由/防火墙隔断），**如实报告，不要调参硬凑** —— 那就把内网源降级为"可选"，仍以公网为主。**这条结论必须回写文档，所以请把串口原始输出交给 WorkBuddy。**
