## 1. 现象（原始日志，逐行照抄）

```
[NTP] 时间已同步：本地 2026-10-05 06:39:55 +0000（TZ=CST-8）        ← ① 时区显示 +0000（应为 +0800）
[NTP] 实际生效源：暂未能从 SNTP 读取（三源配置 主=172.16.0.2 / 备1=ntp.aliyun.com / 备2=203.107.6.88）   ← ② 核心交付没打出来
[M4] 超时（首字节 80ms / 字符间隔 25ms / 兜底 300ms）RX=0 期望 9
[M4] 超时（…）RX=0 期望 9
[WIFI] 已连接 SSID=402FBS RSSI=-60 dBm IP=192.168.1.200 GW=192.168.1.1     ← ③ WiFi 到这一步才连上
[NTP] WiFi 已连上 -> 触发 SNTP 对时 TZ=CST-8 主=172.16.0.2 备1=ntp.aliyun.com 备2=203.107.6.88   ← ④ 到这一步才 configTzTime
[M4] 超时（…）RX=0 期望 9
[UDP -> 192.168.1.114:8888] 2026-10-05 14:39:58 | HEARTBEAT             ← ⑤ 从这里起本地时间完全正确
```

**关键点：① 和 ② 出现在 ③（WiFi 连上）与 ④（`configTzTime` 调用）之前。**

## 2. 根因分析（WorkBuddy 结论，请独立复核）

ESP32 的 RTC 域在**复位后仍然保留**（芯片不断电即保留）。本次是烧录后软复位，RTC 里已经带着上一轮 NTP 同步过的正确时间。

于是：

1. 开机后 `ntpTick()` 里的 `getLocalTime(&now, 0)` **立即返回 true** —— 因为 RTC 有有效时间，与"是否刚跟 NTP 对过时"无关。
2. 代码据此把 `g_timeSynced` 置为 true ⇒ **在 WiFi 还没连、`configTzTime` 还没调、TZ 尚未生效的时刻**，就打印了「时间已同步」⇒ `%z` 读到默认时区 = **+0000**（①）。
3. 紧接着调用 `logNtpEffectiveSource()` ⇒ 此刻 SNTP **一次包都还没收到**，三个 slot 的 `sntp_getreachability()` 全为 0 ⇒ 走兜底分支（②）。

**⇒ ① 和 ② 是同一个根因的两个表现：`getLocalTime()` 的返回值不能用来判「已同步」。**
**⇒ 时区本身没坏**（⑤ 证明 `CST-8` 生效、本地时间正确）；坏的是**判定时机**。

### 附带影响（同样由该根因引起，请一并考虑）

- `g_timeSynced` 被过早置位后，**「时间同步丢失 → 降级 UNSYNCED」这条路径会被掩盖**：只要 RTC 里有旧时间，
  就算 NTP 永远不通，设备也会一直认为自己"已同步"。这对"时间戳可信度"是个隐患。
- 冷启动（断电上电）时 RTC 无有效时间，`getLocalTime()` 会返回 false ⇒ 那时日志反而是对的
  （这也解释了为什么 M2 阶段的自检通过、问题直到现在才暴露）。

## 3. 改动要求

### 3.1 用 SNTP 的真实状态判「已同步」，不要用 `getLocalTime()`

「本次会话是否真的收到过 NTP 回包」才是判据。可用手段（**请先确认 API 在本 core 3.3.10 中确实存在，不要凭记忆写**）：

- `sntp_getreachability(i) != 0`（任一 slot 有过回包）—— 上一轮已核实该 API 可用；
- 或 `sntp_get_sync_status() == SNTP_SYNC_STATUS_COMPLETED`（请核实枚举名）；
- 或自记一个标志：**「本轮已调用过 `configTzTime`」且「其后某 slot 的 reachability 非 0」**，两者同时满足才算同步。

要求：**冷启动与复位后行为一致** —— 复位后即使 RTC 有旧时间，也**不得**在收到 NTP 回包之前打印「时间已同步」。

### 3.2 修好「降级」路径

`ntpTick()` 中 `[NTP] 时间同步丢失：降级为 BOOT+ 计数` 的触发条件，也要改成基于同一判据，
使「NTP 不通」在复位后同样能被正确识别（而不是被 RTC 旧时间掩盖）。

### 3.3 `logNtpEffectiveSource()` 改为「全量打印」而不是「找到第一个就 return」

现状：找到第一个 `reachability != 0` 的 slot 就打印并 return；一个都没命中则打兜底。
**问题：时序稍不对就完全没有信息量**（本次就是）。

改为**三个 slot 全都打印**，例如：

```
[NTP] 源状态：slot0=172.16.0.2 reach=0x01 | slot1=<解析后IP> reach=0x00 | slot2=203.107.6.88 reach=0x00
```

或至少在有 hit 时逐条打印、无 hit 时打印三个 slot 的 IP 与 reachability。
**目标：无论时序如何，这条日志永远能告诉我们"哪个源回包了"。**

调用时机：在**判定为真正同步之后**调用一次；可选地再隔 N 秒补打一次，便于人工确认。
