## 任务 2：三条 SQL / 小脚本（核心，8 分钟）

> 心跳字段没有独立表，都在 `udp_packet.payload`（JSON）里。SQLite ≥3.22 有 json1 可直接用；
> 如果 `json_extract` 报错，就写个 10 行 python 逐行 `json.loads` 统计——两者等价。

### 2-A `clk_hold` / `clk_back` / `reconn` 分布（Y-4 交叉证据）

```sql
SELECT json_extract(payload,'$.clk_hold') AS clk_hold,
       json_extract(payload,'$.clk_back') AS clk_back,
       COUNT(*) AS cnt
FROM udp_packet
WHERE ptype='hb' AND payload IS NOT NULL
GROUP BY 1,2 ORDER BY cnt DESC LIMIT 20;
```

**主控要看什么**：`clk_hold` 是否**>0**（168h 里 lwip 每 3h 自同步一次，理论必然触发钳位或 ts 护栏）。
若全程 `clk_hold=0` ⇒ `02_docs/24` Y-4 交叉证据判"未验证"，报告里要如实写。

### 2-B `boot` / `reset` 序列（世代对账的最后一环）

```sql
SELECT json_extract(payload,'$.boot')  AS boot,
       json_extract(payload,'$.reset') AS reset,
       COUNT(*) AS cnt,
       MIN(recv_time) AS first_seen,
       MAX(recv_time) AS last_seen
FROM udp_packet
WHERE ptype='hb' AND payload IS NOT NULL
GROUP BY 1,2 ORDER BY first_seen;
```

**主控要看什么**：应为 **3 个世代段**，每段内 `boot` 从小到大单调、`reset` 一致（POWERON/USB/BROWNOUT…）。
10-29 两次拔电对应两个新段的 `reset=POWERON` 或 `BROWNOUT`。

### 2-C **电量全量重算**（D-10 验证，最重要）

库里的 `meter_record` 电量列是**入库时旧脚本算的（错式，放大 1000 倍）**，**不要用它**。
请写一个小脚本从 `raw_hex` 全量重算（56 万行，纯本地）：

```python
# 电量重算规格（D-10）：raw = 78 字节空格分隔 HEX，reg[i] = int(bytes[2i:2i+2],16)
# A 相: H=reg[14] L=reg[15]   B: H=reg[23] L=reg[24]   C: H=reg[32] L=reg[33]   合相: H=reg[37] L=reg[38]
# energy = (H*65536 + L) / 1000    ← 单位：度（kWh）
# 输出四列 CSV: recv_time, phase, energy_kwh   （只存 energy 发生变化的行即可）
```

对四条序列各做三个检查，**把结果直接贴回来**：

1. **单调性**：`energy` 是否全程单调不减（允许相等，不允许下降）
2. **跨进位**：找 `L` 从 ≥60000 跳到 <6000 的时刻（即 65535→0 进位），确认该点 `energy` 变化量是 **+0.0xx 度**（连续），而不是暴跌
3. **收支对照**：`(末值 − 初值) 度` vs `SUM(A_power)/1000/3600 度`（功率积分），两者应在 ±15% 内吻合

**预期**：起跑约 321 度、收尾约 321 + 总耗电量；四相中合相 = A+B+C 之和（±0.01 度内）。
