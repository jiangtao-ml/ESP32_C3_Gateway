> **结论先行**：M4 卡了 5 天的根因是 —— **485 模块丝印 `TXD` / `RXD` 是「交叉」约定，不是同名对接**。
> 而它之所以能骗过所有人 5 天，是因为**它的症状和"模块损坏 / 未供电"一模一样**（双向全断、模块电源灯仍亮）。

---

## 1. 最终结论

### 1.1 根因（一句话）

> **`GPIO21` 必须接模块 `RXD`、`GPIO20` 必须接模块 `TXD`。**

模块丝印写的是**模块自身的收发方向**，不是"你那边接什么"：

| 模块丝印 | 实为芯片引脚 | 方向 |
| --- | --- | --- |
| `TXD` | `RO` | 接收**输出** → 应接 MCU 的 **RX** |
| `RXD` | `DI` | 发送**输入** → 应接 MCU 的 **TX** |

### 1.2 结果（2026-10-04 21:33 实测）

```
[M4] 解析 OK ADDR=1 FUNC=0x03 DATA=00 0A 00 14
      REG: [0]=10 [1]=20  CRC=3EDA
```

连续 **65 秒**：解析 OK **65** / 超时 **0** / CRC 失败 **0** / 帧长异常 **0**。

---

## 2. 为什么这个故障能骗过 5 天

按"同名对接"接线后的真实电路状态：

| 接线 | 实际发生 | 表象 |
| --- | --- | --- |
| `GPIO21`（TX）→ 模块 `TXD`（实为芯片 `RO` 输出） | **两个输出对撞** | 不发热、不冒烟、看不出异常 |
| 芯片 `DI`（真正的发送入口） | **悬空，从未被驱动** | 驱动器一点差分都不输出 |
| `GPIO20`（RX）← 模块 `RXD`（实为芯片 `DI` 高阻输入） | 接收端挂在输入脚上 | 永远收不到数据 |
| 模块 `VCC` / `EN` | 供电正常 | **电源指示灯正常点亮** |

**净效果：总线双向全死，而板子看起来完全正常。**

这就是本故障的全部杀伤力 —— 它同时伪造了三个"硬件坏了"的特征：

1. 收发全无（像收发器坏了）
2. 电源灯亮（排除了"没供电"这个思路）
3. 换新模块同样全无（看起来像"两只都坏"或"板子有问题"）

## 4. 六个骗过我们的陷阱

> 这一节是本文最有价值的部分。**每一个陷阱都足以让一次排障绕上几小时。**

### 4.1 陷阱一：「A/B 短接自环」是无效方法

**做法**：把 USB 转 485 模块的 A、B 短接，从串口发 `abc`，看是否回显。

**为什么看似合理**：这是 TTL 串口"TX 接 RX 自环"的思维惯性；网上也广泛流传。

**为什么无效**（物理原因）：

- 两线 RS-485 是**半双工**，收发共用一对差分线。
- **短接 A/B 后差分电压 `V_AB ≡ 0`**，而接收器判据是 `|V_AB| > 200mV` → 0V 正好落在判定窗口**正中间**。
- 标准 fail-safe 接收器（SP485 等）此时输出落入 **Indeterminate（不确定区）**；带 full-fail-safe 的器件则**恒输出高（空闲态）**。
- ⇒ **健康的模块同样不会回显。**

**权威依据**：

| 来源 | 原文要点 |
| --- | --- |
| Industrial Monitor Direct 知识库 | 短接 A/B 使差分塌到 0，**不会回显**；真正的两线 485 回环**必须两个物理 485 端口** |
| Renesas KB（fail-safe 释义） | 短路时 `Vdiff = 0V` 属**无效 RS-485 状态**；fail-safe short 器件保证输出恒高 |
| MaxLinear XR33156 应用笔记 | 标准 fail-safe 接收器在**短路 / 端接**时 `RO = INDETERMINATE` |
| US Converters 知识库 | 无 Echo-On 选项的转换器，回环测试**必须用第二个 485 端口** |

**造成的实际损失**：

1. **旧 USB 转 485 模块被误判"物理损坏"**（`02_docs/07` §4.3）→ 用户额外购买了新模块。当晚用**双端口互测**证明：**旧模块（黑，FTDI）收发完全正常，双向 5/5。**
2. 我（WorkBuddy）在 19:41 又让用户做了一次同样的无效测试（MAX13487 A/B 短接），结论同样不可用。

**正确做法**：

> **两个 485 端口背靠背互测**（A↔A、B↔B、GND 共地）。
> 本项目天然具备这个条件：`USB 转 485`（电脑侧）↔ `MAX13487`（ESP32 侧）本身就是一组合法互测 —— **也就是说，"M4 测试"本身就是那个有效测试。**

---

### 4.2 陷阱二：同一个现象有多个成因（`RX=0`）

`RX=0`（一个字节都没收到）在本次排障中至少对应过 **7 种**不同原因：

| # | 原因 | 关键鉴别 |
| --- | --- | --- |
| 1 | 烧录未生效（跑的是旧固件） | 看固件"指纹"：`字符间隔`值 / UDP 目标 IP / 心跳标签 |
| 2 | 电脑侧根本没人应答 | 检查从站脚本/工具是否在跑 |
| 3 | 模块未供电 | 电源指示灯 / 万用表 |
| 4 | `A/B` 没接到同一对节点 | 用已验证模块对在同一节点互测 |
| 5 | 逻辑侧线插错行 / 错半边 | 目视 + 用 MCU 当通断表 |
| 6 | **`TXD`/`RXD` 约定相反**（本次真凶） | **对调这两根线看现象是否变化** |
| 7 | 引脚本身损坏（曾被 5V 直灌） | 短接回环自检 |

**教训**：`RX=0` 不是"一个故障"，而是"一个**类的症状**"。
**排障必须把它拆成"可独立验证的子命题"**，而不是围着同一个现象反复换件。

---

### 4.3 陷阱三：同一个现象由两个独立样件重现 → 会诱导"都坏了"的错误结论

**这个陷阱今晚踩了两次：**

| 次 | 现象 | 当时的错误直觉 | 实际 |
| --- | --- | --- | --- |
| 1 | 旧模块 + 新模块，A/B 短接自环**同样无回显** | "都是坏的？" | **方法本身无效**，两个模块都好好的 |
| 2 | 旧 MAX13487 + 新 MAX13487，**同样总线全死** | "模块都不行？" | **接线口径错**，两只模块都没问题 |

**教训（已写入长期记忆）**：

> **同一现象由两个独立样件重现时，优先怀疑"接线 / 口径 / 方法 / 工具"，而不是"两个都坏"。**

这条法则如果在第一次就生效，今晚可以少走两个小时。

---

### 4.4 陷阱四：测试设计的盲区 ——「验线通」≠「验落点」

**测试 T 的设计**：`GPIO21 →(原有线)→ 用户认定的 TXD 行 →(新跳线)→ GPIO20`，
ESP32 收到自己的 8 字节 ⇒ 判定"`GPIO21 → TXD` 这根线是好的"。

**盲区**：它只证明了**那根导线是通的**，**无法证明"用户插的那个孔，就是模块 `TXD` 引脚所在的孔"**。
如果整体错了一行，测试 T 依然通过。

**教训**：

> **"验线通"和"验落点"必须拆成两个独立测试设计。**

**补充的"验落点"思路（测试 U）**：利用模块**逻辑侧 `GND` 与总线侧 `GND` 在模块内部是同一节点**这一事实，
让信号"穿过模块"走一圈 —— 若通，说明两侧引脚都真的插进了面包板。
（本次测试 U 未通过，但因存在"引脚未接触"与"测试未做对"两种解释，未能定论；见 §6 待办。）

---

### 4.5 陷阱五：丝印会读反（两处，两次）

| 位置 | 错误读法 | 正确读法 | 后果 |
| --- | --- | --- | --- |
| 总线侧 3 脚顺序 | `GND / A / B` | **`B / A / GND`** | 按错序接会把 `B` 接到 `GND` 上 → 总线差分永远出不去 |
| 逻辑侧 `TXD`/`RXD` 语义 | 同名对接（`TXD`→MCU 的 TX） | **交叉对接**（`TXD`→MCU 的 RX） | **本次 M4 卡 5 天的真凶** |

**两次都发生在"对着照片核对丝印"这一动作上** —— 第一次是 Codex（2026-10-03，把 3 脚排读成 `GND/A/B`，且该错序被写进审查报告固化），第二次是 WorkBuddy（把 `TXD`/`RXD` 定为同名）。

**教训**：

> **丝印判读必须留证据**（放大截图 + 逐字记录），而且**判读结果与被测现象不符时，第一件事是回头复核丝印**，而不是继续换件。
> **对丝印的"常识性假设"（比如"TXD 当然接 TX"）是本项目最高频的致错点。**

---

### 4.6 陷阱六：面包板的"隐形断路"

面包板有两个**用眼睛几乎看不出**的断路方式：

| 陷阱 | 说明 |
| --- | --- |
| **中央凹槽隔断** | 同一行的 `a–e` 与 `f–j` 是**两个互不导通的节点**。模块跨在凹槽上，其两排脚分居两侧。把线插到"同一行的另一半边"→ **看着接上了，实际断路**。 |
| **整排错行** | 插到相邻一行 → 同样看着接上了。 |

**对本项目的具体影响**：
MAX13487 模块跨中央凹槽，**总线侧 3 脚在 `f–j`，逻辑侧 5 脚必在 `a–e`**。
—— 这类问题**只能靠"看清引脚实际落在哪一行哪半边"解决**，问话问不出来，也不该靠猜。

## 5. 方法论沉淀（可复用的排障法则）

### 5.1 七条法则

1. **分层搭建，每层单独验证。** 一次接完再测 = N 个变量同时上场，任一错都表现为同一个症状。
2. **同一现象由两个独立样件重现 → 优先怀疑方法，不要怀疑器件。**
3. **"验线通"与"验落点"分开设计。** 导线连通 ≠ 接点正确。
4. **给固件留"指纹"。** 本次靠 `字符间隔` 值 / UDP 目标 IP / 心跳标签，一眼判定"烧录是否生效"。
5. **免仪表也要先穷尽"能用代码测的"再上仪器。** 本次用三招顶替了万用表：双端口互测、MCU 当通断表、只读监听。
6. **丝印判读留证据、并接受复核。** 与现象不符时先回头复核丝印。
7. **改动只做单变量。** 每次只动一处，改完立刻复测。

### 5.2 免仪表的能力边界（本次实测得出）

| 待验证的事 | 免仪表能否做到 | 方法 |
| --- | --- | --- |
| 485 模块收发是否正常 | ✅ | 双端口背靠背互测（`two_port_loopback.py`） |
| 节点 / 布线是否连通 | ✅ | 用已验证的模块对在同一节点互测 |
| 器件是否在驱动总线 | ✅ | 多口只读监听（`bus_sniff.py` / `m4_verify.py`） |
| MCU 引脚与串口通路 | ✅ | 短接 TX↔RX 回环自检 |
| **器件是否通电（VCC 有无 5V）** | ❌ | **必须万用表** |
| 引脚电气特性（电平、驱动能力） | ❌ | **必须万用表 / 示波器** |
| 两点之间是否导通 | ⚠️ | 只能间接（让信号穿过被测物） |

### 5.3 症状 → 优先怀疑（速查表）

| 症状 | 优先怀疑（按序） |
| --- | --- |
| **双向全断 + 模块电源灯亮** | **① `TXD`/`RXD` 约定接反（同名 vs 交叉）** ② 引脚整排错行 / 错半边 ③ 模块未插实 |
| 双向全断 + 模块不亮 | 供电（`VCC` / `GND` / 5V 来源） |
| 只有发送方向不通 | `MCU TX → 模块发送输入` 这一段 |
| 只有接收方向不通 | `模块接收输出 → MCU RX` 这一段（含分压） |
| 收到数据但 CRC 全败 / 偶发乱码 | 未共地 / 偏置不足 / 极性反 / 波特率不一致 |
| 一发就收到自己的请求帧 | 接收器被常开（`MAX485/3485` 的 `EN` 固定接高） |
