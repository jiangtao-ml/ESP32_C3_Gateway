## 1. 七环链路

### 环 ①　电表里有什么：39 个输入寄存器

`STB3-125` 把整台配电箱的用电状态摊在 39 个 16 位寄存器里，只能读（功能码 `0x04`）。

| 寄存器 | 含义 | 换算 |
| --- | --- | --- |
| 0 | 开合状态 | `%04X` 原始十六进制 |
| 1 / 2 / 3 | 分闸记录 ×3 | `%04X`（半字节 = 一条记录） |
| 4 | 频率 | **÷10** → Hz |
| 5 | 漏电流 | **÷1000** → A |
| 6 | N 线（板载）温度 | **−40** → ℃ |
| 7–15 | **A 相** 9 个 | 见下 |
| 16–24 | **B 相** 9 个 | 同上 |
| 25–33 | **C 相** 9 个 | 同上 |
| 34 / 35 / 36 | 总有功 / 无功 / 视在 | 1:1 |
| 37 / 38 | 总电量 高字 / 低字 | `H×65536/1000 + L` → 度 |

**每相的 9 个**（以 A 相 = 7 为基址）：

| 偏移 | 字段 | 换算 |
| --- | --- | --- |
| +0 | 温度 | **−40** |
| +1 | 电压 | 1:1（V） |
| +2 | 电流 | **÷100**（A） |
| +3 | 功率因数 | **×0.01** |
| +4 | 有功功率 | 1:1（W） |
| +5 | 无功 | 1:1（VAR） |
| +6 | 视在 | 1:1（VA） |
| +7 / +8 | 电量 高字 / 低字 | 同总电量 |

> 🔴 **字段口径只认 `05_hardware/STB3-125_字段字典.csv`**。
> `06_QI协议说明.md` §5.3 与操作卡 §9 的换算表**缺 12 项**，冲突时以 CSV 为准。
>
> ⚠️ **两个已知的"假数据"陷阱**：
> 1. **A/B/C 相温度恒为 −40 ℃** —— 该型号不上报接线柱温度，raw 恒 0，−40 是量程下限的伪装值。
>    固件用 `QI_PHASE_TEMP_ABSENT=1` 把它排除在 `invalid` 外，**否则 quality 永远是 PARTIAL**。
> 2. **电量公式存疑**：文档写 `(H×65536)/1000 + L`；若真实语义是"32 位累加器、单位 0.001 度"，
>    正确式应为 `(H×65536 + L)/1000`，**两者差 1000 倍**。当前按文档实现，待实测定案（`PROGRESS` §8 待确认）。

### 环 ②　怎么问：请求帧与自适应

```
01  04  00 00  00 27  B0 10
│   │   └─┬─┘  └─┬─┘  └─┬─┘
│   │     │      │      └── CRC16（低字节先）
│   │     │      └───────── 读 39 个寄存器
│   │     └──────────────── 起始地址 0
│   └────────────────────── 功能码 0x04 = 读输入寄存器
└────────────────────────── 从站地址 1
```

| 模式 | 请求 | 期望响应 | 何时 |
| --- | --- | --- | --- |
| **一帧读全**（默认） | `01 04 00 00 00 27 B0 10` | **83 B**（3 头 + 78 数据 + 2 CRC） | 启动即用 |
| **3 段降级** | 分 3 次读 16/16/7 个寄存器 | 37 / 37 / 19 B | 从未成功 **且**连续 3 轮失败才降 |

> 🔴 **`0x03` 与 `0x04` 严禁混用**：`0x03` 读的是**保持寄存器（配置值）**，
> 用它等于拿到一堆语义错误的数据。M3/M4 阶段的回环帧 `01 03 00 00 00 02 C4 0B` 只属于历史，
> 真机一律 `0x04`。
>
> E-02 已结案 = **真机接受一次性读 39 个寄存器**（384 轮 100%），"上限 16"对 `0x04` 不成立。

### 环 ③　固件怎么收发：非阻塞状态机

```
IDLE ──到点──► TX ──flush──► WAIT_RX ──收满帧长──► PARSE ──► SEND ──► IDLE
                              │
                              └─超时─► 判失败 ──► SEND(err 行) ──► IDLE
```

**为什么非阻塞**：主循环里还要跑 Web 服务、NTP、LED，`delay()` 会把 UI 卡死。

**三级超时，各管一件事**：

| 级别 | 值 | 管什么 |
| --- | --- | --- |
| 首字节超时 | 80 ms | 从站在不在？ |
| 字符间隔 | **8 ms** | 一帧是否已结束（半帧判定） |
| 兜底 | 300 ms | 整帧上限 |

> ⚠️ **字符间隔 ≠ 整帧上限**：83 字节 @9600 本身要 ~86.5 ms，所以兜底不能低于 120 ms。
> ⚠️ 8 ms 这个值是 M5 真机档位。M4 期间曾临时放到 25 ms，因为**PC 端 USB 转 485 的批量交付**会造成
> >4 ms 的字节间隙，被误判成半帧（见 `02_docs/15` §4.1）。真机是纯硬件 UART，不受影响。

**软件不知道总线忙**：MAX13487 是 AutoDirection（无 DE 脚），没有方向状态反馈。
所以**不要**引入"GPIO 轮询总线忙"这类逻辑 —— 它读不到真实状态，只会引入新 bug。

### 环 ④　怎么判断数据可不可信

收到的帧要过两道关：

**第一道 · 帧长对账**（P0-1 加固，`b7f5942`）
响应帧长必须**与本段请求的寄存器数一致**。堵的是一个很隐蔽的坑：
三段模式下 `g_merged` 是 78 字节合并缓冲，**没有清零点**，只按段偏移覆写。
若某段回了**短帧**却仍被接受，就会留下上一轮的旧值 —— 数据看着正常，其实是掺假的。

**第二道 · 量程校验 → `invalid` / `quality`**

| 判定 | 触发 |
| --- | --- |
| `frequent` | 频率 > 100 Hz |
| `leakage_current` | 漏电流 > 1 A |
| `N_temp` | 温度越出 −40 ~ 160 ℃ |
| `A/B/C_voltage` | 相电压 > 600 V |
| `A/B/C_Pf` | 功率因数 > 1.0 |

- 全通过 → `quality: "OK"`
- 有任一字段进 `invalid` → `quality: "PARTIAL"`，**且 `invalid` 里写明是哪几个**

> 这条设计的价值：**下游不用猜"这条数据靠不靠谱"**，字段自己说了。

### 环 ⑤　上行长什么样：JSON 三种行

**每轮最多两行**：一行心跳 + 一行数据（或错误）。

| 类型 | `type` 字段 | 什么时候发 | 作用 |
| --- | --- | --- | --- |
| 数据行 | 无（默认） | 采集成功 | 业务数据 |
| 心跳行 | `"hb"` | 每轮都发，**在 WiFi 判断之前** | 让接收端能算出"设备到底跑了几轮" |
| 失败行 | `"err"` | 采集失败 | 失败也要可见，不能静默 |

**数据行的字段**（按 JSON 出现顺序）：

```
seq, dev, mac, ip, ts, ts_ok
openState, record1, record2, record3
frequent, leakage_current, N_temp
A_temp, A_voltage, A_current, A_Pf, A_power, A_Q, A_S, A_H, A_L      ← B、C 相同构
power, Q, S, H, L
quality, invalid, seg, raw
```

| 字段 | 含义 |
| --- | --- |
| `seq` | 全局自增，**每发一行 +1**（正常轮：奇数=心跳、偶数=数据） |
| `dev` | `ESP485-<MAC 后 6 位>`，多设备区分用 |
| `ts` / `ts_ok` | NTP 时间 / 时间是否可信 |
| `raw` | **78 字节原始寄存器 HEX** —— 公式可演进、历史可重放 |
| `seg` | ⚠️ **数据行 = 读取模式**（`"1"` 一帧 / `"3"` 三段）；**err 行 = 失败段**（`"F"` / `"S1"~"S3"`）。**两者语义不同，不能当同一字段用** |

> 🔴 **一处文档与代码不一致（已登记 D-07，未决）**：
> `02_docs/16` 写「固件只搬运原始值，不做任何工程量换算」，但**代码实际既换算又发 `raw`**
> （`频率÷10`、`电流÷100`、`温度−40`…）。当前状态 = **两者都给**。
> 待用户/导师定：要么固件只发 raw（换算全下沉到 PC），要么承认固件换算是正式设计并改文档。
> **有结论前两边都不要动**。

### 环 ⑥　UDP 怎么传，以及"发出去"到底算不算数

- 目标：**NVS 里配的 IP : 8888**（改 Web 配置页即生效，不必重烧）
- ESP32 本地端口：`12345`（仅发送，便于抓包定位）
- ⚠️ **只支持 2.4 GHz** WiFi

**核心陷阱：「发送成功」≠「送达」**

`endPacket()` 返回成功只代表**交给了 lwIP**，不代表出了网卡、更不代表对方收到。
所以判断送达必须靠**四计数器对账**，不能看返回值。

### 环 ⑦　接收端怎么落地

`06_tests/udp_collect.py` 在 Ubuntu 上跑：3 线程 / 2 队列 / SQLite WAL。

```
网络收包 ──► 原始包队列 ──► ① 原始包先落盘（udp_packet）  ← 任何解析失败都不丢证据
                    │
                    └──► ② 解析 → 业务表（device_epoch / stat_snapshot / event_log）
                                  │
                                  └──► ③ 报告全 SQL 重算（--report-only，可复现）
```

**六张表**：

| 表 | 装什么 |
| --- | --- |
| `udp_packet` | **原始包**（未解析，可重放） |
| `collect_run` | 一次运行（168h 长跑 = 一个 run） |
| `device_epoch` | 设备世代（重启会产生新 epoch） |
| `stat_snapshot` | 计数器快照（对账用） |
| `ingest_cursor` | 摄入游标（断点续跑） |
| `event_log` | 告警与异常事件 |

**三个成功率必须分开报**（只报一个，答辩必被问倒）：

| 口径 | 公式 | 度量 |
| --- | --- | --- |
| **M1 采集成功率** | `ΣΔpoll_ok / Σ(Δpoll_ok+Δpoll_err)` | 纯 RS-485 总线 |
| **M2 端到端完整率** | `收到数据行数 / (T_run / 周期)` | 业务视角 |
| **M3 传输送达率** | `Σ收到行 / ΣΔudp_tx` | 纯 UDP |

**对账恒等式**（这是"丢的包到底丢在哪"的答案）：

```
2·ΔR  =  R  +  未组装  +  发送失败  +  网络丢失
         │      │          │            │
         │      │          │            └─ ΔT − R     发出去了没到
         │      │          └────────────── ΔS − ΔT    begin/endPacket 失败
         │      └───────────────────────── 2ΔR − ΔS   WiFi 断 / 缓冲截断
         └──────────────────────────────── 实收去重行数
```

> 公式细节与四分类丢包判定见 `02_docs/22` §3。**M6 的 100% 是 M1，不是端到端**；
> 端到端数据行送达是 **98.0%**（1782/1801）。两个数不是一回事，对外说的时候要说清是哪个。

## 2. 出问题先查哪：故障定位树

**从现象倒推环节，别一上来就翻代码。**

| 现象 | 最可能是 | 怎么查 |
| --- | --- | --- |
| `poll_ok` 恒 0 / 一直 TIMEOUT | **接线**（`TXD`/`RXD` 接反，占 90%） | 看下面「第一嫌疑人」 |
| `RX=0` | 引脚坏 **或** 模块坏（**症状完全一样**） | 先烧 `rs485_probe` 体检，再换件 |
| 偶发半帧（`RX=8 期望 9`） | 字符间隔超时太紧 / 总线干扰 | 看 `02_docs/15` §4.1 |
| 有数据但 `quality` 恒 `PARTIAL` | `A/B/C_temp` 的 −40 被当成越界 | 确认 `QI_PHASE_TEMP_ABSENT=1` |
| 数据看着对、但偶发异常值 | **短帧掺假**（P0-1 类） | 查 `parseResponse` 帧长校验是否生效 |
| UDP 显示发了、接收端没有 | IP 配错 / 防火墙 / 不在同一网段 | 先用 `06_tests/udp_listen.py` 单测 |
| 采集率明显低于基线 | 超时参数 / 终端电阻 / 线长 | 对照 `22` §3 三口径，看是 M1 还是 M3 掉 |
| 长跑中途 `TypeError` 死掉 | 已知 B-2（时区 naive/aware）**已修** | 确认跑的是修复后的版本 |
| 报告是空的、快照没数据 | 已知 B-1（只读连接写库）**已修** | 同上 |

### 第一嫌疑人：`TXD` / `RXD` 接反

模块丝印写的是**模块自己**的方向：模块 `TXD` = 芯片 `RO`（收），模块 `RXD` = 芯片 `DI`（发）。

```text
✅  GPIO21 (ESP32 TX)  →  模块 RXD
    GPIO20 (ESP32 RX)  ←  模块 TXD
❌  GPIO21 → 模块 TXD   ⇒ 双向全断，但模块电源灯还是亮的
```

**M4 卡了整整 5 天就是这一条**，复盘见 `02_docs/14`。
