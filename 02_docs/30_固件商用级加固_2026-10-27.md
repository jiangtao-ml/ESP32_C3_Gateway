## 2. 逐条说明

### P0-1 时钟回退钳位（最高优先）

**问题**（`02_docs/24` §5.6 Y-4）：`CLOCK_STEP` 事件数必须 = 0，否则 168h 总体判 F。
触发链：WiFi 掉线 → 重连 → 重新 `configTzTime` → 本机无外部晶振、RTC 日漂 0.9~4.3 s
⇒ SNTP 把时钟**往回拨** ⇒ 1 Hz + 秒级 `ts` 必然撞上已用过的秒 ⇒ 接收端记 `CLOCK_STEP`。
**这是"跑完 7 天才发现"的类型**，所以必须在长跑前解决。

**改法（双保险，缺一不可）**：

1. **源头** `ntpApplyWithGuard()` 替代 2 处 `configTzTime`（原 `:498`、`:515`），置 `g_clkGuardPending`；
   `ntpClampTick()` 在 `ntpHasReply()` 成立后发现时钟比 `g_clkLastGood` 更早，且回退 ≤ `FW_CLK_BACK_HOLD_S`(3600 s)
   ⇒ `settimeofday()` 拉回旧值并计数。回退 > 3600 s 视为时钟真错，接受并重建基线（避免永久卡死）。
2. **兜底** `buildTimestampIso()` 保证 `ts` 会话内**严格递增**：只在 `cur < last` 时用 `last+1` 跳过。

**为什么两样都要**：
- 只做 ②：`ts` 单向超前，且**每次回拨都累积**，168h 内可能偏出十几秒，M10 时间准确性难看；
- 只做 ①：`configTzTime` 是**异步**的，回包到 `loop()` 拦截之间存在窗口，
  `stateTick()` 可能已经用倒退的 `ts` 发出去一行。

**为什么不用"ts 冻结等真实时间追上"**：接收端 `udp_collect.py:640` 对同秒撞车
**直接丢弃该行**（`StoreResult.SAME_SECOND` 不入库）。冻结会连续丢行，直接伤 M2 完整率。

**刻意做的两个细节**：
- `ntpClampTick()` 放在 `loop()` 里、**不受 `ntpTick()` 的 200 ms 节流限制** —— 把漏网窗口压到单次迭代；
- `ts` 护栏**同秒不 +1**，只在真倒退时 +1 —— 同秒是分辨率伪影（8h 实测 6 次，`INFO` 级），
  若同秒也 +1，一旦轮询周期略快于 1 s 就会每轮 +1 并持续累积超前。

**预期效果**：一次被拦下的回退，**预计损失 1 行**（同秒撞车），而不是原来的 D 行。
这是有意的取舍，不是缺陷 —— 见 §5.1。

### P0-2 心跳诚实化

`queue` / `dropped` 由 `0` 改为 **`null`**：本固件**没有发送队列**（UDP 走同步 `sendto`），
恒发 0 属于"看起来有能力、实际不存在"的假数据。改 `null` 后语义 = "本设备无此能力"，
与"队列当前为空（=0）"严格区分。

**接收端不受影响**（已逐行核对）：
- `udp_collect.py:120` `HB_REQUIRED = ("seq","dev","poll_ok","poll_err","udp_tx")` —— **不含这两个键**；
- `:845` 只检查"必须有"，不检查"不能多"；
- `:1060` 只对 `poll_ok`/`poll_err`/`udp_tx` 做 `isinstance(..., int)`，这三个原样保留。

**新增真实计数**：`tx_fail`（`udpSendLine()` 真失败，新增 `g_txFails`）/ `reconn`（复用 `g_reconnectCount`）/ `up`（开机秒数）。

### P0-3 看门狗 + 复位原因 + boot 计数

**问题**：批次 3 及之前，固件若在 `ST_WAIT_RX` 卡死，现场表现为"板子还在、灯还亮、但不再发包"，
**无法区分"死机"与"掉线"**，只能人工断电。2026-10-26 那次 21:41:38 复位，最终只能靠人工回忆
"换过 USB 供电线"才定性 —— 否则就是一条无从追查的玄学复位。

**改法**：
- `esp_task_wdt_init()`（**新签名**，见下）+ `esp_task_wdt_add(NULL)` + `loop()` 首行 `wdtFeed()`；
  30 s 超时 ⇒ `trigger_panic` ⇒ 重启并留下 `ESP_RST_TASK_WDT`。
- `RTC_NOINIT_ATTR` 存 `g_bootMagic` + `g_bootCount`，magic 校验后才自增（RTC 区上电是随机值）。
  `boot_count == 1` ⇒ RTC 区已重建 ⇒ **真断电**；`> 1` ⇒ 软复位/看门狗，**未断电**。
- `esp_reset_reason()` 映射为 15 个可读串。★ 对现场最有区分价值的三条：
  `BROWNOUT` / `PWR_GLITCH` = 供电不稳（充电宝跌落），**不是固件问题**；`USB` = 插拔/换 USB 线。

**⚠️ 必须知道的一个坑**：本机 IDF 5.5 的 `esp_task_wdt.h` **只有新签名**
`esp_task_wdt_init(const esp_task_wdt_config_t *)`，**旧的两参数写法 `esp_task_wdt_init(30, true)` 在该头文件里没有声明**
（已 `grep` 实证）。照 Codex 原文那样写会编译失败。

**为什么 `idle_core_mask = 0`**：不订阅 idle 任务。WiFi/SNTP 内部偶发长阻塞不该触发整机重启，
要盯的是 `loop()` 自己卡死。

**为什么 `wdtInit()` 放在 `setup()` 最末尾**：setup 期间（SoftAP / WebServer 初始化、`WiFi.begin` 首次拉起）
耗时不确定，提前开可能被误杀。

### P0-4 版本自报

`FW_VERSION` 接进心跳 `fw` 字段（此前只被 `web_config.h` 用在 `/status`）。
成本几乎为零，收益是接收端能按固件版本切分数据，长跑报告能立刻看出"哪一段换了固件"。

## 5. 已知限制与未做项（必须诚实读完再烧）

### 5.1 每次被拦的时钟回退，预计丢 1 行

`settimeofday()` 拉回旧值后，下一轮 `ts` 与已发出的最大 `ts` 大概率**落在同一秒**
⇒ 接收端记 `TS_SAME_SECOND`（`INFO`）并**丢弃该行**。

- 相比修复前会连续丢 D 行（且判 `CLOCK_STEP` ⇒ **Y-4 = F**），这是巨大改善；
- 若要把这 1 行也救回来，只能让同秒也 `+1`，但那会造成**超前累积**（§2 P0-1 已论证）。
- **裁决**：选"丢 1 行"，因为 M2 门禁是 97.5%，1 行可忽略；Y-4 是 0 容差。

### 5.2 `ntpClampTick()` 只覆盖"我们主动发起的对时"

`g_clkGuardPending` 只在 `ntpApplyWithGuard()` 后置位。若 lwip 的 SNTP 在周期到期后**自行**重同步，
不走这个入口 ⇒ ①不生效，只剩 ②（`ts` 护栏）兜底，效果是 `ts` `+1` 跳过、**轻微超前**。功能安全，但精度有损。

> ⚠️ **周期更正（2026-10-27，Codex 复核查出）**：此前记"默认 1 h"，实测 `sdkconfig:2295` 的
> `CONFIG_LWIP_SNTP_UPDATE_DELAY` = **10800 s = 3 小时**，不是 1 小时。
> ⇒ **"168h 前先跑 ≥3 h"的直接理由**：3 h 正好覆盖一个完整自同步周期，否则这个分支根本不会被触发到。

**口径裁定（B 类 F-9，2026-10-27 砚青，已拍板）：接受现状 + 靠 `ts` 护栏。**
- 理由：改 lwip SNTP 回调要侵入 core（升级 core 就冲突），收益只是精度；
  真正保命的是 `g_tsLastEmitted` 单调护栏，它**不受 `pending` 标志影响** ⇒ `CLOCK_STEP = 0` 仍成立。
- **验收口径**：`CLOCK_STEP = 0` 为**必须**；`clk_hold` **可能为 0 而仍合格**（lwip 自同步走 ② 路径）。
  ⚠️ 这一条修正了 `02_docs/24` Y-4 的原始表述——原文"`clk_hold > 0` 且 `CLOCK_STEP = 0` ⇒ 钳位生效"，
  在 lwip 自同步场景下会**误判为未验证**，须按本口径读。

### 5.3 `/status` 的 `queue`/`dropped` → **已改为 `null`**（B 类第 6 项，2026-10-27 已落地）

- **原状态**：`web_config.h` 发恒 `0`，与心跳的 `null` 不一致 ⇒ 接收端会读成"队列长度 0、从未丢包"，**属语义造假**。
- **已改**：`web_config.h:108` 格式串 `\"queue\":%u,\"dropped\":%u` → `\"queue\":null,\"dropped\":null`；
  调用处删掉 `(unsigned)0, (unsigned)0` 两个参数。
- **验证**：占位符 **20 个 ↔ 参数 20 个**（原 22/22，无失配）；代入典型值实测输出 **471 字节 / 25 键**，
  `json.loads` 通过，`queue = null`、`dropped = null`、`fw = 0.7.0-batch4`。
- ⚠️ **接收端若有按 int 解析这两个键的代码会抛 `TypeError`**（与心跳同口径）。
  `06_tests/udp_collect.py` 的 `HB_REQUIRED` 本就不含这两键、`:1060` 只判三项 int ⇒ **实测无影响**。

### 5.4 全部为"编译通过 + 静态自查"，**真机一行未验**

尤其是：
- 看门狗**是否真的会触发**、触发后 `reset` 是否真的报 `TASK_WDT`；
- `settimeofday()` 拉回后 `ts` 是否真如预期（丢 1 行而非 D 行）；
- `RTC_NOINIT` 的 `boot_count` 在"软复位 vs 拔电"下是否符合预期。

### 5.5 `FW_VERSION` → **已升 `"0.7.0-batch4"`**（B 类第 5 项，2026-10-27 已落地）

**采用"升版"**。理由很直接：不升版号，P0-4「版本自报」就等于没做——现场无法区分跑的是哪一版，
`fw` 字段也就失去意义。

⚠️ **版本断点的语义必须写清**：`0.7.0-batch4` 起 **电量刻度与 0.6.x 不兼容（差 1000 倍）**。
接收端 / 报表要按 `fw` 字段区分口径，**严禁把两版电量混算**（`(H*65536)/1000+L` vs `(H*65536+L)/1000`）。

### 5.6 `up` 字段在 49.7 天后回绕

`millis()/1000` 是 `uint32_t`。168 h（7 天）安全，**168 h 以上不适用**。

### 5.7 F-2：大幅回退（> 3600 s）被接受后 `g_tsLastEmitted` 不重置 —— **裁定：维持现状**

**场景**：NTP 把时钟往回拨超过 `FW_CLK_BACK_HOLD_S`（3600 s）⇒ 钳位**放行**，但 `g_tsLastEmitted`
仍是旧值 ⇒ 此后 `ts` 长期超前（旧未来值 `+1`）。

**裁定 ③（维持现状 + 把验收口径写死）**，理由三条：
1. 回退 > 3600 s 说明时钟已经离谱。此时 **`ts` 超前是更安全的失败模式**——它不倒退，
   就不会撞上已用过的秒 ⇒ **不产生 `CLOCK_STEP`**，而 Y-4 是 0 容差。
2. 若改成"接受并重置基线"，等于**主动制造一次 `CLOCK_STEP`**——为修精度去破 0 容差门禁，不划算。
3. 新增心跳字段（方案②）要把契约再改一次，收益只是"能看见"；而 `clk_back` 已经能看到回退秒数。

**验收口径**：168 h 报告中若出现 `clk_back > 3600`，必须同时检查该时段是否出现 `CLOCK_STEP`。
**`CLOCK_STEP = 0` 即合格**；`ts` 超前量应 ≈（回退量 − 已流逝时间），**不视为缺陷**。

### 5.8 `reconn` 语义：**"本次启动内累计重连尝试次数"** —— 已定，不再改

A 类修复后不再清零（原实现使它恒为 0）。⚠️ 它**不是"成功重连次数"**：
- 一次断网可能触发 N 次尝试（受 `WIFI_RECONNECT_INTERVAL_MS` 节流），`reconn` 记的是 N；
- 判"网络是否恢复过"请看 `up` 与心跳连续性，**不要用 `reconn` 反推**。

若将来需要"成功重连次数"，**另开计数器**（如 `reconn_ok`），**不得静默改本字段口径**。

## 6. 烧录与验证步骤（复核通过后执行）

**安全前置（硬红线）**：RS-485 侧若仍接在**带电配电箱**上，烧录前**必须断电 + 验电**。
本轮用户已确认"板子已拆下、485 线已拔"，该前置**当前已满足**。

1. 断电 → 拔 485 → 插 USB 到本机 → `Get-CimInstance Win32_PnPEntity` 确认 COM 口出现；
2. 编译确认（已在 §3 完成，产物 `1089225`/`49568`）；
3. `pio run -e esp32c3 -t upload`（`pio_verify` 工程，`upload_speed` 目前 921600，
   若握手失败降到 460800）；
4. 抓串口 115200，**必须看到**：
   - `[BOOT] reset_reason=POWERON boot_count=1（RTC 保留区已重建 => 真断电/首次上电）` ← 第一次拔电后烧录
   - `[WDT] 任务看门狗已启用：30000 ms ...`
5. 软复位一次（`GET /reset` 带 Basic Auth），**必须看到** `boot_count=2` 且 `reset_reason=SW`
   ⇒ 证明 RTC 保留区有效、boot 计数可区分软复位与断电；
6. 接回 485、恢复采集，跑一轮 ≥8 h，检查：
   - 心跳含 `fw`/`reset`/`boot`/`tx_fail`/`reconn`/`up`/`clk_hold`/`clk_back`，且 `queue`/`dropped` 为 `null`；
   - `event_log` 里 `CLOCK_STEP` 计数 = **0**；
   - `boot` 全程不变（若中途变大 ⇒ 说明发生过软复位/看门狗，**要查原因**）；
   - `clk_hold > 0` 且 `CLOCK_STEP = 0` ⇒ **钳位生效的决定性证据**。

### 回归失败时的回退

`config.h` 里把 `FW_WDT_ENABLE` / `FW_CLK_GUARD_ENABLE` / `FW_TS_MONOTONIC_ENABLE` 任一置 **0** 即可局部回退；
全部置 0 = 完全回到批次 3 行为（`.ino` 的新函数变空壳，不影响编译）。

### ⚠️ F-4 的偏差说明（必须留痕：原方案不可行）

我原建议的"**缩短 Web 超时**"在本环境**做不到**，实测依据：

- `WebServer.h:66-69` 的 `HTTP_MAX_{DATA,POST,SEND,CLOSE}_WAIT` 四个宏**前面没有 `#ifndef` 保护**
  （第 64 行的 `#endif` 属于上面的 `HTTP_RAW_BUFLEN`）⇒ **`-D` 覆盖无效**，
  源文件里的无条件 `#define` 会胜出；改库则污染工具链（换机器即丢、团队不可见）。
- 若走"工程 `lib/` 副本覆盖"路线：要维护 40 KB+ 库代码副本，**收益与成本不匹配**。

⇒ 退到 **提高 WDT 窗口到 60 s**，定量依据：

| 环节 | 最坏耗时 | 出处 |
|---|---|---|
| 等请求头 | 5 s | `HTTP_MAX_DATA_WAIT` |
| 写响应（8 KB，TCP 缓冲不足时多次 `write`） | 2 × 10 s = 20 s | `WIFI_CLIENT_MAX_WRITE_RETRY=10` × `SELECT_TIMEOUT=1s`（`NetworkClient.cpp:31-32`） |
| 等客户端关连接 | 5 s | `HTTP_MAX_CLOSE_WAIT` |
| **合计** | **≈ 30 s** | 正好压在 30 s 线上 ⇒ 会误杀 |

抬到 60 s 后留 2 倍余量。代价：真卡死检出延迟 30 s → 60 s，对 8h/168h soak 无实质影响
（重启即自愈，且 `reset=TASK_WDT` + `boot` +1 可观测）。

**残留风险（已接受的失败模式）**：若连续两个极端慢客户端各阻塞满额（> 60 s）仍会重启。
配置页属人工操作场景，非自动流量 ⇒ 可接受。**台架验证第 4 项必须实测一次慢客户端**（见 §6）。
