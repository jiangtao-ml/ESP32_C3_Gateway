## 2. 方法学更正（本轮最重要）

### 2.1 被推翻的做法

> 「把 USB 转 485 模块的 A/B 短接，从串口助手发 `abc`，接收区应回显」—— **错误方法。**

### 2.2 为什么不成立

- 两线 RS-485 是**半双工**，收发共用同一对差分线，靠驱动使能切换方向。
- 把 A、B 短接后，`V_AB = V_A − V_B ≡ 0V`。而 RS-485 接收器判据是 **`|V_AB| > 200mV`** —— 0V 正好落在判定窗口**正中间**。
- 标准 fail-safe 接收器（SP485 等）在**短路 / 端接**时输出落入 **Indeterminate（不确定区）**；带 full-fail-safe 的器件则**恒输出高（空闲态）** → UART 收不到任何字节。
- 结论：**健康模块在这个测试下同样「无回显」。该测试无判别力。**

### 2.3 权威依据

| 来源 | 原文要点 |
| --- | --- |
| Industrial Monitor Direct 知识库 | “Placing a jumper between the A and B terminals simply collapses the differential voltage to zero … **will not echo characters back to a host**. A true RS-485 two-wire loopback test requires **either two physical RS-485 ports** …” |
| Renesas 官方 KB（fail-safe 释义） | A/B 短路时 `Vdiff = 0V`，属**无效的 RS-485 状态**；带 fail-safe short 的器件保证此时 Rx 输出**恒为高（idle）** |
| MaxLinear XR33156 应用笔记 | 标准 fail-safe 接收器（SP485）在**短路与端接**两种情形下 `RO = INDETERMINATE` |
| US Converters 知识库 | 无 Echo-On 选项的 485 转换器，回环测试**必须用第二个 485 端口**，A 对 A、B 对 B |

### 2.4 正确做法

**两个 485 端口背靠背互测**（A↔A、B↔B、GND 共地）。

本项目天然具备这个条件：**`USB 转 485`（电脑侧）↔ `MAX13487`（ESP32 侧）本身就是一组合法互测**。也就是说 —— **M4 的测试本身才是那个有效测试**。

## 4. 故障定位逻辑

```
ESP32 GPIO21 ──▶ [DI]  MAX13487  [RO] ──▶ 分压 ──▶ GPIO20   ← 各自专有（本轮已排除为主因）
                          ↕
                     A(+) / B(-)                            ← 共用 ⭐ 嫌疑
                          ↕
            [A/B]   CH340 485 收发器（USB 转 485）            ← 共用 ⭐ 嫌疑
                          ↕
                        PC (COM7)                            ← 共用
                      三方 GND                               ← 共用 ⭐ 嫌疑
```

**双向全断 ⇒ 故障在共用段。** 按目前证据排序的嫌疑：

| 序 | 嫌疑 | 支持点 | 排除方法 |
| --- | --- | --- | --- |
| 1 | **MAX13487 未真正供电**（VCC 线未插到 5V 那一路） | 器件无电时既不驱动 A/B 也不输出 RO → **双向全断**，与现象完全吻合 | 测点 1 |
| 2 | **A/B 两根线没真正接通**（面包板孔位错行 / 端子未压紧） | 双向全断 | 测点 6 |
| 3 | **三方未共地** | 双向全断（短距台架下概率较低，但可能） | 测点 7 |
| 4 | USB 转 485 模块收发器坏 | 双向全断；但**已不能用 X1 作证据**，目前无任何实测支持 | 需两端口互测 |
| 5 | MAX13487 坏 / 被 EN 关断 | 双向全断 | 测点 3、5 |

> **注**：`GPIO20` 是否受损（R-13）本轮**仍未验证**。它只会影响回程，不会造成去程全断，故排在嫌疑之后，但不能忘。

### 8.2 最终判定

> **故障点 = MAX13487 模块本身或其供电回路。**

推理链（闭合）：

1. 两个 USB 转 485 模块在同一对节点上**能互通** ⇒ 该节点电气正常、布线正确、两模块完好。
2. MAX13487 的 `A`/`B` 脚**就在同一对节点上**（同一行、同一半边）。
3. 但 ESP32 每秒发出的 `01 03 00 00 00 02 C4 0B` **两个监听口都收不到**。
4. ⇒ **MAX13487 没有把任何差分信号驱动到 A/B 上。**
5. ⇒ `GPIO21 → TXD` 的正常工作（第 2 层已验）无法转化为总线信号，只能是收发器侧：**未插实 / 未供电 / 器件失效**。

**此前被提出但已排除的假设**：A/B 接反（若接反会收到**反相乱码**，而非"零字节"）、EN 未接高（用户确认 `EN`→5V）、A/B 落在逻辑侧、管脚顺序读反（用户确认按字母接）。

### 8.3 免仪表手段的能力边界（重要结论）

| 想验证的事 | 免仪表能否验证 | 说明 |
| --- | --- | --- |
| 模块收发是否正常 | ✅ 能 | 双端口背靠背互测 |
| 节点/布线是否连通 | ✅ 能 | 用已验证模块对在同一节点上互测 |
| 器件是否在驱动总线 | ✅ 能 | 双口只读监听 |

## 9. 🎯 根因与 M4 通过（2026-10-04 21:30–21:33）

### 9.1 根因：模块 `TXD`/`RXD` 为**交叉**约定

> **正确接法：`GPIO21`（ESP32 TX）→ 模块 `RXD`；`GPIO20`（ESP32 RX）← 模块 `TXD`。**

模块丝印写的是**模块自身的收发方向**：

| 模块丝印 | 实为芯片脚 | 方向 |
| --- | --- | --- |
| `TXD` | `RO` | 接收**输出** → 应接 ESP32 的 **RX** |
| `RXD` | `DI` | 发送**输入** → 应接 ESP32 的 **TX** |

**此前按"同名对接"（`GPIO21`→模块 `TXD`）接线，后果：**

| 现象 | 机理 |
| --- | --- |
| 模块 `DI` 从未被驱动 | `GPIO21` 接在芯片 `RO`（输出）上 → **两个输出对撞**；芯片真正的发送入口悬空 ⇒ **驱动器不输出任何差分** |
| `GPIO20` 收不到任何东西 | 挂在 `DI`（高阻输入）上 |
| **总线双向全死** | 上述两条合起来 |
| 模块电源灯**仍亮** | 只是没被驱动，不是没电 ⇒ **极易误判为"模块坏 / 未供电"** |

这也解释了为什么**两只 MAX13487 表现完全一致** —— 不是模块坏，是接线口径错。

### 9.2 验证过程（对调两根线后）

| 观测点 | 结果 |
| --- | --- |

### 9.6 方法论教训（写入长期记忆）

1. **同一现象由两个独立样件重现时，优先怀疑"接线/口径/方法"，而不是"两个都坏"。** 本项目两次踩中（USB 转 485 模块、MAX13487 模块）。
2. **"验线通"与"验落点"必须分开设计。** 本文 §8.1 的测试 T 只证明了导线连通，无法证明"那一行就是模块引脚所在行"。
3. **丝印的读写要留证据。** 本文 §9.1 的结论来自对模块照片的放大逐字核对；同类错误（3 脚排顺序 `B/A/GND` 被旧文档记成 `GND/A/B`）已发生两次。
