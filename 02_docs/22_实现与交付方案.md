## 2. 168 小时连续采集接收程序

### 2.1 为什么现有工具不能直接用

| 工具 | 能做到 | 缺什么 |
| --- | --- | --- |
| `udp_listen.py` | 收包、打印、按源 IP 计数 | 无 JSON 解析、无落盘、无 seq 连续性、无统计 |
| `db_proto.py` | 字典驱动解析、四层校验、幂等入库 SQLite | **只认旧文本格式，不认 JSON 上行** |
| `m5_parse.py` | 39 字段表驱动换算 | 面向 HEX 文本，非 JSON |
| `.workbuddy/tmp/*.py` | 一次性解析 M6 数据 | 临时脚本、未入库、无长跑能力 |

结论：**新建 `06_tests/udp_collect.py`，复用 `db_proto.py` 的解析与入库函数，不重写。**

### 2.2 进程模型：3 线程 + 2 队列

```
┌──────────────┐   q_pkt (maxsize=20000)   ┌──────────────┐
│ T1 收包线程   │ ───────────────────────► │ T2 落库线程   │ ── SQLite (WAL)
│ recvfrom     │                          │ 批量 UPSERT  │
└──────┬───────┘                          └──────┬───────┘
       │ 每包只做：记时 + 解 JSON + 分类            │
       │ 严禁：SQL / print / 文件 I/O              │
       ▼                                          ▼
   内存计数器  ◄──────────────  q_stat (满则丢弃)
                                    │
                            ┌───────▼────────┐
                            │ T3 统计线程     │ 10s 控制台 / 60s 快照
                            │ 只读连接        │
                            └────────────────┘
```

**为什么必须解耦**：一次 Windows Defender 全盘扫描或 WAL checkpoint 就能让 `commit` 阻塞数十秒。若收包与写库同线程，这几十秒内新到的包只能堆在内核缓冲区，**溢出即静默丢包**——而且事后完全看不出来，会被误判成"WiFi 不好"。

| 线程 | 允许 | 严禁 |
| --- | --- | --- |
| T1 收包 | `recvfrom`、`json.loads`、计数器累加、`q_pkt.put_nowait` | 任何 SQL、任何 `print`（控制台写阻塞会传染）、任何文件写 |
| T2 落库 | 单写连接、批量事务、`q_stat.put_nowait` | 网络 I/O |
| T3 统计 | 只读连接（`mode=ro`）、写快照文件 | 写主库 |

**背压策略**：`q_pkt` 满时**不阻塞 T1**，丢弃并累加 `q_drop`，同时记 `QUEUE_FULL` 告警。这是**唯一允许的、可观测的**丢弃点——与内核缓冲静默丢包必须能区分开。

### 2.3 收包层参数（逐条给值）

```python
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 1024 * 1024)   # 必须在 bind 前
if hasattr(socket, "SO_EXCLUSIVEADDRUSE"):
    s.setsockopt(socket.SOL_SOCKET, socket.SO_EXCLUSIVEADDRUSE, 1)
s.bind(("0.0.0.0", 8888))
s.settimeout(0.5)
```

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| `SO_RCVBUF` | **1 MiB** | 典型包 1.1 KB ⇒ 约 950 包 ≈ **475 s** 缓冲。Windows 默认 64 KB 只够 29 s |
| 地址复用 | **`SO_EXCLUSIVEADDRUSE`** | Windows 上 `SO_REUSEADDR` 允许第二个进程**静默抢包**（NetAssist 忘了关 = 数据被分走且无报错） |
| 超时 | 0.5 s | 用于响应停止标志；超时不是错误 |
| 单包上限 | 4096 B | 明文最坏 1106 B、密文 1135 B；超出记 `oversize`，不崩溃 |

**异常自恢复**（循环内全部 `continue`，绝不退出）：

| 异常 | 触发场景 | 处理 |
| --- | --- | --- |
| `socket.timeout` | 正常空闲 | 继续 |
| `ConnectionResetError` (10054) | Windows UDP 端口不可达回传 | 继续 + 计数 |
| `OSError` (10040/10022) | 巨型包 / 缓冲不足 | 继续 + 计数 |
| `JSONDecodeError` | 半包、乱码、非本协议流量 | 入 `udp_packet(parse_status='bad_json')`，不污染统计 |
| 其他 | — | 写 traceback 到 `event_log`；连续 100 次才告警 |

**三类行判别**（按字段，不按长度）：

```python
t = obj.get("type")
ptype = "data" if t is None else ("hb" if t == "hb" else ("err" if t == "err" else "unknown"))
```

必填字段校验：`data` 需 `seq,dev,ts,raw,quality`；`hb` 需 `seq,dev,poll_ok,poll_err,udp_tx`；`err` 需 `seq,dev,type,seg,reason`。缺任一 → `parse_status='bad_field'`，保留原文，不参与统计。

### 2.4 解析层：复用 `db_proto.py`

```python
# JSON raw → 39 寄存器 → 复用既有入库
regs_hex = obj["raw"].split()          # 78 个 "AA"
assert len(regs_hex) == 78
db_proto.store(conn, {"ts": ts_db, "hexs": regs_hex, "seg": obj["seg"]},
               device_id, slave_addr=1, src="udp", fields=fields,
               seq=obj["seq"], known_missing={"A_temp","B_temp","C_temp"})
```

| JSON 字段 | 落点 | 规则 |
| --- | --- | --- |
| `ts` | `collect_time` | `T` → 空格；`ts_ok=false` 时用 epoch 锚点换算（`boot_wall + BOOT秒`），并置 `src="udp_boot"` |
| `quality` | `quality` | 直通；**接收端复核**：`quality=OK` 但 `invalid` 非空 ⇒ 记 `quality_conflict`（固件口径 bug 的证据） |
| `invalid` | `invalid_fields` | 逗号串直通，另做字段级频次统计 |
| `seg` | `seg_ok` | `"1"`→`"1"`；`"3"`→`"111"`（沿用 `db_proto.store` 既有约定） |
| `raw` | `raw_hex` | 原样保留 233 字符 |
| `dev`/`mac`/`ip` | 新表 `udp_packet` | `meter_record` 不加列；设备身份由 `device_id` 承载 |

**对 `db_proto.py` 的最小扩展**（向后兼容，不改既有行为）：

1. `store_json(conn, obj, device_id, fields, epoch_id)` —— 封装上面的映射，返回 `("new"|"dup", quality)`。
2. `build_ddl_v2(fields)` —— 给 `meter_record` 增 `epoch_id`，并建 `UNIQUE(device_id, epoch_id, seq)`。

**为什么要加 `epoch_id`**：现主键是 `(device_id, collect_time)`，秒级精度 + 1Hz 周期下，**NTP 回跳 1 秒就会让两条不同轮次撞主键并被 `ON CONFLICT DO UPDATE` 静默覆盖**——一行数据凭空消失且无任何报错。`(device_id, epoch_id, seq)` 才是真正的幂等键。

### 2.5 持久化：6 张表

```sql
-- ① 原始流水（唯一不可再生资源，只增不改）
CREATE TABLE udp_packet (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    recv_time TEXT NOT NULL,          -- 接收墙钟（含毫秒）
    recv_mono REAL NOT NULL,          -- time.perf_counter()，抗墙钟跳变，用于抖动
    src_ip TEXT, src_port INTEGER,
    dev TEXT, device_id TEXT, seq INTEGER,
    ptype TEXT NOT NULL,              -- data|hb|err|unknown|bad
    payload_len INTEGER, payload BLOB,  -- hb 不存 payload（只存下列字段）
    enc INTEGER DEFAULT 0,
    parse_status TEXT,                -- ok|bad_json|bad_field|decrypt_fail|oversize
    epoch_id INTEGER,
    poll_ok INTEGER, poll_err INTEGER, udp_tx INTEGER,
    rssi INTEGER, free_heap INTEGER, ts_ok INTEGER
);
CREATE INDEX idx_pkt_dev_seq ON udp_packet(device_id, seq);
CREATE INDEX idx_pkt_recv    ON udp_packet(recv_mono);
CREATE INDEX idx_pkt_type    ON udp_packet(ptype, recv_mono);

-- ② 采集会话（一次长跑一行；重启不新建）
CREATE TABLE collect_run (
    run_id INTEGER PRIMARY KEY AUTOINCREMENT,
    started_at TEXT, planned_end TEXT, ended_at TEXT,
    target_hours REAL DEFAULT 168, period_ms INTEGER DEFAULT 1000,
    bin_sha256 TEXT, note TEXT
);

-- ③ 设备启动世代（seq 回退时切分；所有统计的分组单位）
CREATE TABLE device_epoch (
    epoch_id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id TEXT, seq_first INTEGER, seq_last INTEGER,
    first_recv TEXT, last_recv TEXT,
    poll_ok_at_start INTEGER,
    detect TEXT                       -- cold_start|seq_rollback|poll_reset|manual
);

-- ④ 分钟级快照（趋势/告警，不参与最终口径）
CREATE TABLE stat_snapshot (
    ts TEXT PRIMARY KEY, run_id INTEGER, device_id TEXT,
    pkt_rx INTEGER, data_rx INTEGER, hb_rx INTEGER, err_rx INTEGER,
    seq_last INTEGER, lost_lines INTEGER, full_lost_rounds INTEGER,
    data_lost INTEGER, dup INTEGER, q_depth INTEGER, q_drop INTEGER,
    poll_ok_last INTEGER, poll_err_last INTEGER, udp_tx_last INTEGER,
    rssi INTEGER, free_heap INTEGER, db_mb REAL, disk_free_mb REAL
);

-- ⑤ 断点游标
CREATE TABLE ingest_cursor (k TEXT PRIMARY KEY, v TEXT);
-- k = last_packet_id | run_id | last_report_at

-- ⑥ 异常事件（报告"事件表"直接来源于此）
CREATE TABLE event_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts TEXT, kind TEXT, severity TEXT, detail TEXT
);
```

> `udp_packet` **不建 `UNIQUE(device_id, seq)`**——重复包必须留下来当证据（重包率是实测指标），去重放在分析期。

**SQLite 参数**：

```python
PRAGMA journal_mode = WAL            -- 读写不互斥
PRAGMA synchronous  = NORMAL         -- 崩溃不损坏；最多丢最后一个事务（该事务数据仍在内存队列）
PRAGMA wal_autocheckpoint = 2000     -- 约 8 MB 一次
PRAGMA journal_size_limit = 67108864 -- WAL 上限 64 MB
PRAGMA busy_timeout = 10000
PRAGMA temp_store = MEMORY
```

**提交策略**：每 **2 s** 或累计 **500 行** 或队列空闲 **>1 s**，三者先到即 commit。168h ≈ 30 万次提交，实测 CPU 占用 `[待实测]`。
**每 6 小时**做一次 `wal_checkpoint(TRUNCATE)`，防止 168h 后留下几百 MB 的 `-wal`。

**写序（不可颠倒）**：先写 `udp_packet` → commit → 再写 `meter_record`。
理由：原始包不可再生，解析结果可再生。解析崩了、字典换版了、口径改了，都能从 `udp_packet` 全量重放。

**存储预算**：168h @1Hz = 604,800 轮 ≈ **121 万包**。心跳不存 payload（只存字段）、数据/err 存全文 ⇒ **约 1.0–1.5 GB**。**预留 ≥10 GB**，并每 60s 检查一次剩余空间。

### 2.6 断点续收与可复算

| 需求 | 做法 |
| --- | --- |
| 进程重启不清零 | 统计**不保存运行时累加值**；控制台数字只是内存快照，报告数字 **100% 由 SQL 从 `udp_packet` 重算** |
| 168h 倒计时跨重启 | `collect_run.started_at` 一经写入不再改动 |
| 断电后补解析 | 启动时读 `ingest_cursor.last_packet_id`，对 `parse_status='ok'` 但 `meter_record` 缺行的记录补入库（`--repair`） |
| 验收复算 | `--report-only` 必须与运行时报告**逐字节一致**（排序键固定 `id`，浮点统一 `%.4f`） |

> "重启后接着统计"不是靠把数字存盘，而是靠**数字本来就能从原始流水重算**。这一条同时解决了断点续收、断电恢复、事后复算三个问题。

### 2.7 可观测性

控制台每 10 s 一行（单行 ≤160 字符）：

```
[09:12:30] up 12:00:00 | rx 43210 (d 21580/h 21600/e 30) | 送达 99.93% | 整轮丢 12/21600 (0.06%)
           | 仅数据丢 3 | dup 0 | seq 43210 | q 0/20000 | db 128MB | disk 42GB | heap 182k | M1 99.87%
```

事件类型（同时写 `event_log` 与滚动日志）：

| kind | 触发 | 级别 |
| --- | --- | --- |
| `BIND_FAIL` | 8888 被占用 | FATAL（退出） |
| `IP_CHANGE` | `src_ip` 与上次不同 | WARN |
| `REBOOT` | seq 回退 + 计数器回退 | WARN |
| `GAP` | 连续 >30 s 无任何包 | ALERT |
| `SILENT_DEATH` | 有包但 seq 停滞 >60 s（WiFi 断） | ALERT |
| `DISK_LOW` | 剩余 <10 GB | ALERT |
| `DECRYPT_FAIL` | 单包解密失败；连续 >10 升 ALERT | WARN |
| `QUEUE_FULL` | `q_pkt` 满 | ALERT |
| `CLOCK_STEP` | `ts` 跳变但到达间隔正常（NTP 步进） | WARN |

日志按 50 MB 滚动、保留 10 个；日志里**不写完整 payload**（会撑爆），只写 `dev/seq/type/len`，原文在 DB。

### 2.8 168h 自动收尾与报告

满 168h：置 `stopping` → 关 socket → 排空 `q_pkt` → 最后一次 commit → `wal_checkpoint(TRUNCATE)` → 生成报告 → 写 `ended_at` → 退出码 0。

**报告结构**（可直接贴进验收文档）：

1. 封面表：设备 / MAC / 固件版本 + bin SHA256 / 起止时间 / 实际时长 / PC 主机名与 IP / DB 路径与大小
2. **核心指标表**（§3.6 的 M1–M18，填实值 + 阈值 + 通过与否）
3. **对账表**：`Δseq / Δudp_tx / ΣΔpoll_ok / ΣΔpoll_err / rx` 五个总量 + 恒等式校验
4. 分时段趋势（每小时一行）
5. 异常事件表（来自 `event_log`）
6. 数据质量分布 + 字段级 NULL 率（`A/B/C_temp` 预期 100% NULL）
7. 加密对比章节（若启用）

### 2.9 第二章验收标准

| # | 判据 | 阈值 |
| --- | --- | --- |
| 1 | 连续运行时长 | ≥168 h，无进程退出 |
| 2 | 进程自身崩溃 | 0 次（Ctrl+C 除外） |
| 3 | 队列溢出丢弃 | 0 包（`q_drop = 0`） |
| 4 | 断电恢复 | 强制断电 3 次，每次重启后库不损坏、`--report-only` 数字与断电前一致 |
| 5 | 复算一致性 | 运行时报告 == `--report-only` 报告（逐字节） |
| 6 | 磁盘 | 全程剩余 ≥10 GB，无 `DISK_LOW` |
| 7 | 单包解析 | `bad_json + bad_field` 占比 ≤0.01% |
| 8 | 30 分钟冒烟 | 先跑 30 min，`poll` 计数与接收行数对账闭合 |

## 3. 数据收集率、丢包率、重包率

### 3.1 必须先承认：这里有三个不同的"成功率"

只报一个数一定会在答辩时被问倒。三个都要报，并说明关系。

| 口径 | 公式 | 度量什么 | 会漏掉什么 |
| --- | --- | --- | --- |
| **M1 采集成功率** | `ΣΔpoll_ok / Σ(Δpoll_ok+Δpoll_err)` | **纯 RS-485 总线**：轮次在 MCU 里跑没跑成功 | 全部网络损失、WiFi 断线期间的轮次 |
| **M2 端到端完整率** | `收到数据行数 / (T_run / 周期)` | **业务视角**：我到底拿到多少条电表数据 | 无法区分"采集失败"与"传输丢失" |
| **M3 传输送达率** | `Σ收到行 / ΣΔudp_tx` | **纯 UDP**：设备交出去的行有多少到了 | WiFi 断线期间未发送的行（分子分母同时剔除） |

**三者关系（写进报告，否则数字对不上会被当成算错）**：

```
M2 ≈ A × M1 × D
  A = 链路可用率 = ΣΔR / (T_run/周期)
  D = 数据行送达率
```

- 老师基线 **96.9%** 是 **M1**（纯总线），与 UDP 一点关系都没有。
- 我们 M6 的 100% 也是 **M1**（900s，975/975）。
- **M2 一定 ≤ M1**，差值就是网络与链路不可用的代价。

### 3.2 四计数器区间对账（本方案的数学核心）

**可行性依据（已逐行核对源码）**：

| 计数器 | 语义 | 递增时机 | 位置 |
| --- | --- | --- | --- |
| `poll_ok` / `poll_err` | 采集轮数 | 每轮进入 `sendUdpPayload` **开头**，**在 WiFi 判断之前** | `.ino` L791-792 |
| `seq` | 已组装行数 | 每个 `build*Json` 内 `++g_seq`，**在 WiFi 判断之后** | L692 / L736 / L759 |
| `udp_tx` | 交给 lwIP 的行数 | `beginPacket` 与 `endPacket` 都返回 1 | L772-783 |

**关键事实**：WiFi 未连接时 `sendUdpPayload` 在 L798 提前 `return`——**`seq` 不增、`udp_tx` 不增，但 `poll_ok/poll_err` 照增**。这让"链路不可用轮数"从猜测变成可计算的差值。

对相邻两个心跳（同一 epoch）：

```
ΔR = Δpoll_ok + Δpoll_err     真实执行轮数
ΔS = seq 增量                 真实组装行数
ΔT = udp_tx 增量              交给 lwIP 的行数
R  = 区间内实际收到并去重的行数

闭合恒等式（逐区间成立，全 run 求和仍成立）：

    2·ΔR = R + 未组装 + 发送失败 + 网络丢失

    未组装   = 2ΔR − ΔS        （WiFi 断 / 缓冲截断）
    发送失败 = ΔS − ΔT          （beginPacket/endPacket 失败）
    网络丢失 = ΔT − R           （发出去了但没到）
```

> ⚠️ **一处必须修正的推导**：初稿曾把 `k = ΔS/ΔR` 判为"必须等于 2，否则该区间作废"。**这是错的**——WiFi 断开时 `ΔS` 本就小于 `2ΔR`，按等式判会把**最该统计的区间全部丢弃**。
> 正确做法：**把 2 当作设计常量**（每轮最多 2 行），只校验 **`ΔS ≤ 2·ΔR`**；`ΔS > 2ΔR` 才是协议异常（宏被改动或 seq 语义变了），该区间标 `EPOCH_ANOMALY` 并排除。

### 3.3 丢包必须四分类

正常轮 seq 为（奇数=心跳，偶数=数据）；失败轮为（奇数=心跳，偶数=err）。据此：

| 类别 | 判定 | 含义 |
| --- | --- | --- |
| **整轮丢失** | 奇数 seq 缺 且 配对偶数 seq 也缺 | 连心跳都没到 ⇒ 链路级丢失 |
| **仅数据行丢失** | 偶数 seq 缺，但同轮 `Δpoll_ok=1` | 心跳到、采集成功、数据行没到 ⇒ **包长敏感**（数据行 892 B vs 心跳 213 B） |
| **仅心跳丢失** | 奇数 seq 缺，偶数到 | 少见，通常伴随乱序 |
| **err 行丢失** | 偶数 seq 缺，但同轮 `Δpoll_err=1` | 失败可见性下降 |

判据优先级：**先看 `Δpoll_ok/Δpoll_err`（累计计数，可靠），再看 seq 缺哪一条**。两者矛盾时以计数器为准并记异常。

> "仅数据行丢失"是本次长跑最值得看的指标：它区分"位错主导"（丢失率 ∝ 包长）与"尾部丢帧主导"（最后发出的大包优先丢）。这直接决定加密对比时"+29 B 包长"会不会有影响。

### 3.4 重包率

```
重包率 = 1 − distinct(device_id, epoch_id, seq) / 收到且 parse_status='ok' 的包数
```

同时报三个衍生物：

| 指标 | 公式 | 用途 |
| --- | --- | --- |
| DB 幂等冲突率 | 命中 `(device_id, epoch_id, seq)` 已存在 / 入库尝试 | 与重包率应同步 |
| 时段撞车率 | 命中 `(device_id, collect_time)` 已存在 / 入库尝试 | **>0 即证明发生过时钟回跳**，是数据被静默覆盖的直接证据 |
| 期望值 | 0 | UDP 单播不重复是理论；必须实测验证 |

> ⚠️ **键里必须带 `epoch_id`**。设备重启后 `seq` 从 1 重来，若用 `(dev, seq)` 去重，**每次重启都会被算成上千个"重复包"**，重包率瞬间爆表。

### 3.5 周期抖动

`ts` 只有秒级（Q-12 裁定不加毫秒），**用它根本算不出 ±50ms**（21 §9 D-08）。改用接收侧单调时钟：

```python
d = perf_counter[i] - perf_counter[i-1]
jitter = d - 1.000
```

**样本筛选（不做则数字无意义）**：

| 剔除 | 理由 |
| --- | --- |
| 跨 epoch | 间隔 = 停机时长 |
| 跨 `CLOCK_STEP` | NTP 步进改变发包节奏 |
| `d > 5 s` | 属"可用性"不属"抖动" |
| **同一轮的两个包**（hb + data 间隔≈0） | 会污染分布 ⇒ **只取同类型相邻包**（心跳序列最佳，因每轮必发） |

**必须写进报告的局限**：测到的是「设备抖动 + WiFi 空口排队 + PC 内核调度 + 线程唤醒」的**合成上界**，**不能**分离出 MCU 内部 `loop()` 抖动。想做设备侧抖动，需固件新增 `loop_ms` 字段（21 §11 G-07，本方案不改）。

## 4. 明文传输 vs 加密传输对比

### 4.1 先明确加密保护什么（否则会写出过度承诺）

| 威胁 | 明文现状 | AES-128-GCM 后 |
| --- | --- | --- |
| 同网段被动窃听（用电数据 = 用电行为画像） | **完全暴露** | 保护 |
| 伪造 UDP 包注入假数据 | 可任意伪造 | 保护（Tag 验证失败即丢弃） |
| 重放旧包 | 可重放 | **部分**（靠 `seq` 单调性由上层判断，GCM 本身不防） |
| 密钥泄露 | — | **不防** |
| 拒绝服务 / 泛洪 | 不防 | **不防** |
| 配置面攻击（AP 常开、`/status` 免鉴权） | 不防 | **与本项无关**（属 21 §11 G-05/G-06） |

**定性声明（必须原文进报告）**：本加密为**对比实验能力**，采用预共享密钥、无密钥协商、无前向保密、无密钥轮换。**不构成生产级安全方案。**

### 4.2 帧格式

```
偏移   长度    字段
0      1      版本字节：bit7=1 表示加密帧，低 4 位=协议版本(2)
1      12     nonce
13     n      密文（n = 明文 JSON 字节长度，等长）
13+n   16     GCM Tag
──────────────────────────────
总计   n + 29
```

- **AAD** = 版本字节本身（1 B），防版本降级，接收端可独立复现。
- **无需长度字段**：UDP 保留报文边界，`len(payload) − 29` 即明文长度。
- **明文/密文判别**：明文 JSON 首字节恒为 `0x7B`（`{`），密文首字节恒 ≥0x80，**不可能冲突**。
- **MTU 硬约束**：明文最坏 1106 B → 密文 **1135 B**；`1472 − 1135 = 337 B` 余量 ⇒ **不触发 IP 分片**。
  > 这条必须写进报告：一旦分片，任一分片丢失即整包丢失，会凭空把丢包率放大数倍，整个对比结论作废。
- **缓冲**：新增 `QI_ENC_BUF_MAX 1280`，**另开静态缓冲**，不复用 `g_payload`（mbedTLS 输入输出重叠是未定义行为）。

### 4.3 Nonce 构造（否掉一个常见错解）

**错解**：`4B 设备ID + 4B seq + 4B 毫秒计数`。
**为什么不成立**：`seq` 与 `millis()` **在重启时同时归零**。跨两次开机的碰撞条件是"第 N 条报文的 seq 相同且发送毫秒相同"——断电重启后 WiFi 连接耗时高度一致，落在同一毫秒的概率远高于 1/2³²。**毫秒字段对跨重启防重没有任何贡献，是"看起来严谨、实际不设防"。**

**推荐构造（12 B）**：

```
nonce[0..3]  = dev_tag  = CRC32(MAC 字符串) 低 32 位     （设备维度，启动算一次）
nonce[4..7]  = boot_id  = NVS 持久化的开机序号，每次启动读→+1→立即 commit
nonce[8..11] = seq      = g_seq（本行组装后的值）
```

**唯一性三段论证**：

1. **同一 boot 内**：`seq` 每发一行严格 +1 ⇒ 任意两条 `nonce` 不同。
2. **跨 boot**：`boot_id` 持久化且严格单调递增 ⇒ `nonce[4..7]` 不同。
3. **回绕**：`seq` 为 uint32，2 行/s 下需约 **68 年**才回绕；`boot_id` 每次重启 +1，168h 内为个位数。

**失效兜底（fail-closed）**：若启动时 `boot_id` 读回校验失败（Flash 损毁/分区满），置 `enc_ready=false` 并**整体禁用加密、退回明文**——绝不允许用可能重复的 nonce 硬跑。

### 4.6 对比实验设计（控制变量）

**核心原则：两个实验臂跑同一个二进制。**

### 4.8 统计功效（必须写，防过度解读）

2 h = 7200 轮 = 14400 行。若真实丢失率 p=0.5%，二项标准差 ≈ `√(0.005×0.995/14400) ≈ 0.059%`，**95% CI ≈ ±0.12%**。

⇒ **两臂差异小于约 0.2% 时，8 h 实验根本区分不了**，只能报「**未见显著差异**」，**不能**报「加密不影响丢包」。

要做到等效性结论：四段合并后比较（n≈28800/臂，CI ≈ ±0.08%），或延长到 24 h。

| 真正风险 | **内存**：`g_payload`(1200) + 加密输出(1280) 常驻 ≈ 2.5 KB，占 `free_heap` 约 1.4% | 用 168h 的 `free_heap` 斜率验证无泄漏 |

### 4.10 兼容性与默认关闭（决策项，须挂 §8）

**加密默认关闭（`enc_on=0`）。** 理由：

1. 老师参考实现是**明文 UDP**，默认加密会直接打断与老师接收端的联调（违反 21 §7.3 生态兼容约束）。
2. M7 验收需要「老师能收」+「我们能解」两条同时成立。
3. 加密定位是**可选能力 + 对比实验**，不是交付形态。

### 4.11 第四章验收标准

| # | 判据 | 阈值 |
| --- | --- | --- |
| 1 | 默认模式 | 出厂 / `--init` 后 `enc_on=0`，老师接收端可直接收 |
| 2 | 解密正确性 | 8h 实验中 `decrypt_fail = 0` |
| 3 | 不触发分片 | Wireshark 中密文帧无 `More fragments` |
| 4 | 包长 | 密文帧 = 明文帧 + 29 B（逐包校验） |
| 5 | nonce 唯一 | 168h（或 8h × 强制重启 50 次）内无重复 nonce |
| 6 | fail-closed | 人为破坏 `boot_id`，确认加密整体禁用而非带病运行 |
| 7 | 结论合规 | 报告含 CI 与"未见显著差异"的措辞约束 |

### 5.2 7 天连续供电（现有文档完全没提，且是**最容易翻车的一条**）

现状是「充电宝 + 拔 USB」——**充电宝撑不过一天**，168h 必然在 12–24 小时内断电。

| 方案 | 可行性 | 说明 |
| --- | --- | --- |
| 5V/2A 适配器（推荐） | 高 | 输出隔离，USB 保持空置 ⇒ 同时消除地环路风险；需确认纹波不影响 485 |
| USB 充电头 + 数据线 | 中 | 需剪断数据线或确认无主机；否则又形成地环路 |
| 大容量 UPS | 中 | 成本高，仅作掉电缓冲 |
| 太阳能 / 电池组 | 低 | 不现实 |

**验收标准**：连续供电 ≥168h 不掉电；掉电 3 次均能自恢复（并入 §6 判据 13）。

### 5.4 设备侧看门狗（PC 代理）

固件**无看门狗、无自动重启**（21 §11 G-01）。用 PC 侧代理兜：

```
每 60 s: GET http://192.168.1.200/status（Basic Auth）
  连续 5 次失败（≈5 min） → GET /reset
  再连续 5 次失败        → 告警，人工断电
```

**验收标准**：人为让设备死机（如持续占用堆），确认 ≤6 min 内自动恢复，且 `event_log` 有记录。

### 5.5 异常处理矩阵

| 层 | 异常 | 检测 | 自动动作 | 是否计入采集率 |
| --- | --- | --- | --- | --- |
| 设备 | 采集超时/CRC/帧长错 | `reason` | 记 err 行，工具位不变 | **计入**（M1 分母） |
| 设备 | 死机 | 心跳中断 >3 min | PC 看门狗 `/reset` | 计入 M14，不计入 M3 |
| 链路 | WiFi 断 | 心跳中断 + `src_ip` 消失 | 固件自恢复（≤60s）；接收端记 `GAP` | **不计入 M3**，计入 M14 |
| 链路 | IP 漂移 | `src_ip` 变化 | 告警 + 提示改 NVS | 计入 M14 |
| 接收 | 写库阻塞 | `q_depth` 高水位 | 扩大缓冲 / 延长提交 | 计入 `q_drop` |
| 接收 | 端口被抢 | 绑定失败 / 包数半量 | 启动即退出 | 该时段记为丢失 |
| 接收 | 磁盘不足 | `disk_free < 10GB` | 告警 + 停止落 payload | 计入事件 |
| 环境 | 断电 | 进程退出 | 重启后 `--repair` 补解析 | 计入中断时长 |

**分级**：`INFO` / `WARN` / `ALERT` / `FATAL`。**ALERT 必须有人响应**，FATAL 立即退出。

### 5.6 数据校验：四层 + raw 自校验

| 层 | 校验 | 位置 |
| --- | --- | --- |
| L0 传输 | 长度、JSON 合法性、字段类型、必填字段 | 接收端收包层 |
| L1 帧 | 地址=1、功能码=0x04、`byteCount` 匹配、CRC 正确 | 固件（已在位），接收端用 `raw` 复算复核 |
| L2 业务 | 量程、电量单调性、时间合理性 | `db_proto.l2_*` |
| L3 跨源 | 与电表本机显示对照（M5 已做 ≥20 组）、环比突变检测 | 人工 + 脚本 |

**raw 自校验（本方案独有，老师实现没有）**：数据行同时带工程量与 `raw`。接收端用 `raw` 独立重算 39 字段，与 JSON 工程量逐字段比对：

```
一致率 = 匹配字段数 / 39
```

**验收标准**：一致率 = 100%。任何不一致都是**固件换算 bug 的直接证据**，且能定位到具体字段——这是"固件只搬运原始值"设计原则的真正价值兑现点。

| # | 指标 | 阈值 | 不通过处理 |
| --- | --- | --- | --- |
| 1 | M1 采集成功率 | ≥97% | 查 `reason` 分布，定位总线问题 |
| 2 | **M2 端到端完整率** | **≥96%** | 拆成 A / M1 / D 定位；**只认全程，禁止事后剔除时段** |
| 3 | M3 传输送达率 | ≥99% | 查 WiFi / RSSI / 端口抢占 |

| 7 | 抖动 p99 / max | ≤50 ms / ≤200 ms | 沿用任务书 M6 判据 |
| 8 | 时间戳可信率 | ≥99% | 查 NTP 三源可达性 |

| 10 | 数据质量 OK 占比 | ≥95% | `A/B/C_temp` 恒 −40 **不计入** invalid |

| 12 | 数据覆盖空洞 | 每小时 ≥1 条数据行 | 任一小时为空即判不通过 |
| 13 | 断电可恢复 | 强制断电 3 次，每次统计连续、库不损坏 | 从每日快照恢复 |

**阈值 96% 的隐含约束（必须写进验收文档，否则会被问倒）**：

由 `M2 ≈ A × M1 × D`，取 A≈99.7%、D≈99.9%，要达 M2 ≥96% 需 **M1 ≥96.4%**。也就是说：
**这条主判据实际上把 M1 的隐含下限抬到了约 96.4%**，与表中 M1 目标 97% 一致，但必须显式写出这条推导——否则会出现"三个数字各自达标、合起来不达标"的尴尬。

另报 `M2'`（排除链路不可用时段的诊断值）用于定位问题，**不替代主判据**。
