## 1. 1 秒周期的时序预算

### 结论
**可行**，但有改进空间。按现方案最坏情况约 310-320ms，占 1 秒周期的 31%-32%，余量充足；但“固定 300ms 超时”有两个隐患（周期漂移与重试溢出），建议改为**帧长驱动的动态超时**，仅保留 300ms 作为兜底上限。

### 理由（复核计算见附录 A.2）
1. 发送：8 字节 × 10 bit（8N1 = 1 起始 + 8 数据 + 1 停止）= 80 bit ÷ 9600 = **8.333ms**。
2. 接收（测试帧功能码 0x03、读 2 个寄存器，合法响应为 9 字节：地址 1 + 功能码 1 + 字节数 1 + 数据 4 + CRC 2）= 90 bit ÷ 9600 = **9.375ms**。
3. 固定超时占用：300ms ÷ 1000ms = **30%**。
4. 最坏情况单周期（从站无响应）= 8.333 + 300 + 解析 + UDP ≈ **310-320ms**，1 秒**够用**，余量约 680ms。
5. 但有两个放大场景：
   - **重试放大**：若实现“3 次重试 × 300ms”，最坏 = 8.333×3 + 900 ≈ 925ms，加上 UDP/解析可能**溢出 1 秒**，与 M6 的周期抖动指标直接冲突。
   - **周期漂移**：若时间戳在周期**结束**时更新，实际周期变成 1 秒 + 300ms = 1.3 秒。必须在周期**开始**打点（`nextPoll += 1000`），而不是 `now + 1000`。
6. 固定 300ms 的代价不只是时间：正常响应通常 10-50ms 内到达，白等约 250-290ms；而且如果写成 `while (millis() - t < 300)` 的阻塞循环，会直接违反 FR-06（禁止阻塞）。

### 建议修改
1. 超时改为两级：
   - **字符间隔超时**：Modbus RTU 标准 1.5 字符 ≈ **1.56ms**，实装取 **3-5ms** 容错；
   - **整帧兜底上限**：保留 **300ms**，仅在始终收不到首字节时兜底。
2. 收帧判据改为**帧长驱动**：功能码 0x03 的响应长度 = `3 + 2N + 2`（N 为寄存器数，测试帧 N=2 → 9 字节），收满即结束，不再等满 300ms。
3. 首字节另设**首字节等待超时**（建议 50-100ms，真机实测后再收紧）。
4. 明文写入任务书：周期基准在**周期开始**打点；`millis()` 比较必须用无符号减法（防 49.7 天溢出）。
5. 若保留重试，限定“重试总预算 ≤ 300ms”或“重试不跨周期”。
6. 收益量化：动态超时后最坏 ≈ 8.3 + 3.7 + (9.4 + 3.7) ≈ **25ms**，周期占用从约 32% 降到约 3%。

## 2. MAX13487 AutoDirection 在 9600 下的方向切换可靠性

### 结论
**需实测**（列为中高风险）。发送完成判定**必须在代码里显式处理**，且**不能用固定 delay 代替**，推荐 `Serial1.flush()`。“自己吃自己”（自回收 echo）风险**低但非零**，必须用 M3 回环实测确认，不能靠推理。

### 理由
1. MAX13487E 的 AutoDirection 是**边沿触发**：DI 上有跳变就使能驱动，DI 静默一段时间后释放驱动、使能接收。方向切换完全由硬件完成，软件**无法直接观察** TX/RX 状态，因此软件必须有一个“确认发完”的判据，否则会在驱动器仍占用总线时就开始收或过早切换逻辑。
2. 9600 下 1 bit = **104.2μs**，1 字节 = 1.042ms。方向翻转的硬件延时在微秒量级，相对比特时间可以忽略，**这正是低速率反而安全的原因**（速率越高越危险）。但具体保持时间必须**查 MAX13487E 数据手册的自动方向时序参数确认，本报告不臆测数值**。
3. **发送完成判定建议**：Arduino-ESP32 的 `Serial1.flush()` 会等待 UART 发送 FIFO 与移位寄存器全部空，是**唯一可靠的“发完”判据**。
   - ❌ 不要用 `delay(10)` 之类的固定延时替代：波特率改成 19200/38400 或帧长变化就会失效。
   - ⚠️ `flush()` 返回后，MAX13487 的驱动**可能仍未释放**（还有硬件保持时间）。因此紧接着读之前给一个**可配置的小间隔（建议 100-200μs，实测有问题再加大）**是合理的工程容错，但必须写成常量并注明理由。
   - 不要依赖 TC 中断：Arduino 层没有向用户暴露 UART TC 中断，自行配寄存器属于过度工程。
4. **“发出的帧被自己吃掉”的两种可能**：
   - (a) **真回显**：若接收器在驱动期间仍使能，会读到本机发送的数据。MAX13487E 设计上会在发送期间关闭接收器以防回显，概率低；但**部分国产 MAX13487 模块带板载逻辑，行为可能与原厂不同**，必须实测。
   - (b) **更现实的失败模式是首字节丢失**：若驱动释放与接收使能的翻转窗口与从站响应首字节重叠，会丢 1 个字节，导致 CRC 失败、整帧丢弃。9600 下每字节 1.04ms，窗口仅在翻转瞬间，风险低但存在。
   - **实测方法（M3）**：① 只发不收，确认发送后 RX 缓冲区无残留；② 回环连续 1000 帧统计误帧率；③ 有条件时用逻辑分析仪看 RO 与 A/B 时序。
   - **软件兜底**：发送完成后、进入等待响应前，**显式清空 RX 缓冲区**，再计时收帧。几乎零成本，建议直接写进 FR-04。
5. **另一处必须核对的硬件细节**：DI（TXD 输入）由 ESP32 的 3.3V 驱动，而 MAX13487 是 **5V 供电**。必须查手册确认 DI 的 VIH ≤ 3.3V（多数 MAX13487E 为 TTL 兼容，VIH 约 2.0V，即可行）。**任务书 5.2 只讲了 RX 分压，完全没讲 TX 侧电平，这是一处遗漏。**

### 建议修改
1. 任务书 FR-04 增加：发送完成后调用 `Serial1.flush()` 等待发送完成；随后显式清空接收缓冲区，再启动接收超时计时。
2. 任务书 6.5 增加禁止项：❌ 用固定 `delay()` 作为发送完成判据。
3. 任务书 5.2 增加条目：TX（GPIO21）到 DI 的 3.3V 逻辑电平兼容性需按模块手册核对。
4. 任务书 5.3 自检清单增加：发送后接收缓冲区无自回收残留（M3 用日志验证）。
5. 把“发送完成判据”列入 M3 验收（见第 10 点）。

## 3. 测试帧 CRC 字节序

### 结论
**可行 —— 复核通过，`0xC4 0x0B` 正确。** 无需修改。

### 理由
用 CRC16/Modbus（初值 `0xFFFF`，多项式 `0xA001`，反射算法，低字节先发）对 `01 03 00 00 00 02` 独立重算（见附录 A.1）：

- 计算结果 CRC 字 = `0x0BC4`
- Modbus RTU 规则：**CRC 低字节先发** → 字节序列 `0xC4, 0x0B`
- 与任务书 6.4 及 `00_context.md` 四.4.1 的测试帧**完全一致** ✓

### 建议修改
无需修改。建议在任务书 6.4 加一句固化说明：“CRC16/Modbus，初值 0xFFFF，多项式 0xA001，低字节先发”，避免后续实现写成高字节在前（这是 Modbus 最常见的实现错误之一）。

## 4. 非阻塞实现：是否一开始就上状态机

### 结论
**建议 M2 就引入最小状态机（IDLE → TX → WAIT_RX → PARSE → SEND），不要走 M6 再重构的路线。** 同时把任务书里 M6 的措辞从“重构”改为“加固”。

### 理由
1. **M2 本身就无法用顺序阻塞写法**：M2 验收是“连续 ≥60s 每秒一包”，同时还要周期检查 WiFi/NTP 状态。只要禁止 `delay()`（FR-06 与 6.5 已明文禁止），**M2 事实上必须有一个非阻塞调度骨架**。既然骨架必须有，状态机就不是“提前引入的复杂度”，而是同一件事。
2. **“先简单实现、M6 再重构”是本项目最大的进度风险**：
   - M3/M4/M5 的验收证据（回环日志、模拟从站记录、真机联调记录）都建立在当前固件行为上。M6 若推翻主干重写，**此前全部验收证据作废**，需重跑 M3-M5。
   - 任务书 7.2 的“铁律：上一里程碑未通过验收不得启动下一个”**约束不了**“已通过的里程碑被后续重写作废”这种情况。
3. **成本对比**：5 状态机约 40-60 行（`switch(state)` + `millis()` deadline）。M2 阶段 TX/WAIT_RX 分支可以先留空（只跑调度 + WiFi/NTP/UDP），属于**增量式**引入，不是一次性铺开。
4. **M6 真正的价值不在“改成状态机”，而在“加固”**：重试与退避、超时统计、看门狗、异常分类（从站无响应 / CRC 错 / WiFi 断 / UDP 失败）、2 小时计数与丢包统计。若 M6 才引入状态机，这些加固会被“重写”挤掉。

### 建议修改
1. 任务书 7.1 M6 描述改为：**非阻塞状态机加固**（重试/退避/异常分类/统计/看门狗）+ 2 小时压力测试。
2. 任务书 7.1 M2 交付核心补充：同时交付**非阻塞调度骨架（状态机最小版）**。
3. 任务书 6.1 增加 FR-07：主循环为单状态机，禁止阻塞等待；所有等待以 deadline 形式表达。
4. ⚠️ 此条**涉及 `00_context.md` 六.4 的原文措辞**（“非阻塞状态机重构”），Codex 无权修改，需用户/总控决策是否同步（见第 12 节 H-4）。

## 5. 时间戳的时间源

### 结论
**任务书当前缺失该定义（属遗漏，必须补）。** 建议：UDP 报文时间戳**取 NTP 同步后的墙钟（UTC+8 本地时间）**；`millis()` **只用于调度，不作为时间戳**；未同步时必须显式降级并加标记，禁止输出冒充真实时间的伪墙钟。

### 理由
1. **两套时钟性质完全不同**：
   - NTP 墙钟：可读性强，可直接与电脑端日志对齐；缺点是**冷启动未同步时无效**。
   - `millis()`：单调、永不失败，但有**开机零点**与**49.7 天溢出**，跨设备无法对齐。
2. **关键澄清（任务书当前理解有偏差）**：断网并不会让时间戳失效。ESP32 的 SNTP 同步成功后会用内部 RTC 继续走时（漂移约几十 ppm，秒级精度在数小时内完全够用）。真正的降级场景只有两类：
   - (a) **冷启动且从未同步成功**（WiFi 未连或 NTP 不可达）；
   - (b) 长时间断网导致的缓慢漂移（2 小时压测可忽略，但应在 M6 记录）。
3. **必须避免的失败模式**：未同步时直接格式化 `time(NULL)` 会打印出 `1970-01-01 08:00:00`，**下游看起来像正常数据**。这是最危险的静默错误，比报错更糟。任务书 9.2 说“现象优先于解释”，那就必须让“未同步”在数据里**可见**。
4. 建议实现：用 `configTzTime("<CST-8>", "ntp.aliyun.com")`（一次调用同时设定 NTP 与 UTC+8 时区，避免手工 ±8 小时运算出错），再用 `getLocalTime()` 取值；同步状态用 `sntp_get_sync_status()` 或“epoch 是否大于合理阈值（如 1700000000）”判定。

### 建议修改
1. 任务书 6.2 增加副节“时间戳来源与降级”：
   - 主源：NTP 同步后的墙钟，格式 `YYYY-MM-DD HH:MM:SS`（UTC+8）；
   - 同步判据：`epoch > 1700000000`（2023-11-15 之后）视为已同步；
   - 降级：未同步时**不得**输出墙钟，改为 `BOOT+<秒>.<毫秒>`（如 `BOOT+000123.456`），并在同一行加 `UNSYNCED` 标记；同步恢复后立即切回墙钟**并打印一条状态切换日志**；
   - 重同步：WiFi 重连成功后立即触发一次 SNTP；正常运行每 6-12 小时重同步一次。
2. 任务书 6.1 增加 FR-08：时间戳来源为 NTP 墙钟；`millis()` 仅用于周期调度。
3. 任务书 9.1 M2 验收增加：未同步状态下必须能观察到 `UNSYNCED` 标记（可人工断网验证）。
4. 补充说明：1 秒周期下**相邻两包时间戳可能相同**（1 秒粒度）。若下游需要唯一性，建议时间戳加毫秒或加序号，请在任务书中明确取舍。

## 6. secrets.h 的引入方式

### 结论
**可行。** 下面给出 `.ino` 的 include 写法、编译失败守卫、只含占位符的模板；并建议把**非敏感常量**从 `secrets.h` 拆到入库的 `config.h`。

### 理由与建议
1. **include 写法**（Arduino IDE 中 `.ino` 与 `secrets.h` 同目录，sketch 目录在包含路径上）：
   ```cpp
   // 01_firmware/esp32c3_gateway/esp32c3_gateway.ino
   #include "secrets.h"   // 引号形式，相对 sketch 目录；不要写成 <secrets.h>
   ```
   注意：**不要让 `.ino` 与 `secrets.h` 分处不同目录**。Arduino 的 `.ino` 不支持跨目录相对包含（除非改用 `src/` 结构并调整包含路径）。当前目录规划（同目录）是正确的。
2. **建议 `secrets.h` 模板（只含占位符，无真实凭据）**：
   ```cpp
   // 01_firmware/esp32c3_gateway/secrets.h   ——  不入库（.gitignore 第 80 行已忽略）
   #pragma once
   #define WIFI_SSID      "<REPLACE_WITH_SSID>"
   #define WIFI_PASSWORD  "<REPLACE_WITH_PASSWORD>"
   ```
3. **建议额外提交一个入库模板** `secrets.h.example`（内容同上，仅占位符），让仓库在缺 `secrets.h` 时仍能说明如何搭建。已复核：`.gitignore` 第 80 行的 `secrets.h` 是精确文件名匹配，`git check-ignore -v 01_firmware/esp32c3_gateway/secrets.h.example` **无输出、退出码 1**，即**不会被忽略**，可以正常入库 ✓。
4. **编译期守卫**（避免“忘了建 secrets.h 却编译通过、运行时连不上”这类难查问题）：
   ```cpp
   #include "secrets.h"
   #ifndef WIFI_SSID
   #error "secrets.h 缺失或未配置：请复制 secrets.h.example 为 secrets.h 并填写"
   #endif
   ```
5. **建议拆分（推荐，非强制）**：`secrets.h` 只放**凭据**；把 `UDP_TARGET_IP` / `UDP_TARGET_PORT` / `NTP_SERVER` / 485 波特率 / 超时等**非敏感常量**放进**入库的** `config.h`。理由：
   - 这些常量正是任务书要求“阶段二固化为常量”的受控参数（FR-05 与 4.2），放在入库文件里才能被评审与 diff 追踪；
   - 避免“改个 UDP 端口也要动不入库文件”，减少各角色之间信息不同步。
6. **纪律提醒**（建议写入 6.5）：不得把凭据写进 `.ino`；不得在串口日志中打印 SSID/密码；`secrets.h` 不得出现在截图或粘贴的编译日志里。

### 建议修改
任务书 FR-01 备注扩展为上述第 1-6 条；8.2 交付物 M1 增加 `01_firmware/esp32c3_gateway/secrets.h.example`（模板，入库）。

## 7. WiFi 掉线后的行为

### 结论
**拆分：最小自恢复必须进 M2（不能延后）；完整的断网友好自恢复归 M6。** 理由是该能力属于**测试基础设施**，不是功能特性。

### 理由
1. M2 验收是“连续 ≥60s 每秒一包**无中断**”。实验/教室环境的 2.4GHz 拥塞、路由器省电、DHCP 续租都可能造成瞬时掉线。**若 M2 没有自恢复，每次掉线都要人工复位重跑**，M3/M4/M5 的调试成本会被成倍放大。
2. 2 小时压测（M6）里，任何一次掉线若无自恢复就直接判定失败，所以它最终必须在 M6 前存在。放到 M6 才做是“最后一刻才补”，风险最高。
3. 成本极低：核心逻辑约 10 行。

### 最简实现思路（M2 版）
1. `WiFi.setAutoReconnect(true)` **且** `WiFi.persistent(true)`；
2. 但**不要只依赖** `setAutoReconnect`（不同 core 版本行为不一致，存在不触发的情况），额外做**非阻塞周期检查**：
   - 每 5 秒检查一次 `WiFi.status()`；
   - `WL_CONNECTED`：正常；状态由断变连时**打印一条日志并立即触发 SNTP 重同步**；
   - `WL_DISCONNECTED` / `WL_CONNECTION_LOST`：调用 `WiFi.reconnect()`；
   - `WL_NO_SSID_AVAIL`：AP 消失，`reconnect()` 无效，需 `WiFi.begin(ssid, pass)` 重新扫描；
   - 重试**必须节流**（≥5s 一次），避免高频重连把 CPU/射频占满。
3. **绝不允许** `while (WiFi.status() != WL_CONNECTED) delay(...)` 阻塞连接。
4. **UDP 侧**：重连后 socket 可能失效，建议 `udp.stop(); udp.begin(localPort);` 重建；目标 IP 若靠 DHCP 变化需在重连后处理（这也是“阶段二固化 IP”的理由之一，见 H-6）。
5. **计数与日志**：记录重连次数与断线累计时长并串口打印 —— 这是 M6 压测报告需要的数据，M2 就开始记，M6 才有证据。

### 建议修改
1. 任务书 6.1 增加 FR-09（最小自恢复，M2 交付）：`WiFi.status()` 周期检查 + 节流重连 + 状态变化日志。
2. 任务书 7.1 M6 描述明确：在 FR-09 基础上增加退避策略、断线/恢复统计、异常分类与 2 小时不间断验证。
3. 任务书 9.1 M2 成功条件增加：人为断开路由器 2.4GHz 30 秒后，设备在 ≤60 秒内自动恢复发包，无需人工复位（可验证、可复现）。

## 8. ESP32-C3 使用 HardwareSerial(1) + RX=GPIO20、TX=GPIO21 的可行性

### 结论
**可行，但有 1 个必须设置的编译选项（否则直接冲突）**：必须把 Arduino IDE 的 **USB CDC On Boot 设为 Enabled**，并显式传入引脚。板型细节建议在 M1 实测确认。

### 理由
1. **UART 资源**：ESP32-C3 只有 **2 个 UART 控制器（UART0、UART1）** 加 1 个 USB Serial/JTAG。因此 `HardwareSerial(1)` = UART1 **存在且合法**；`HardwareSerial(2)` 不存在，不要写。
2. **引脚可映射性**：ESP32-C3 通过 GPIO 交换矩阵，UART1 的 TX/RX 可映射到任意具备相应方向能力的 GPIO；**GPIO20/21 都是普通 IO，可以作 UART1** ✓。
3. ⚠️ **关键冲突点**：ESP32-C3 的 **GPIO20/21 正是 UART0 的默认引脚（U0RXD=GPIO20，U0TXD=GPIO21）**。
   - 若 Arduino IDE 中 **USB CDC On Boot = Disabled**，则 `Serial` 绑定 UART0，**占用 GPIO20/21**，与 `Serial1`（同样映射到 GPIO20/21）**直接冲突**：两个外设驱动同一组引脚，日志与 485 互相干扰。
   - 解法：**USB CDC On Boot = Enabled**，让 `Serial` 走 **USB Serial/JTAG（GPIO18/19，即板载 USB-C）**，把 GPIO20/21 让给 `Serial1`。
4. **USB 引脚不冲突**：USB Serial/JTAG 用 **GPIO18 (D-) / GPIO19 (D+)**，与 GPIO20/21 无关 ✓。
5. **不涉及 strapping 风险**：ESP32-C3 的 strapping 引脚是 GPIO2/8/9（GPIO9 通常接 BOOT 键），**GPIO20/21 不是 strapping 引脚** ✓，上电时不会被其电平影响。
6. **建议显式传参**（不要依赖 core 的默认映射，不同 core 版本对 C3 的 Serial1 默认引脚定义不一致）：
   ```cpp
   Serial1.begin(9600, SERIAL_8N1, 20, 21);   // 形参顺序：baud, config, rxPin, txPin
   ```
   ⚠️ 形参顺序是 **(rx=20, tx=21)**。写反会导致收发全错，且现象是“什么都收不到”，极易误判为硬件问题。
7. **需实测确认的板型差异（M1）**：市面 ESP32-C3 SuperMini 有多个版本，丝印/引脚标号不一致（部分标 `GPIO20/GPIO21`，部分直接标 `RX/TX`；个别版本板载 LED 或按键占用其它 GPIO）。M1 应做一件事：**烧一个最小 UART1 回环程序（GPIO21 短接 GPIO20），用 USB CDC 打印收发结果**，确认引脚可用 —— 这一步同时验证了 M3 的前置条件。
8. 补充：`HardwareSerial(1)` 的 `flush()`、`available()` 等 API 均可用；可选 `Serial1.setTimeout()` 用于 `readBytes()` 超时。

### 建议修改
1. 任务书 5.1 备注补充：GPIO20/21 为 ESP32-C3 UART0 默认引脚；使用 UART1 复用时必须将 Arduino IDE 的 USB CDC On Boot 设为 Enabled，`Serial` 走 USB Serial/JTAG（GPIO18/19）。
2. 任务书 7.3 M1 展开项增加两行：① 编译选项 USB CDC On Boot = Enabled；② 最小 UART1 回环自检通过。
3. 任务书 5.1 增加形参顺序提示 `Serial1.begin(9600, SERIAL_8N1, 20, 21)`，并注明顺序为 RX, TX。

## 9. 任务书 5.2 节 5 条 ⚠️ 警告的技术准确性

### 结论
**整体方向正确，但有 1 处致命措辞风险、2 处潜在错误、1 处物理遗漏。** 数值部分（1kΩ/2kΩ → 3.33V，以及反向 1.67V）**复核正确**。

### 逐条判断

**第 1 条（共地）—— 可行，需补充。**
- 正确且必须：RS-485 虽为差分，但收发器需要参考地；不共地会因共模电压超限（−7V ~ +12V）导致通信异常，严重时损坏收发器。清单里已包含“USB 转 485 模块”✓。
- 遗漏：若两端由**不同电源**供电，应确认共模电压在 −7V ~ +12V 内（严重场景需加隔离）。另建议补充“尽量单点接地，避免地环路”。

**第 2 条（电平转换）—— 数值正确、方向正确，但有 2 处需修正/补充。**
- 复核（附录 A.3）：`5V × 2k/(1k+2k) = 3.333V` ✓；反向 `5V × 1k/(1k+2k) = 1.667V` ✓。计算无误。
- **VIH 校核**：ESP32-C3 IO 的 VIH = 0.75 × VDD；VDD=3.3V 时 **VIH = 2.475V**。3.333V > 2.475V，**余量约 0.86V，判定可行** ✓。同时 3.333V 仅比 VDD 高 33mV，**低于绝对最大额定 VDD+0.3V = 3.6V**，属允许范围（会有微小钳位电流，工程上可接受）。
- ⚠️ **必须修正的理解**：该分压只在 **MAX13487 模块的 RO（RXD）引脚确实为 5V 输出**时才成立。**如果该模块板载了电平转换、RO 本身已是 3.3V 输出，再加这个分压会把 3.3V 压成 2.2V —— 低于 VIH 2.475V，反而把链路搞坏。**
- **上电前必做**：先给模块上 5V（**不接 ESP32**），用万用表量 RO 空闲电平：
  - 量到约 5V → 用 1kΩ/2kΩ 分压 ✓（按任务书）；
  - 量到约 3.3V → **直连 GPIO20，不加分压**；若已焊上分压需拆除；
  - 量到高阻/不定 → 说明需外部上拉或模块异常，先查手册。
- 可选改进：若希望分压后不超过 3.3V 轨，可用 **1kΩ/1.5kΩ → 3.0V**（仍远高于 VIH，且不再高于 VDD）。非必须。
- 遗漏：分压点会多接一根杜邦线，有引入噪声/容性负载的可能，线尽量短。

**第 3 条（供电）—— 可行。**
- 正确：MAX13487 VCC 需 5V，ESP32-C3 逻辑 3.3V。面包板阶段 5V 来自电脑 USB（经 SuperMini 的 5V 引脚），模块电流仅十余毫安，USB 供电余量足够 ✓。
- 补充：确认 USB 端口/线缆供电能力（建议 500mA 以上端口）；注意上电顺序（两者同时上电，避免“5V 已上、3.3V 未上”时把 3.33V 灌进未上电的 GPIO20）。

**第 4 条（总线偏置 / 终端）—— 有风险，需按总线节点数重算。**
- 单模块场景：4.7kΩ 偏置 + 120Ω 终端，空闲差分电压约 `5V × 120/(4700+120+4700) ≈ 63mV` —— **低于 RS-485 判定阈值 200mV，偏置本身并不足以保证失效安全**。实际能否可靠保持空闲电平，取决于 **MAX13487E 是否具备 true fail-safe 接收器**（需查手册确认；若具备，63mV 也没问题）。
- ⚠️ **多节点场景（M3/M4 一定会遇到）**：MAX13487 模块 + **USB 转 485 模块**（通常也自带 120Ω 终端）挂在同一条总线上，终端并联 **60Ω**，偏置并联 **2.35kΩ**。驱动器带 60Ω 属 RS-485 额定测试条件，**通常可行**；但若后续再接 QI 真机（第三个节点），需**实测确认**是否应拆掉部分模块的终端/偏置。
- 建议：把“总线上终端电阻总数”作为 M3 检查项（**理想是总线两端各 1 个 120Ω，中间节点不装**）；任务书 5.2 第 4 条补充“多节点并联时的等效负载与偏置需实测核算”。

**第 5 条（EN 引脚：悬空或接 3.3V）—— ⚠️ 高风险，措辞必须修正。**
- 问题 1：**“悬空”对 CMOS 输入是错误的**。CMOS 输入悬空 = 电平不确定，可能自激振荡、增加功耗、产生随机翻转。
- 问题 2（更严重）：**“接 3.3V”是否正确完全取决于该引脚的真实定义**。市面上“MAX13487 模块”的引脚命名混乱：
  - 若该脚是 **DE（驱动使能）**：接高 = **强制驱动器一直使能**，会**长期占用总线**，导致收不到任何从站数据、与其它节点冲突，甚至发热。这是**功能性致命错误**。
  - 若该脚是 **RE(bar)（接收使能，低有效）**：需接低才使能接收；接 3.3V（高）会**关闭接收器**，同样收不到数据。
  - 若模块确实实现了原厂 MAX13487E 的 AutoDirection，则该脚可能根本不需要外接。
- 结论：**在核对实物丝印与模块手册之前，不要按“悬空或接 3.3V”施工。** 建议改为：“先核对模块丝印与手册确定该脚定义；未确认前保持断开；确认后按下拉/上拉到确定电平，不得悬空。”
- 注：这条也是 `00_context.md` 三.5 的原文，属于**事实来源本身的技术风险**，需用户决策是否更新（见 H-1）。

**第 6 条（任务书 5.2 缺项，建议新增）** —— 见下方补漏条目。

### ⚠️ 额外发现：任务书 5.3 自检清单第 2 条措辞有致命误读风险

原文：`RXD → 1kΩ → GPIO20，且 1kΩ 与 2kΩ 交点接 GPIO20（不是 2k 接 RXD）`

- 前半句读起来是**“RXD 串一个 1kΩ 直接到 GPIO20”**。若照此施工（只串 1kΩ、忘记 2kΩ 到 GND），结果是 **5V 经 1kΩ 直接进入 GPIO20**，空载时 GPIO20 承受接近 5V —— **超出绝对最大额定 3.6V，可能永久损坏引脚**。
- 这是**上电前检查清单**，属于最不能有歧义的位置。
- **建议改写为**：`RXD —[1kΩ]— 分压节点 —[2kΩ]— GND；分压节点接 GPIO20（禁止只串 1kΩ 直连）`

### 5.2 建议新增的补漏条目
1. **TX 侧电平**：GPIO21 → DI 的 3.3V 驱动能力需按模块手册确认（多数 MAX13487E 为 TTL 兼容，VIH 约 2.0V，可行）。
2. **A/B 极性与丝印**：不同厂商 A/B 定义可能相反（任务书 5.3 已列为待确认 ✓，保留并强调必须**整条总线统一**）。
3. **上电顺序**：避免 5V 先上而 3.3V 后上（3.33V 灌入未上电 GPIO）。
4. **接线长度与走线**：9600 下几米杜邦线可用，但避免与强电/电机线并行。

### 建议修改
- 任务书 5.2 第 2 条补充“上电前先实测 RO 空闲电平，确认是否真的需要分压”。
- 任务书 5.2 第 4 条补充“多节点终端/偏置并联核算”。
- **任务书 5.2 第 5 条按上述重写（必须）。**
- **任务书 5.3 第 2 条按上述重写（必须）。**

## 10. 任务书 9.1 节验收标准是否技术可验证

### 结论
**有风险：M3/M5/M6/M7 有多处不可判定表述，且 9.2 第 4 条“否则以【无异常即可】暂记”等于给模糊标准留了自动通过的兜底 —— 这条必须先删。** 其余条目可判定，配量化建议即可冻结。

### 逐里程碑理由与量化建议

**M0 —— 可验证 ✓（需定义“审查通过”）**
- “13 个章节齐全”可数 ✓。
- “Codex 技术审查通过”需定义“通过”判据 → 建议：“本审查报告（`02_docs/02_任务书技术审查_Codex.md`）中不存在【不可行】结论，且所有【有风险】项均已在任务书中落实应对条目”。

**M1 —— 基本可验证 ✓（一处措辞有误）**
- “能完成一次空程序编译烧录” ✓，以 `03_logs/` 中的编译/上传日志为证。
- ⚠️ 措辞问题：“ESP32 与电脑处于同一 **2.4GHz 网段**可互通” —— 电脑在 5GHz，频段不同**不代表**不在同一网段。按字面判可能造成误判失败。建议改为：“ESP32 与电脑处于**同一局域网、同一网段**，且双向 UDP 收发验证通过（频段差异不构成判据）”。
- “互通”需给方法 → 建议：“电脑向 ESP32 的 IP:端口发送 1 个 UDP 包，ESP32 回显 1 个包，电脑收到，连续 10 次 0 丢失”。

**M2 —— 需量化（现状大体可测）**
- “连续 ≥ 60s 每秒一包无中断” ✓ 可测。需明确：ARP 首次解析可能丢首包，建议**从第 2 个包开始计时**。
- “时间戳与真实时间偏差 ≤ 1s（[待确认] 阈值）” → 需定义**测量基准与方法**。建议：“以电脑端（已 NTP 同步）接收时刻为基准，`|t_网关 − t_电脑| ≤ 1s`，统计 10 分钟约 600 包，允许 ≤1% 超差，且**无单点偏差 > 2s**”。
- 建议补：“串口同时打印 epoch 与格式化本地时间，用于证明时区确为 UTC+8”（否则无法排除把 UTC 当本地时间打印的错误）。
- 建议补：“人为断开路由器 30s，≤60s 内自恢复”（对应第 7 点 FR-09）。

**M3 —— 需量化**
- “收发字节完全一致、CRC 正确、**无丢包、无死机**” → “无丢包/无死机”不可判定。建议：“连续 1000 次回环（≥15 分钟），误帧数 = 0、丢帧数 = 0、无重启（用启动计数或串口复位原因打印验证）”。
- 建议补：“发送后 RX 缓冲区无自回收残留”（对应第 2 点）。

**M4 —— 基本可验证，补 2 项**
- “从站不回包时 300ms 超时正常触发且不阻塞下一周期” ✓ 可测，但“不阻塞”需量化 → 建议：“连续 10 次超时后仍完成后续轮询，且周期抖动 ≤ 阈值”。
- 建议补：“CRC 故意注入 1 位错误时能被识别并丢弃（不崩溃）”。
- ⚠️ 若采纳第 1 点建议（动态超时），此条 300ms 需同步改为“字符间隔超时 + 300ms 兜底”。

**M5 —— 最模糊，必须量化（且不得猜寄存器）**
- “数据与 QI 设备本地显示一致（[待确认] 对照方式）”：**“一致”没有定义量纲、缩放与容差**。建议：
  - 对照方法：QI 设备本地显示（或老师提供的参考值）截图 + 同一时刻网关输出，**至少 20 组**；
  - 容差：明确为“原始寄存器值完全相等”或“工程量误差 ≤ ±1 个最低有效位 / ≤ ±0.5% 满量程”（由用户/总控选定其一）；
  - 必须记录**缩放系数与单位**（寄存器原始值 → 工程量），否则“一致”无从判定；
  - 明确采样时刻对齐方式（人工同步，误差 ≤ 2s）。
- “稳定读数” → 建议：“连续 10 分钟，读取成功率 ≥ 99%”。
- **注意：本节不得填入任何具体寄存器地址或指令格式**（遵守“不猜 QI 协议”约束）。

**M6 —— 需量化**
- “重启次数 0” ✓ 可测。
- “循环周期抖动在 [待确认] 阈值内” → 建议：“周期 = 1000ms，99 分位偏差 ≤ ±50ms，单次最大偏差 ≤ 200ms（网关侧统计）”。
- “丢包率在 [待确认] 阈值内” → 需先定义分母。建议：“**网关侧发送计数** 对 **电脑侧抓包计数**（抓包工具固定，如 Wireshark 或网络调试助手日志）；2 小时理论 7200 包，接收 ≥ 7128（丢包率 < 1%）”。注意 UDP 本身不保证可靠，必须写明这是**局域网链路质量指标**，不是协议保证。

## 附录 A. 复核计算过程（可复现）

### A.1 CRC16/Modbus 复核（审查点 3）
- 输入：`01 03 00 00 00 02`
- 算法：初值 `0xFFFF`，逐字节异或后 8 次右移，最低位为 1 时异或多项式 `0xA001`（反射算法）
- 结果：CRC 字 = `0x0BC4` → 线上字节 **`0xC4 0x0B`**（低字节先发）✓ 与任务书一致

### A.2 时序（审查点 1，9600 / 8N1，1 字符 = 10 bit = 1.0417ms）

### A.3 分压与逻辑电平（审查点 9）

| 项 | 计算 | 结果 |
| --- | --- | --- |
| 正确分压（1k 上 / 2k 下）| 5 × 2000/(1000+2000) | **3.333V** |
| 错误分压（2k 上 / 1k 下）| 5 × 1000/(2000+1000) | **1.667V** |
| ESP32-C3 VIH（VDD=3.3V）| 0.75 × 3.3 | **2.475V** |
| ESP32-C3 VIL | 0.25 × 3.3 | **0.825V** |
| ESP32-C3 IO 绝对最大额定 | VDD + 0.3 | **3.6V** |
| 判定 | 3.333 > 2.475 且 3.333 < 3.6 | **可行**（余量 0.858V）|
