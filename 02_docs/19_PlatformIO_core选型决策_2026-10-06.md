# 19 · PlatformIO core 选型决策（`2.0.17` vs `3.x`）

> 最后更新：**2026-10-06 · 砚青** ｜ 类型：**决策备忘（建议稿，待用户 / 老师拍板）**
> 触发：用户要求从"高质量 + 未来商业化"出发，系统比较两方案并给明确推荐。
> 相关：`PROGRESS.md` §5b · `02_docs/16` §9.5 · `01_firmware/pio_verify/`

---

## 0. 先纠正一个前提：这不是两个平级选项

用户把两个方案并列（方案一 `2.0.17` / 方案二 `3.x`），但实际状态是：

| | 方案一 `2.0.17` | 方案二 `3.x` |
| --- | --- | --- |
| 与**当前板子**的关系 | **替换掉**已验证的 core | **就是当前板子跑的 core** |
| M0–M5 验证成果 | **全部作废**，要重跑 | **仍然有效** |
| 电脑侧 `arduino-cli` 编译基线 | 不等价（Flash −23.4% / RAM +4.7%，实测） | 等价（同 core） |

📌 **你现在的板子跑的是 arduino-esp32 `3.3.10-cn`，M4（1000 次）与 M5（真机 59/60）全部是在它上面通过的。**
⇒ 方案一是"**换掉已验过的核心**"，方案二是"**把已验过的核心搬到 PlatformIO 上**"。**两者的验证工作量不对称得多。**

⚠️ **另一个必须分清的混淆**：老师的要求是"**组内用 PlatformIO**"（**工具链**），不是"**必须用 2.0.17**"（**core 版本**）。这两件事是**可分的** —— 用 PlatformIO 同时钉 3.x，完全满足老师的要求。

---

## 1. 五个维度的系统比较

### 1.1 兼容性（代码层）

**实测结论（本仓库固件 API 审计，2026-10-06）**：`esp32c3_gateway.ino` 只用到
`Serial1.begin/flush`、`WiFi.begin/config/status`、`WiFiUDP`、`configTzTime` —— **全部在两个 core 上都存在、签名稳定**。
而 3.x 迁移的**全部破坏性变更区**（`ADC` / `LEDC` / `RMT` / `Timer` / `I2S` / `SigmaDelta` / `Hall` / `BLE`）**本项目一个都没用**。

⇒ **对"当前固件"而言，两个 core 的兼容性差异≈0**。"换 core 风险大"的直觉在本项目**不成立**。

**但有两个例外，且都指向 3.x**：

| 例外 | 说明 |
| --- | --- |
| **① 批次 3 的 Web 配置页** | 3.x 起网络层统一到 `Network.h`，新版 `WebServer` 库 `#include "Network.h"`；**`2.0.17` 没有这个头文件** ⇒ 钉 2.0.17 会**直接把批次 3 卡住**（要么降级用老 WebServer 库、要么自己写裸 socket）。 |
| **② `Serial1.flush()` 语义** | 本项目依赖"`flush()` 等到 TX 完全空闲"来做 485 换向（见 `config.h` 注释）。该行为已在 3.3.10 实测；**换 core 必须重新验一次**。 |

### 1.2 稳定性与安全（**商业化的胜负手**）

| 项 | `2.0.17` | `3.x` |
| --- | --- | --- |
| **官方支持状态** | ❌ **不支持**（Espressif 安全策略页明列：`4.x ✅ / 3.x ✅ / 2.x ❌ / 1.x ❌`） | ✅ 支持 |
| **生命周期** | **2024-07 起停止支持**（官方公告：2.0.x 维护至 2024-07 后 discontinued） | 活跃维护 |
| **安全补丁** | **不再有** —— 已知漏洞不会修 | 持续修 |
| **已知高危漏洞** | 全部**不可修**；且 **2026-09-18 又披露两个 `WebServer` 高危漏洞**（路径穿越 / 认证绕过）—— **批次 3 正好要用 `WebServer`** | 已修 / 可修 |

> 🔴 **对商业化这是决定性的**：拿一个 **EOL 且无安全补丁**的 core 去做"未来要卖"的设备，等于把**不可修复的已知漏洞**出厂。客户做安全审计 / 招标问卷时，"核心已停止支持"是**一票否决项**。

### 1.3 工具链与可复现性（**两个方案都有坑，3.x 的坑可解**）

| 项 | `2.0.17` | `3.x` |
| --- | --- | --- |
| PlatformIO 官方支持 | ✅ **官方 `espressif32` 平台最高就到此**（`6.12.0`） | ❌ **官方不支持** ⇒ 必须用社区 fork **`pioarduino`** |
| 获取方式 | 标准 `platform = espressif32@6.12.0` | `platform = https://github.com/pioarduino/platform-espressif32/releases/download/<版本>/platform-espressif32.zip` |
| 可复现性风险 | 低（官方） | **中** —— 依赖社区仓库；**切勿用 `stable` 浮动标签**，必须钉**精确 release URL** |

⇒ 这一项 `2.0.17` 占优（官方支持），但**它占优的代价是 1.2 那张红表**。
⇒ 3.x 的复现风险 **可以通过"钉死精确版本 + 把框架包归档进发布流程"消掉**（见 §3）。

### 1.4 验证工作量

| | 方案一 `2.0.17` | 方案二 `3.x` |
| --- | --- | --- |
| 需重验范围 | **全部**：M2 WiFi/NTP/UDP、M3 回环、M4 真实总线 1000 次、M5 真机、超时档位、`flush()` 换向 | **仅"对照验证一次"**：确认 PIO 产物与现行 `arduino-cli` 产物**行为等价** |
| 估算工作量 | **大**（等于从 M2 重跑一遍 M5，且真机窗口稀缺 ⇒ 卡在"只有你能碰配电箱"） | **小**（一次台面 + 一次真机长跑） |
| 依赖真机 | **强依赖**（M4/M5 必须重做） | 中（真机长跑本就是 M6 要做的，可合并） |

### 1.5 潜在风险汇总

| 风险 | 方案一 `2.0.17` | 方案二 `3.x` |
| --- | --- | --- |
| 安全漏洞不可修 | 🔴 **高（确定发生）** | 🟢 低 |
| 核心停止支持 | 🔴 **高（确定发生）** | 🟢 低 |
| 批次 3 Web 配置页受阻 | 🔴 高（缺 `Network.h`） | 🟢 无 |
| 已验成果作废返工 | 🔴 高 | 🟢 无 |
| 构建链可复现性 | 🟢 低（官方） | 🟡 中（社区 fork，可解） |
| 与老师环境一致 | 🟢 一致 | 🟡 需在 `platformio.ini` 里写明并告知老师 |

## 2. 结合"高质量 + 未来商业化"的权衡

商业化要的是三件事，逐条对：

1. **可长期供货 / 可审计** ⇒ `2.0.17` **停支 + 无补丁**，直接出局。
2. **可复现构建** ⇒ 两方案都能做到（3.x 需钉死版本，见 §3）；**不是选 2.0.17 的理由**。
3. **可演进（要加 Web 配置页、要长期维护）** ⇒ 3.x 的 `Network.h` / 新网络栈是**唯一能往前走的路**。

而"和老师一致"的诉求，实质是**组内协作摩擦**，不是技术质量。它可以用**更低成本**满足：**代码本身两个 core 都能编**（§1.1 已实测），我们在 `platformio.ini` 里钉 3.x 并**在交付说明里写明**即可；老师的 PlatformIO 要求照样满足。

## 3. ✅ 推荐：方案二（`3.x`），但必须"钉死 + 自持"

### 3.1 结论

**推荐 3.x。** 理由按权重：

1. **它已经是你的验证基线** —— 选 2.0.17 = 亲手作废 M0–M5，且返工**卡在只有你能碰的真机窗口**上。这是最大的一笔成本。
2. **2.0.17 已 EOL 且无安全补丁** —— 商业化下这是**不可接受的出厂风险**，且批次 3 要用的 `WebServer` 恰在 2026-09 新披露高危漏洞。
3. **本固件不碰任何 3.x 破坏性 API** —— "迁移风险"这个反对理由在本项目**实测不成立**（§1.1）。
4. **批次 3（Web 配置页）在 2.0.17 上直接走不通** —— 选 2.0.17 等于给下一批**提前挖坑**。

### 3.2 落地方式（把 3.x 的"坑"消掉）

```ini
; 01_firmware/pio_verify/platformio.ini —— 要点：钉精确版本，不用 stable 浮动标签
[env:esp32c3]
platform = https://github.com/pioarduino/platform-espressif32/releases/download/55.03.30/platform-espressif32.zip
board = esp32-c3-devkitm-1          ; HW-466AB 对应 SuperMini，需按实际 flash/分区核对
framework = arduino
board_build.mcu = esp32c3
monitor_speed = 115200
; 3.x 若自定义额外编译参数：必须保留 -MMD -c（3.x 的构建变更，漏了会编不过）
```

**四条自持措施**（商业化必需）：
1. **钉精确 release**（如 `55.03.30` → Arduino `3.3.0` / IDF `5.5.0`），**禁止 `stable`**。
2. **把框架包归档**（下载好的 platform zip 存进本项目发布物 / 内网），发布构建**不依赖 GitHub 可达** —— 这条同时解决你们已踩过的"国内直连 PIO CDN ≈14 KB/s"问题。
3. **保留 `arduino-cli` 作为参照工具链**：它已是"命令行 + 可复现 + 能烧"，既是**审计基准**，也是 PIO 出问题时的**退路**。
4. **迁移后做一次对照验证**（不可省）：同代码在两套工具链下**编译产物大小对比** + 一次台面（`m5_slave_04.py`）+ 一次真机 ≥10 min。

### 3.3 ⚠️ 待确认（写进 §8.1）

- 现板 core 报作 **`3.3.10-cn`** —— **"`-cn`"疑似国内镜像封装，其版本号是否对应官方 `3.3.x` 的某个确切 patch，需核实**。若它**不是**官方版本，则"PIO 3.x 与现板等价"这句话**不精确**，对照验证更不能省。
- 建议一致化的目标：**把开发板包统一到官方 `3.3.x` 的某一确定版本**，两边（Arduino15 与 PlatformIO）对齐，避免"两套环境、两个 patch"。

## 4. 如果老师坚持 2.0.17（退让方案）

若老师出于组内统一而要求 2.0.17，**技术上可行**（当前固件两个 core 都能编），但必须让他知道代价：
- **批次 3 的 Web 配置页在 2.0.17 上做不了**（缺 `Network.h`）⇒ 要么放弃 Web 配置页、要么用老库绕。
- 产品侧**等于接受"核心已 EOL、无安全补丁"**。
- 需要**把 M2–M5 重跑一遍**（尤其碰真机）。
> 建议姿态：**代码保持"双 core 可编"**（这也是质量要求），环境**推荐钉 3.x**；把这份备忘给老师看，让他基于**安全支持**而非习惯来做决定。
