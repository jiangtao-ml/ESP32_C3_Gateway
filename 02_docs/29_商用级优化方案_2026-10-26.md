### 1.2 已经达到商用级的要素（这些不用再改，别再"优化"掉）
1. **三线程解耦**：T1 收包只做 `recvfrom` 入队，T2 落库，T3 统计 —— 落库慢不会丢包（`Q_MAX=20000`）。
2. **原始流水不可再生优先**：`udp_packet` 每包立即 `commit`，宁可多一次 fsync 也不丢证据。
3. **世代（epoch）机制**：seq/poll 计数回退即切世代，避免重启被算成上千"重复包"（这是很多人踩的坑，本仓库已解决）。
4. **对账恒等式**：`期望行 = 收到 + 未发出 + 网络丢失 → 残差`，缺口不是"猜"出来的，是算出来的。
5. **缺口三层归因**：`udp_rcvbuf_errors` / `nic_rx_dropped` / `rx_missed` 分开记，能区分"空口丢"与"接收端丢"。
6. **fail-closed 解密**：错解一律 `None`，脏数据比丢包严重（`decrypt_frame` docstring 已写明）。
7. **同秒撞车四因区分**：`SAME_SECOND`/`CLOCK_STEP`/`COLLIDE`/首包分开处理，没把分辨率伪影当故障（第一版错过并被记录下来）。
8. **`--selftest` 构造数据集自检**：不需要设备就能验统计引擎，这是回归测试。
9. **在线备份 + WAL checkpoint**：`VACUUM INTO` 每 24h、`TRUNCATE` 每 6h。
10. **字段字典 CSV 驱动**：新增点位不改代码，改 CSV。

## §3 优化方案与具体改动

> 每条给出：问题 → 根因 → 改哪里 → **怎么改** → 风险 → **怎么验证**。
> 代码为**示意实现**，不是最终提交版本；落盘前需复核。

### P0-1 时钟回退钳位（拆掉 `CLOCK_STEP` 死结）★最高优先

**问题**：WiFi 掉线 → 重连 → `g_ntpResyncPending=true` → `configTzTime` 重新对时 → 本机无外部晶振、RTC 日漂 0.9–4.3 s ⇒ SNTP 把时钟**往回拨** ⇒ 1 Hz + 秒级 `ts` 必然撞上已占用的秒 ⇒ 接收端记 `CLOCK_STEP` ⇒ **Y-4 = 0 ⇒ 168h 总体判 F**。这是"跑完 7 天才发现"的类型。

**根因**：`configTzTime` 无条件接受 SNTP 结果，没有"时钟只许前跳"的钳位。

**改哪里**：`esp32c3_gateway.ino` 新增 `ntpApplyWithGuard()`，替代 3 处 `configTzTime` 调用（`:498`、`:515`，以及后续同类）。

**怎么改**（示意）：
```c
// ---- 新增：时钟单调护栏 ------------------------------------------------
static uint32_t g_clkHoldCount = 0;      // 被拦下的回退次数（上心跳）
static time_t   g_clkLastGood  = 0;      // 上次被接受的墙上时间

// 只许前跳：SNTP 结果早于 g_clkLastGood 时不接受，保持旧时钟。
// Δ>CLK_BIG_STEP_S（默认 3600）视为"真的错了"，仍接受并单独计数（避免永久卡死）。
static const int32_t CLK_BIG_STEP_S = 3600;

static void ntpApplyWithGuard(const char *why) {
  configTzTime(NTP_TZ_INFO, g_ntpPrimary, NTP_SERVER_2, NTP_SERVER_3);
  // SNTP 是异步的，首个回包在几十~几百 ms 后到；此处只能"挂标志"，
  // 真正的判定放在 ntpTick 的下一次检查里（见 ntpClampTick）。
  g_clkGuardPending = true;
}

// 在 ntpTick() 里，ntpHasReply() 成立之后调一次
static void ntpClampTick() {
  if (!g_clkGuardPending || !ntpHasReply()) return;
  g_clkGuardPending = false;
  time_t now = time(nullptr);
  if (now < 1600000000) return;                    // 明显未就绪
  if (g_clkLastGood && now < g_clkLastGood) {
    int32_t back = (int32_t)(g_clkLastGood - now);
    if (back <= CLK_BIG_STEP_S) {                  // 小幅回退 ⇒ 拒绝
      struct timeval tv = { .tv_sec = g_clkLastGood, .tv_usec = 0 };
      settimeofday(&tv, nullptr);
      g_clkHoldCount++;
      Serial.printf("[CLK] 拦下 NTP 回退 %ld s（保持 %ld），累计 %lu 次\n",
                    (long)back, (long)g_clkLastGood, (unsigned long)g_clkHoldCount);
      return;
    }
    Serial.printf("[CLK] 回退 %ld s 超过大跳阈值，接受（疑似真错误）\n", (long)back);
  }
  g_clkLastGood = now;
}
```

**风险**：
- `settimeofday` 会与 `getLocalTime` 竞争 —— 单线程 loop，无并发问题，但**必须**在 `ntpTick` 内调用（不要在 ISR）。
- 若 RTC 初始就慢很多（首次对时），`g_clkLastGood` 为 0 直接接受，不受影响。
- **保底做法（若不想改固件）**：接收端把 `SAME_SECOND` 与 `CLOCK_STEP` 从**判据里剔除**，改为只在 `ts` 倒退 **> 5 s** 时记 `CLOCK_STEP`。这是"改判据而不是改代码"，**但必须导师同意**，因为它动了 Y-4 的口径 —— 只有你能去问。

**怎么验证**：`06_tests/ntp_verify.py` 打通后，人为 `WiFi.disconnect()` 3 次，串口应出现 3 次 `[CLK] 拦下 NTP 回退`，且接收端 `event_log` 的 `CLOCK_STEP` 计数**不增加**。

### P0-2 心跳里的 `queue`/`dropped` 是假数据

**问题**：`.ino:756` 写死 `(unsigned)0, (unsigned)0`。接收端把它当"发送端积压为 0"写进 `stat_snapshot.q_depth`，报告里出现"队列健康"的结论 —— **这是自证清白式的假指标**，商用交付里最忌讳。

**两条路，我推荐 B**：
| 路 | 做法 | 代价 |
|---|---|---|
| A | 真做发送队列（环形缓冲 + 有界重发） | 引入重复 `seq` 风险（`.ino:793` 明确禁止重传），与 M8 冲突。**不建议** |
| **B** | 诚实化：`"queue":null,"dropped":null`，新增 `"tx_fail":<计数>` | 5 行代码；接收端需容忍 null（`HB_REQUIRED` 不含这两键，已兼容） |

**怎么改 B**：
```c
static uint32_t g_udpTxFail = 0;   // beginPacket/endPacket 失败次数

// buildHeartbeatJson 内，替换 "...\"queue\":%u,\"dropped\":%u"
"\"queue\":null,\"dropped\":null,\"tx_fail\":%lu,\"reconn\":%lu,\"up\":%lu",
(unsigned long)g_udpTxFail, (unsigned long)g_reconnectCount,
(unsigned long)(millis() / 1000UL)
```
`udpSendLine()` 失败分支里 `g_udpTxFail++`。
**同时**：接收端 `Writer._process` 里 `obj.get("poll_ok")` 那组判断保持不动（`queue` 不在必需键内），并在 `build_report` 的"队列"行改为读 `tx_fail`。

**为什么这条是 P0**：它不影响跑不跑得完，但影响**报告可不可信**。168h 报告里出现一个恒为 0 的"健康指标"，评审一眼就会怀疑其余数字。

**验证**：`--selftest` 加一条用例：构造 `queue:null` 的心跳，断言 `store` 不报 `BAD_FIELD`，且 `stat_snapshot.tx_fail` 有值。

### P0-3 看门狗 + 复位原因上报（`R-02` 收口）

**问题**：固件无 `esp_task_wdt`。若 `loop()` 内任一 tick 卡死（例如 `udp.write` 遇协议栈异常），设备**静默停采**，云端只看到"没数据了"，与"断网"无法区分。

**改哪里**：新文件 `watchdog.h`（或直接进 `.ino` 顶部）+ `setup()` / `loop()`。

**怎么改**：
```c
#include <esp_task_wdt.h>
#include <esp_system.h>

RTC_NOINIT_ATTR static uint32_t g_bootCount;   // 深睡/复位不丢
static uint32_t g_bootCountNow = 0;

// setup()
g_bootCount++;
g_bootCountNow = g_bootCount;
esp_reset_reason_t rsn = esp_reset_reason();
esp_task_wdt_init(30, true);       // 30 s 超时，超时直接复位（不打印）
esp_task_wdt_add(NULL);            // 喂自己（loopTask）

// loop() 末尾
esp_task_wdt_reset();
```
心跳新增：`"boot":<g_bootCountNow>,"rsn":<rsn编码>`

**⚠️ 必须先做的实测（否则会变成复位循环）**：
1. `esp_task_wdt_init(30,true)` 后，`Serial1.flush()` 在 9600 波特下一帧 83 B ≈ 86 ms —— 远小于 30 s，安全。
2. `WiFi.begin()` 首次连接若阻塞 > 30 s 会复位 ⇒ 建议 **30 s 起，实测 8h 无复位后保持**；若 8h 内 `boot` 增长，说明有真阻塞点，这本身就是**有价值的发现**。
3. `RTC_NOINIT_ATTR` 在断电后归零 —— 这是已知局限，报告中"boot 计数在断电后会重新计"，靠 `esp_reset_reason()` 区分软复位/上电。

**顺带解决一件事**：`rsn` 能让 `R-02` 从"开放风险"变成"已监控"。8h 门控里 `boot` 恒为 1 是一条**硬证据**。

### P0-5 接收端在 Windows 上的文件系统检查形同虚设

**问题**：`env_check()` 用 `open("/proc/mounts")` 判网络盘。Windows 上 `OSError` 被 `except` 吞掉（`udp_collect.py:2399`），**静默跳过**。而旧电脑正是 Win10（你的方案）⇒ 这条检查 100% 不生效，而"DB 放在网络盘/OneDrive 同步目录"恰恰是 SQLite WAL 最常见的破坏源。

**怎么改**（纯标准库 + ctypes，不装依赖）：
```python
def _fs_kind_win(path: str):
    """Windows：返回 (盘符类型名, 是否远端)。取不到返回 (None, False)。"""
    try:
        import ctypes
        root = os.path.splitdrive(os.path.abspath(path))[0] + "\\"
        t = ctypes.windll.kernel32.GetDriveTypeW(root)
        names = {0: "UNKNOWN", 1: "NO_ROOT", 2: "REMOVABLE", 3: "FIXED",
                 4: "REMOTE", 5: "CDROM", 6: "RAMDISK"}
        return names.get(t, "UNKNOWN"), (t == 4)
    except Exception:
        return None, False
```
`env_check()` 里加分支：
- `REMOTE`(4) ⇒ 硬项失败（网络盘）
- `REMOVABLE`(2) ⇒ 硬项失败（U 盘，会被拔）
- `FIXED`(3) ⇒ 继续检查"是否在 OneDrive/Dropbox 同步目录"（路径含 `OneDrive`/`Dropbox`/`坚果云` ⇒ **硬项失败**，这是 Windows 侧的 WAL 杀手）

**验证**：`--env-check` 在 C 盘、D 盘、网络映射盘、OneDrive 目录各跑一次，四种输出都要对。
