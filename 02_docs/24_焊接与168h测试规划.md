## 0. 三个必须先纠正的前提

写在最前面，因为后面所有数字都依赖它们。

| # | 常见说法 | 核实结果 | 影响 |
| --- | --- | --- | --- |
| **F-1** | 「MAX13847」 | 全仓 0 次出现。实物 = **MAX13487(E)**，SOIC-8，**无 DE 脚**（AutoDirection）。文档里 `MAX13487` 与 `MAX13487E` 混用，是同一颗 | 器件选型、引脚定义 |
| **F-2** | 「UDP 丢 2/1800 ≈ 99.9%」 | **错**。M6 那 900 s 的原始数据：seq 145–1945 应有 1801 行，实收 1782 行，**缺 19 行 = 18 条数据行（870 B）+ 1 条心跳（190 B）** ⇒ 数据行送达 **882/900 = 98.0%** | **M2 阈值 96%，只剩 2 个百分点余量**。原记录保留并加更正括注，见 `PROGRESS.md §8.2` |
| **F-3** | 「周期 1 s，168h = 604800 轮」 | **成立**。M6 900 s 内 `poll_ok` 75→975（+900），898 个心跳间隔 = 1.000 s、1 个 = 2.000 s，零系统性漂移 | 604800 可直接作 M2 分母 |

> F-2 是本方案最重要的一个修正。如果按 99.9% 去准备，会在 168h 跑完才发现只有 98%，届时既没有时间排查，也很难解释为什么"和之前一样却没通过"。

## 1. 硬件与接线（施工摘要）

详细工序见 `05_hardware/洞洞板固化操作卡_2026-10-08.md` **v1.1**，纸面绘图规格见 `05_hardware/洞洞板布局图_2026-10-21.md`。此处只列**会影响测试结果**的要点。

### 1.1 唯一权威接线（8 根，交叉）

| # | 从 | 到 | 说明 |
| --- | --- | --- | --- |
| 1 | ESP32 `5V` | 模块 `VCC` | 模块必须 5V |
| 2 | ESP32 **`3.3`** | 模块 **`EN`** | 固定高电平；**本次裁定接 3.3V**（原文档写 5V，已统一） |
| 3 | ESP32 `G` | 模块 `GND` | 共地，先焊 |
| 4 | ESP32 `21`（TX） | 模块 `RXD` | **交叉**：模块 RXD = 芯片 DI |
| 5 | ESP32 `20`（RX） | 模块 `TXD` | **交叉**：模块 TXD = 芯片 RO |
| 6/7/8 | 模块 `A`/`B`/`GND` | 端子 `1`/`2`/`3` | 总线侧丝印顺序是 **B → A → GND** |

- 模块板载已有 `472/121/472` ⇒ **板上不得再加终端或偏置**（重复加终端会让 A↔B 变 60 Ω）。
- **不分压已定稿**：用户 2026-10-21 确认 `RXO` 直连 `GPIO20`，不做 1k/2k 分压。详见 `05_hardware/洞洞板固化操作卡` §0。
- **本板无排母**：两个模块的引脚直接穿板焊死，**焊上即不可拆**。因此图纸签核与焊后电检（M1–M17）两关的权重高于常规做法。

### 1.2 安全红线（原样执行）

1. 真机带电期间**拔掉 USB 数据线**，改用独立 5V 供电——不隔离，强电会经 USB 地 + 485 共模**烧电脑主板**。
2. **每次改接线前断电 + 验电**；没有万用表不许开箱。
3. STB3-125 **只读不写**：合闸 / 分闸 / 锁扣 / 复位 / 写寄存器 / 广播一律禁止。
4. 禁止 5V 直灌 GPIO20（绝对最大额定 3.6 V）。

## 2. 代码优化（长跑前必须先做完）

### 2.1 优化目标的重新定义

原始诉求是"提升跑数据时的表现"。先说结论：**提速不是瓶颈**。

- 一轮采集约 105–120 ms，占 1 s 窗口约 10%；
- 周期实测零漂移，`endPacket` 全部返回成功，`udp_tx` 与 `seq` 逐行相等（0 处不符）；
- `free_heap` 在 900 s 内稳定在 179.5 KB，斜率 −17 B/小时。

真正的风险是**可观测性缺失**与**2% 的系统性丢失**。所以本节优化的重点是"让 168h 结束时拿到的报告可信"，而不是"让每秒快 1 ms"。

### 2.2 接收端（`06_tests/udp_collect.py`）

| # | 改动 | 为什么这是必须的 |
| --- | --- | --- |
| B-1 | 统计线程改用**读写连接**（原来是只读） | 原来它要写 `stat_snapshot` 与 `event_log`，但连接是 `mode=ro`，异常又被 `except sqlite3.Error: pass` 吞掉 ⇒ **分钟快照、GAP、磁盘告警全部静默为空**，而报告看起来正常 |
| B-2 | `ensure_run` 统一返回 **aware datetime** | 续跑返回 naive、新建返回 aware ⇒ 进程重启过一次后 T3 比较 `deadline` 抛 `TypeError` 死亡，**168h 自动收尾永不触发** |
| B-3 | 注册 **SIGTERM/SIGINT** handler（只置标志） | 原来只捕 `KeyboardInterrupt`；`systemctl stop` 发 SIGTERM 会直接杀进程 ⇒ 排空队列、`ended_at`、checkpoint、报告**全部跳过** |
| A-4 | 新增 `stop_signal_at`，时长以它为准 | `ended_at` 是收尾之后才写的，30 min 冒烟里收尾能花 2 min，拿它算时长会把 M2 拉低约 6.7%——自己制造的门控失败 |
| A-5 | `SO_RCVBUF` 设后**回读**并落库 | Linux 会把 1 MiB 请求**静默截断**到 `net.core.rmem_max`（Ubuntu 默认 208 KB ⇒ 约 190 s 而非设计里的 475 s），不报错、不看就发现不了 |
| A-6 | 每 60 s 采 `/proc/net/snmp`（`InErrors`/`RcvbufErrors`）与网卡 `rx_dropped`/`rx_missed_errors` | 这是 Linux 独有的证据源。**没有它，就永远分不清"空口丢"与"接收端丢"** |
| A-7 | 主机名 / IP / OS / Python / SQLite 版本 / 代码 commit / bin SHA256 落库 | 原来 `COMPUTERNAME` 在 Linux 输出 `主机：?`；且这些数必须从库里读，不能读运行时环境，否则 `--report-only` 换机重算时封面会变，"逐字节一致"永远不成立 |
| A-8 | 报告固定 **LF** 行尾 + `--report-out` | Windows 的 CRLF 会让跨机复算 diff 全红，被误判成"复算不一致" |
| A-9/A-10 | SQLite <3.24 直接退出；新增 `--env-check` | `ON CONFLICT DO UPDATE` 需要 3.24（Ubuntu 18.04 自带 3.22）。带病跑 168h 是最贵的失败方式 |
| A-11 | 每日 `Connection.backup()` 在线备份 + SHA256，保留 3 份 | 不用 `VACUUM INTO`（需 SQLite ≥3.27），`backup()` 在所有版本都对且不长时间持锁 |
| A-13 | `--verify-raw`：用 `raw` 重算 39 字段与 **JSON** 比对 | 必须比 JSON，不能比 `meter_record`——后者本来就是 raw 算出来的，自己跟自己比必然 100%，是同义反复 |

**不变的部分**：收包线程仍只做 `recvfrom + json + 计数 + 入队`；报告数字仍 100% 由 SQL 重算；`udp_packet` 先写的顺序不变；**`db_proto.py` 一个字未改**；不引入第三方依赖。

### 2.3 固件（4 项零协议风险加固）

| # | 改动 | 收益 |
| --- | --- | --- |
| C-1 | `udpSendLine()` 校验 `write()` 返回值（≠`strlen` 即失败） | 短写时 `endPacket()` 仍可能返回 1 ⇒ `udp_tx` 记成"已发"而实际只发出一部分，接收端只看到 `bad_json`，对账时被算成"网络丢失"，**把排查方向整条带偏**。**不做应用层重传**（重传会造重复 `seq`，污染 M8） |
| C-2 | 数据行的 `ip` 改用栈上 `char[16]`，去掉每轮 `String` 分配 | 消除实测 356/712 B 的堆锯齿，降低 168h 碎片风险；JSON 里 `ip` 逐字节不变 |
| C-3 | 丢轮分支打 `[POLL][SKIP]` 日志 | 原来该分支**完全静默**，168h 对账出现"墙钟有 N 轮、poll 只涨 N−k"时查不出是设备跳轮还是网络丢包。**只加日志，不加 JSON 字段** |
| C-4 | `SERIAL_VERBOSE_ROUND` 开关（长跑设 0） | 每轮从约 1961 B / 44 次 write 降到约 120 B / 2 次；168h 累计省掉约 1.09 GB 的纯格式化浪费 |

## 3. 验收标准（34 条，判定 P / F / M）

判定规则：
- **P（Pass）**：达到阈值。
- **F（Fail）**：未达阈值，或数据不足以判定。
- **M（Manual）**：需人工裁定（由导师/第二人确认）。
- **主判据任一 F ⇒ 总体不通过**，其余为分项结论。

### 3.1 主判据（9 条，一票否决）

| # | 判据 | 公式 | 阈值 | 判定条件 | 数据来源 |
| --- | --- | --- | --- | --- | --- |
| Y-1 | **端到端完整率 M2** | 数据行 / 604800 | **≥96%** | <96.0% ⇒ F；96.0–96.5% ⇒ M（需解释余量） | `SELECT COUNT(*) FROM udp_packet WHERE ptype='data'` |
| Y-2 | 传输送达率 M3 | 去重收到 / 应唯一发送 | ≥99% | <99% ⇒ F | 见 §4 M3 |
| Y-3 | 重包率 M8 | 1 − distinct/rx | ≤0.01% | >0.01% ⇒ F | `GROUP BY device_id,epoch_id,seq HAVING COUNT(*)>1` |
| Y-4 | 时钟回跳 M10 | `CLOCK_STEP` 事件数 | **= 0** | ≥1 ⇒ F（说明 ts 倒退，数据可能被覆盖） | `event_log WHERE kind='CLOCK_STEP'`；**交叉证据（2026-10-27 起可用）**：心跳 `clk_hold` > 0 且 `CLOCK_STEP` = 0 ⇒ 固件时钟钳位确实生效；若 `clk_hold` = 0 而 `CLOCK_STEP` = 0，说明整段没触发过回退，属"未验证"而非"已验证" |
| Y-5 | 队列溢出 | `q_drop` | **= 0** | >0 ⇒ F（接收端自己丢的包） | `MAX(q_drop) FROM stat_snapshot` |
| Y-6 | 解析失败率 | (bad_json+bad_field)/rx | ≤0.01% | >0.01% ⇒ F | `udp_packet.parse_status` |
| Y-7 | 非人为重启 | `device_epoch` 数 − 1 − 计划重启 | **= 0** | ≥1 ⇒ F | `device_epoch` |
| Y-8 | 数据覆盖空洞 | 每小时数据行数最小值 | **≥1** | 任一小时为 0 ⇒ F | `substr(recv_time,1,13)` 分组 |
| Y-9 | 磁盘余量 | 全程 `disk_free_mb` 最小值 | ≥10 GB | <10 GB ⇒ F | `MIN(disk_free_mb) FROM stat_snapshot` |

### 3.5 先做 8 小时门控（不是放宽阈值）

M2 只剩 2 个百分点余量，**不能拿 168h 去赌**。168h 开跑前必须先跑 8 h：

| 8h 观测 | 动作 |
| --- | --- |
| M2 ≥97.5% 且 95% 置信下界 ≥96.5% | 放行 168h |
| 96.5%–97.5% | 延长到 24 h；仍 <97.5% ⇒ 停 |
| **<96.5%** | **停，不上 168h**，按 §6 判定树排查 |
| ≈98% 且 pcap 证明是空口丢 | 可放行，但报告必须写"系统性空口损失约 2%，阈值余量仅 2 点"；最差小时 <90% 仍停 |

统计功效：8 h = 28 800 轮，98.0% 的 95% CI ≈ ±0.16%（与 96% 相距约 12σ）。
**30 分钟只有 1800 轮，且 1 Hz 丢包成簇**，CI 约 ±0.65%，不足以判断 2 个点的余量。

## 6. 未采集数据的错误分析方案

### 6.1 五个层级与判据

从"缺口"出发，逐层排除。**每一层只回答一个问题，答不出来就停在该层记"证据不足"。**

```
缺口 (gap_id)
 ├─ L1 设备在跑吗？         ΔR 是否明显小于墙钟轮数
 ├─ L2 跑了但没组装？        Δseq < 2ΔR
 ├─ L3 组装了没发出？        Δseq > Δudp_tx + 1
 ├─ L4 发出但没到？          Δudp_tx + 1 > R
 │    ├─ L4a 内核缓冲溢出     RcvbufErrors 增量 > 0
 │    ├─ L4b 网卡/驱动丢      rx_dropped / rx_missed_errors > 0
 │    ├─ L4c 空口丢          pcap 也少 且 DB ≈ pcap
 │    └─ L4d 端口被抢        pcap 有、DB 几乎无、ss 出现两个 socket
 ├─ L5 到了没入库？          udp_packet 有、meter_record 无
 └─ L6 入库但值错？          raw 重算与 JSON 不符
```

### 6.2 每层的证据与 SQL

| 层 | 判据 | SQL / 证据 |
| --- | --- | --- |
| L0 | 列出所有缺口，**不猜原因** | 相邻 `hb` 的 `recv_mono` 差 > 5 s 即为一个缺口，按 `epoch_id` 分组编号 |
| L1 | 设备没跑 | `SELECT poll_ok, poll_err FROM udp_packet WHERE ptype='hb' ORDER BY id`，看相邻两条的差是否 < 墙钟轮数 |
| L2 | 跑了没组装（WiFi 未连时 `seq` 不增、`poll` 照增） | `Δseq` vs `2·ΔR`；配合 `poll_ok/poll_err` |
| L3 | 组装了没发出 | `Δseq` vs `Δudp_tx + 1`；台上时看 `[UDP][ERR]` |
| L4 | 发出没到 | `Δudp_tx + 1` vs 该窗口内 `COUNT(*)` |
| L4a | 内核缓冲 | `MAX(udp_rcvbuf_errors) - MIN(...) > 0` |
| L4b | 网卡/驱动 | `nic_rx_dropped` / `nic_rx_missed` 增量 |
| L4c | 空口 | pcap 与 DB 同窗计数：`\|P − R\| / P < 1%` 且 `P < 期望` |
| L4d | 端口被抢 | `ss -lunp \| grep 8888` 出现两个 socket；或 pcap 有而 DB 几乎无 |
| L5 | 到了没入库 | `SELECT parse_status, COUNT(*) FROM udp_packet GROUP BY 1`；`event_log` 的 `STORE_BAD` |
| L6 | 值错 | `--verify-raw` 输出的 `_rawcheck.csv` |

### 6.3 闭合判据

```
1 − R/期望  ≈  L_air + L_recv + L_parse
```

不闭合的部分记 `UNATTRIBUTED`，**必须留在报告里**，超过 0.1% 触发人工复核。

### 6.4 五条硬规矩

1. **没有 pcap 覆盖，不得判定"空口丢"**。
2. **没有计数器差分，不得判定"设备没发"**。
3. **没有 `RcvbufErrors` / `rx_dropped`，不得判定"接收端丢"**。
4. `UNATTRIBUTED` 不得省略、不得改名、不得合并进其它类。
5. **禁止用"可能 / 大概 / 应该是"填空**；证据不足就写"证据不足，需补测"。

> 这一节的目的是**防止把猜测写进验收文档**。一个没有被证伪过的归因，比"未知"更危险。
