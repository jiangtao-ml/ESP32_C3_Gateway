## 0. 一句话结论

**项目本身的工程纪律比一般学生项目强得多**（字段字典驱动、先模拟后真机、"作者≠验证者"、方法学红线留档）——这些是资产，不要动。

**拖效率的不是技术，是三件事：**

1. **同一份事实散在 8+ 个文件里** —— 最典型的 IP `.113` 遍布 8 个入库文件；它每隔几天就漂一次，每次要人工同步 8 处。
2. **规则本身在重复、并已自相矛盾** —— 同一批规则在 `PROGRESS.md` §2b/§6、接手指令 §5、`00_context.md` 里各写一遍；`README.md` §6.1 已出现两段互相打架的 EN 说明（证据见 §4.6）。
3. **一条"WorkBuddy 不许写 ESP32 代码"的硬分工，把最便宜的验证动作（编译、跑宿主机测试）也一并锁死了** —— 这条是把"作者≠验证者"这个**正确原则**，错误实现成了"某角色永久禁用某动作"。

## 2. 流程与协作：可优化项（按收益排序）

### 2.1 【高】事实源重构：单一机器可读源 + 一处叙述层

**现状**：`192.168.1.113` 出现在 8 个入库文件（`config.h`、`README.md`、固件 `README.md`、任务书 §11、`00_context.md`、`04_ai_prompts/02·03·04`、接手指令 §5）。**它每周漂 1~2 次**，每次都要人工核对全仓。

**建议**：
- 机器参数（IP / 端口 / 超时 / 帧）**只以 `01_firmware/esp32c3_gateway/config.h` 为唯一来源**。
- 文档里的这些值**改为指向**（如"当前 `UDP_TARGET_IP` 见 `config.h`"），不再逐处抄数值；保留漂移史只在一个地方（`README.md` §6.4）。
- 加一个 `06_tests/check_docs_sync.py`：扫描"文档写死的值"与 `config.h` 是否一致，不一致就报错。把"人工纪律"换成"自动检查"。

### 2.2 【高】规则去重：一个规则只写一次

**现状**：`git add -A` 禁令写在 §2b 第 6 条 + §6 第 1 条 + 接手指令 §5 第 10 条 + README §2.3；"改完留痕"写在 §2b 第 2/3/4 条 + §6 第 7/8/9 条 + 接手指令 §5 第 6/7/8 条。

**问题**：规则抄 3~4 遍 ⇒ 改一处忘一处 ⇒ 已经产生矛盾（§4.6 就是活证据）。

**建议**：**规则只保留在 `PROGRESS.md` §2b 一处**；`README`、接手指令、`00_context.md` 一律**改成引用**，不再复述。接手指令是"给外人看的拷贝"，允许它复制，但**每次改规则必须连带更新它**（或干脆让接手指令只写一句话："规则以 `PROGRESS.md` §2b 为准"）。

### 2.3 【高】解耦 M6 与 PlatformIO：这是**自设的路障**

**现状**：`PROGRESS.md` §5b / `README.md` §4 把 "M6 前置 = 先定 PlatformIO core" 写成了串行依赖。

**问题**：**M6 压测验的是"固件在真机上的长时间稳定性"，与"用哪个构建工具"技术上是正交的**。`arduino-cli` 已经能编能烧、行为已验过 5 个关卡。把 PlatformIO 的 core 选择卡在 M6 前面，会让**唯一还需要真机做的事**被迫等一个纯工程问题。

**建议**：
- **M6 现在就能跑**（arduino-cli 产物），门槛改为"批次 1/2 真机通过"。
- PlatformIO 迁移降为**独立工作流**（导师要求的组内工具链统一），**不与 M6 串行**；迁完再单独补一次对照验证。

### 2.4 【中】证据入库缺口

**现状**：`03_logs/*` 被 `.gitignore` 忽略，但 `PROGRESS.md` / `00_context.md` 反复引用 `03_logs/M5真机首测_20261005_2035.log` 作为"M5 通过"的证据 ⇒ **证据在本地，仓库里没有**。同理 `老师固件_app镜像_20261005.bin`（逆向依据）也不入库。

**建议**：把**关键证据**的"结论摘要 + 关键片段"写进 `02_docs/`（正缺的 `08_M5真机联调记录.md` 正好承担这个），并**允许 `03_logs/` 里加白名单**（如 `!03_logs/M5真机首测_*.log`）保留原始证据。

### 2.5 【中】多智能体并发无锁

**现状**："不要和另一个智能体同时改同一个文件"只能靠 `git status` + 自觉。Codex 常驻同仓库。

**建议**：轻量加锁——改公共文件前先在该文件顶部留一行 `> 锁定：<角色> <日期>` 或用 `.workbuddy/tmp/LOCK.<文件>` 约定；**或**更简单：**明确"谁拥有哪个文件"**（如 firmware 归 Codex/我，`02_docs` 归我，`00_context` 归用户），把并发面降到最低。

## 3. 代码结构：可优化项

### 3.1 【高·批次 3 前必做】1194 行单文件的拆分

**现状**：`esp32c3_gateway.ino` 单文件承载 WiFi / NTP / UDP / Modbus 帧组装 / CRC / JSON 三行 / 状态机 / 解析。批次 3（AP + Web 配置页 + `/status` + NVS）会再塞进至少 400~600 行。

**建议**：批次 3 之前拆成 `.h/.cpp`（Arduino 支持同目录多文件）：
- `net.{h,cpp}`（WiFi / NTP / UDP）、`qi_modbus.{h,cpp}`（帧 / CRC / 解析）、`report.{h,cpp}`（JSON 三行）、`web_cfg.{h,cpp}`（批次 3）。
- ⚠️ 这**违反" M6 只加固不重构"**，所以**必须把"拆分"作为一个独立、零行为变更的步骤**（拆完逐字节比对编译产物大小 / 冒烟一次），不与功能变更同批。**若你决定不拆，就要接受批次 3 后单文件 1800 行。**

### 3.2 【高】纯函数没有宿主机测试

**现状**：CRC16、Modbus 解析、JSON 组装、温度换算——**全都能在 PC 上跑**，但现在只能在真机/串口上验。这正是项目"验证成本高、真机机会少"的根因。

**建议**：加一个宿主侧测试（把纯函数抽到 `qi_pure.h`，用 gcc/py 对拍 + `06_tests/` 里放向量表）。收益：**改解析/CRC 再也不用等真机**。`db_proto.py` 已经有字段字典和换算，可作为"参照实现"对拍。

### 3.3 【中】编译/烧录无脚本

**现状**：每次要敲那一长串 arduino-cli 路径 + `--fqbn ...:CDCOnBoot=cdc`，容易漏 `CDCOnBoot`（漏了 Serial 会抢 GPIO20/21）。

**建议**：`01_firmware/build.ps1`（compile）/ `upload.ps1`（compile+upload COM 口自动探测），把易错参数固化。零风险。
