### 1.1 两个悬案解开

- **`reg1/2/3` = `record1/2/3` 分闸记录**。实测 `0x6660` / `0x0066` / `0x0000`。
  ⚠️ **解码方式待确认**：字段表说是 varchar（4 条记录/字段），本文件的读法是"每半字节 1 条记录"
  （`0x6660` → 欠压/欠压/欠压/空位），**这是推测**；也可能是 ASCII 字符或 BCD。**定案前不得写进固件/入库逻辑**。
  不过它与现场自洽：施工/工地供电反复欠压跳闸是常见现象。
- **`reg7` = `A_temp`（A 相接线柱温度），量程 −40~160** ⇒ 实测 `raw = 0` → **−40 ℃ 恰好是量程下限**，
  而 A 相电压 222 V 说明该相是带电的 ⇒ **这是"无数据"的伪装值，不是真实温度**。
  同一时刻 `N_temp = 24 ℃`（板载温度）正常 ⇒ 判断该设备**不上报 A/B/C 接线柱温度**。

### 1.2 电量公式（字段表原文）

```
A 相总电量 = (A_H × 65536) / 1000 + A_L   单位度，精度 0.001
B 相总电量 = (B_H × 65536) / 1000 + B_L
C 相总电量 = (C_H × 65536) / 1000 + C_L
合相总电量 = (H   × 65536) / 1000 + L
```

⚠️ 字段表把 `A_L` 描述为「double 型，单位度，精度 0.001」，但公式里 `A_L` 是按**原始低字**（0~65535 整数）
参与运算的。**二者表述不一致**，按 `H=4, L=58831 → 59093.144 度` 验证，**公式口径才是对的**。
建议在字段字典里把 `A_L` 改注为「低字原始值（0~65535）」，避免下游把 0.001 再乘一次。

### 1.3 连带影响：操作卡 §9 换算表不完整

`06_tests/M5_真机联调操作卡.md` §9 只列了 27 项，**缺 `record1/2/3`、`A_Q/A_S`、`B_Q/B_S`、`C_Q/C_S`、`power/Q/S` 共 12 项**。
⇒ 应把 §9 改为**引用字段字典**，不要再维护第二份。

## 2. 数据链路分层与格式约定

```
L0 总线帧      Modbus RTU（485 差分，CRC16 保证）            ← 固件
L1 上行报文    UDP 文本：`YYYY-MM-DD HH:MM:SS | <78B HEX>`   ← 固件（M5 现状）
L2 解析换算    取 39 寄存器 → 按 §1 字典换算 → 判质量        ← PC / 边缘 / 云
L3 持久化      入库（结构化字段 + 原始留证 + 质量标记）
```

### 设计原则（建议固化为项目铁律）

> **固件只搬运原始值，不做任何工程量换算。**

理由（都是商业化的钱）：
1. **换算式变更不用召回设备**——改服务端即可，现场设备零动作；
2. **可重算**：保留原始 78 字节，历史数据可离线重放；新增字段/纠错不必重新采集；
3. 避免把"未验证的公式"固化进 240 台设备里的每一台。

M5 当前的 P12 已经就是这样（`m5_parse.py` 在 PC 侧换算），**这是隐性优势，不要"顺手优化"掉**。

## 3. 解析结果的字段契约（建议在字段表基础上补 6 列）

原字段表定义的是**"值"**，没有定义**"这条数据可不可信"**。商业化必须补：

| 新增字段 | 类型 | 用途 |
| --- | --- | --- |
| `device_id` | varchar | 设备唯一标识（优先 `macAddress`；**不要**用自增 `id` 当设备外键） |
| `src` | varchar | 数据来源：`real` 真机 / `sim` 模拟器 / `replay` 回放 —— **防止测试数据混入生产** |
| `raw_hex` | varchar(156) | 原始 78 字节 HEX，**留证 + 可重放** |
| `seg_ok` | char(3) | 三段成败位图，如 `111`；`101` 表示 S2 失败 |
| `quality` | varchar | 整行质量：`OK` / `PARTIAL`（部分字段无效）/ `BAD` |
| `invalid_fields` | varchar | 被判无效的字段名（逗号分隔或 JSON） |

建议索引：`UNIQUE(device_id, collectTime)` —— 补传/重发场景必然产生重复，靠唯一键做**幂等**。

## 4. 「错误的数据不要」—— 分四层，且**不要靠"丢整条"实现**

| 层 | 检查 | 现状 |
| --- | --- | --- |
| **L0 传输层** | CRC16 校验；**任一段失败即整轮不上传** | ✅ 已在固件实现（P6） |
| **L1 结构层** | 三段齐全 / 帧长 / `byte count` 与长度自洽 | ✅ 已在固件实现（P4） |
| **L2 语义层（新增，重点）** | ① 量程越界（按 §1 表逐字段判）<br>② **无效值伪装**：`A/B/C_temp == −40`（=量程下限）⇒ 判无效<br>③ 状态一致性：`openState` 合闸但三相电压全 0 ⇒ 可疑<br>④ 电量单调性：总电量只增不减，回退 ⇒ 计数字段异常<br>⑤ 时间合理性：`collectTime` 与 `saveTime` 偏差过大 / 时间戳重复 | ❌ **待做** |
| **L3 业务层** | 连续失败 N 次告警；设备级数据缺失率统计 | ❌ 待做 |

### ⚠️ 「不要错误数据」的两种实现，强烈建议选 (b)

- **(a) 整条丢弃**：简单，但**一个温度字段无效会连带丢掉 39 个有效字段**。
  按本次实测，A/B/C_temp 三项恒为无效 ⇒ **按 (a) 每一条数据都会被丢掉**，系统直接废掉。
- **(b) 整行入库 + 无效字段置 NULL + 打质量标记**：可追溯、可统计，也能按客户要求出
  "只看 `quality='OK'`" 的视图。

> 商业化要的是**数据质量可观测**，不是"看不见坏数据"。建议默认 (b)，
> 并保留一个**可配置的严格模式**给有强制要求的客户。

## 5. 商业化落地要考虑的（按优先级）

### P0 —— 不做会翻车

1. **上报协议必须换掉 UDP。** 现在是"无连接 / 无重传 / 无鉴权"，**丢一个包就永久丢 1 秒数据**（本次 59/60 就有 1 次缺口）。
   建议：**MQTT(QoS1) + TLS**，边缘侧本地缓存 + 序号 + 断网续传。
2. **规模账要早算。** 1 台 1 Hz = **8.64 万条/天**；1000 台 = **8640 万条/天**。
   ⇒ 必须定**采样/入库分频**（例：1 s 采样、15 s 或 60 s 落库）、**时序库**（TDengine / TimescaleDB / ClickHouse）
   或**分区表 + 冷热分离**。用自增主键 + 单表 MySQL 撑不住。
3. **安全基线**：一机一密、TLS、固件签名、安全启动、OTA 校验。
   485 侧目前是**明文、无认证**（现场短距离可接受，但必须写进威胁模型）。
   ⚠️ 历史提交里有明文 WiFi 凭据（Q-07 已按"策略 A 不改写历史"结案）—— 商业化前必须真换密码 + 一机一密。
4. **🚨 架构分叉点：只读铁律 vs 客户要"远程分合闸"。**
   `00_context.md` 三.5 明令本阶段**只读不写**（合闸/分闸/锁扣/解锁/复位/广播一律禁止）。
   但商业化后客户**一定**会要控制功能 —— 这是**产品需求与安全红线的正面冲突**。
   **必须先把安全设计做完**（强鉴权 + 二次确认 + 操作审计 + 权限分级 + 失败回滚 + 物理闭锁），
   才谈开放写操作。**在 M6 之前不要动它。**

### P1 —— 规模化之前必须补齐

5. **设备管理**：OTA、远程配置、心跳超时/离线告警、设备台账（`macAddress` ↔ 现场位置/箱号/客户）。
6. **时间一致性**：目前单 NTP 源（校内 chrony）。商业化需多源 + 单调时钟；
   **入库统一存 UTC + 时区字段**（现场是 CST-8），避免跨时区/夏令时事故。
7. **幂等与去重**：`UNIQUE(device_id, collectTime)`；补传必然重复。
8. **可重放**：`raw_hex` 保留策略（保留期/压缩/归档），这是纠错与审计的底牌。

### P2 —— 长期

9. **合规**：用电数据含用户行为与商业信息 ⇒ 等保、留存期、加密存储、数据出境。
10. **可靠性冗余**：单 ESP32 无冗余。建议心跳 + 离线判定 + 现场备用网关（哪怕只做"存储转发"）。
11. **硬件成本**：ESP32-C3 ~50 元 + **RS485 隔离模块（必配，不是可选）**；规模化后复核选型。
    `MAX13487` 5 V 双向、`EN` 固定高——已确认，无方向切换风险 ✅。
12. **可运维性**：日志分级、远程诊断、故障自恢复演练（断电/断网/485 断线各一次）。

## 7. 结论

1. **那份《数据库说明.docx》完全能用，而且是关键拼图** —— 它补齐了 39 个寄存器的完整语义，
   让 M5 的"解析"从"27 项 + 12 个问号"变成"39 项全解"。
2. **"错误的数据不要"的正确做法不是丢行，而是"整行入库 + 字段级置 NULL + 打质量标记"** ——
   否则按本次实测的无效值情况，会把全部数据都丢光。
3. **当前架构有一个商业化优势要守住**：固件只搬原始值、换算全在服务端 ⇒ 公式可演进、数据可重放。
4. **最大的架构分叉点是"要不要开放写操作"**，它撞的是项目自己的安全红线，需要单独决策。

## 8. 与老师的参考实现对比（2026-10-05 收到实拍，**重要**）

老师的 `ESP32-C3 + MAX13487 采集器`（固件 **1.5.0**，设备标识 `ESP485-AF49E4`）已经跑起来了，
能力清单与我们的 M5 对照如下：

| 能力 | 老师的实现 | 我们的 M5 | 结论 |
| --- | --- | --- | --- |
| **配置方式** | **常驻 AP 热点 + Web 配置页**（`ESP485-CFG-XXXX`，`http://192.168.4.1/`），保存**立即生效**、配置存闪存 | 编译期常量（`config.h`） | **老师的更适合商用**：现场改参数不用重烧 |
| **状态观测** | **`/status` JSON**：`mac/fw/ip/rssi/uptime_ms/poll_ok/poll_err/udp_tx/queue/dropped` | 只能看串口 / UDP 数据 | **值得抄**：`poll_ok/poll_err` 正是 M5 的"读取成功率" |
| **上行格式** | **JSON**：`seq` + `dev` + `ip` + `ts` + `quality` + 39 字段（**工程量**） | 文本 `时间戳 \| 78B HEX`（**原始值**） | 取舍见 §8.2 |
| **传输** | UDP :9000（带 `queue`/`dropped` 计数） | UDP :8888 | 同一代方案，**两边都还没上 MQTT** |
| **设备标识** | `dev = "ESP485-" + MAC 后 6 位` | 无（只有 IP） | **抄** —— 正是 §3 建议的 `device_id` |
| **质量标记** | **`"quality":"00"`** | 无（只有固件侧 PASS/FAIL） | 老师**已经做了** ✅ 但编码含义待确认 |
| **序号** | `seq` 递增 | 无 | **抄** —— 算丢包率、去重都要 |
| **时间戳** | ISO8601 + 微秒：`2026-10-03T20:40:23.503800` | `YYYY-MM-DD HH:MM:SS`（Q-12） | 入库用老师的 ISO 格式；人眼通道保留 Q-12 |
| **实测成功率** | `poll_ok 402 / poll_err 13` ≈ **96.9%** | 59/60 ≈ **98.3%** | 同量级 ⇒ **1 Hz 下 ~97% 可作基线** |

### 8.1 三点重要发现

1. **`quality` 字段老师已经实现了。**
   我 §3 建议的"整行入库 + 打质量标记"**方向与老师一致**（不是我独创）。
   ⚠️ 但 `"quality":"00"` 的**编码含义未知**（是位图？故障码枚举？）—— **需向老师确认**，
   确认前不得自行定义第二套。

2. **`A/B/C_temp = −40` 在老师的数据里同样存在**（`"A_temp":-40,"B_temp":-40,"C_temp":-40`）。
   ⇒ **不是我方接线或解析的问题**，是该型号设备确实不上报接线柱温度。
   ⚠️ 而老师的数据里 **−40 被原样输出、直接进库** ⇒ **说明这个"无数据伪装值"目前会污染数据库**。
   ⇒ §4 的 **L2 无效值判定是真实存在的缺口**，且已被老师自己的数据佐证。

3. **老师的 `recor1 = "6666"` / `recor2 = "0066"` / `recor3 = "0000"`，
   与我们实收的 `0x6660` / `0x0066` / `0x0000` 完全同构**
   （4 位十六进制字符 = 4 条分闸原因，逐位对应）。
   ⇒ 我 §1.1 标"推测"的**半字节解码，现已被老师的独立实现佐证**，置信度可上调为
   「已由老师实现验证」（仅 `0` 与 `F` 的区别仍待确认）。
   📌 另注：老师的字段名写作 **`recor1/2/3`**（少一个 d），若日后要接收老师的数据需做兼容映射。
   📌 **老师的 JSON 里没有 `openState`**（其余 38 项齐全）—— 是有意省略还是遗漏，值得一问。

### 8.2 一处架构分歧（要总控裁定）

- **老师：固件内换算** —— JSON 直接给工程量（`"frequent":50.1`、`"A_voltage":231`、`"A_current":0.11`）。
- **我们 M5：固件只搬原始值** —— 78 B HEX，换算在 PC / 服务端。

| 对比项 | 老师（固件换算） | 我们（只搬原始值） |
| --- | --- | --- |
| 接收端复杂度 | **低**（直接入库） | 需要一个解析层 |
| 公式 / 字段含义变更 | **要重烧每一台设备** | 改服务端即可 |
| 历史可重算 | **不能**（JSON 里没有原始值） | **能**（保留 raw） |
| 现场演示友好度 | **高** | 低 |

**建议（折中，不推翻任何一方）**：
1. M5 的"原始值"通道**保持不动**（已实测可用）；
2. 由**服务端**生成"工程量 JSON"（等价于老师的输出）—— 接收端一样简单，但公式仍可演进；
3. 若总控决定让**固件直出 JSON**，则**必须同时附带 `raw`（78 B HEX）字段**，否则历史数据不可重算。
4. 两条路都要把 `seq` / `dev` / `quality` / `ts` 对齐（见 §8.3），**格式统一是接老师数据的前提**。

### 8.3 可以马上就抄的三件事

| # | 抄什么 | 落在哪 |
| --- | --- | --- |
| 1 | **`/status` 计数器**：`poll_ok` / `poll_err` / `udp_tx` / `queue` / `dropped` / `uptime_ms` | 补进 P13 的 UDP 行或另开一行；`poll_ok/poll_err` 就是 M5「读取成功率」的现成分母分子 |
| 2 | **`dev` 设备标识** = MAC 后 6 位 | 我们的 UDP 行加 `dev=` 字段，入库即 `device_id` |
| 3 | **`seq` 递增序号** | 同上；用来算丢包率、做补传去重 |

> 老师的 `queue` / `dropped` 两个计数说明**固件里有本地排队**（我 §5-P1 建议的"边缘缓存"雏形）。

| # | 问题 | 风险 | 处置 |
| --- | --- | --- | --- |

### 9.2 安全项的正确姿势（回应"老师要方便"）

问题不在"开放"，在**开放给谁**：

- **现在** = 知道那个（已流出的）密码的人，**任何时间、任何距离**内都能进；
- **目标** = **手里拿着这台设备的人**才能进。

做到这一点的最小改动、且**完全不牺牲现场便利**：

| # | 改动 | 现场体验 | 关掉的口子 |
| --- | --- | --- | --- |
| 1 | **AP 上电只开 N 分钟，或长按按键才开** | 装机时开着，照样方便；**运行期自动关门** | 设备在线期间的常开入口 |
| 2 | **一机一密，密码印在设备标签上** | 照样"看一眼标签输入" | 一处泄露 = 全网泄露 |
| 3 | **配置页加口令（复用 AP 密码）** | **零额外记忆成本** | 同网段任意人可改 |
| 4 | **改 UDP 目标地址需二次确认** | 多点一次 | **唯一能把数据引流出去的开关** |
| 5 | 长期：上行 MQTT + TLS | 无感知 | 伪造 / 窃听 |

> 一句话：**把"墙上那把万能钥匙"换成"每台设备各自的门卡"，便利性一点没少。**

### 9.4 对齐清单：以逆向的那块板为基准

**基准版固件**（`48:F6:EE:15:9B:88`）的上行格式串（原文，见 `02_docs/17` §3）：

```
{"seq":%lu,"mac":"%s","ip":"%s","ts":"%s","ts_ok":%s,
 "openState":"%04X","record1":"%04X","record2":"%04X","record3":"%04X",
 "frequent":%.1f,"leakage_current":%.3f,"N_temp":%d,
 "<A|B|C>_temp":%d,"<A|B|C>_voltage":%u,"<A|B|C>_current":%.2f,"<A|B|C>_Pf":%.2f,
 "<A|B|C>_power":%u,"<A|B|C>_Q":%u,"<A|B|C>_S":%u,"<A|B|C>_H":%u,"<A|B|C>_L":%.3f,
 "power":%u,"Q":%u,"S":%u,"H":%u,"L":%.3f}
```

| 类别 | 项 | 决定 |
| --- | --- | --- |
| **必须一致** | 字段名、字段顺序、语义 | 按上表逐字对齐（与 `05_hardware/STB3-125_Database_Fields.md` 三方吻合） |
| **必须一致** | `openState` / `record1/2/3` 的表示 | **`"%04X"` 十六进制字符串**（半字节解码已确认） |
| **必须一致** | 设备标识 | **用 `mac`**（完整 MAC），**不用 `dev`** |
| **必须一致** | 心跳行独立 | `"type":"hb"` + `rssi/free_heap/poll_ok/poll_err/udp_tx/queue/dropped/cfg` |
| **必须一致** | `/status` 22 项 | 逐字对齐 |
| **必须一致** | `ts` 时间戳 | ISO8601（基准是 `2026-10-03T20:40:23.503800`）；**人眼通道可继续用 Q-12 格式** |
| **可以不同（推荐）** | **换算位置** | 基准 = **固件内换算**；我们**推荐"基线字段 + 末尾追加 `raw`（78 B HEX）"** —— JSON 接收端按名取值，多一个字段不破坏兼容，但换来**公式可演进 + 历史可重放**。⚠️ **此项需一次裁定** |
| **可以不同（推荐）** | **质量标记** | 基准这版**没有** `quality`（老师新版有）。**建议：上报格式严格对齐基准、不加 `quality`；把质量判定放在"入库层"**（§4 的 L2/L3），落成数据库的 `quality` / `invalid_fields` 列。**上报字段 ≠ 数据库列**，两边都不冲突 |
| **保持现状** | 传输 | 双方都还是 UDP（老师 :9000，我们 :8888）；MQTT 属产品化阶段 |

> 一句话：**"以这块版本为准"我们落成"字段与语义逐字对齐，只有在'可重算性'和'质量标记位置'两点上做加法，并把加法做成向后兼容"。**

### 9.5 PlatformIO 迁移（**窗口已到**）

**这条不是新话题，是接上一条已登记的决策。** 项目记录里写着：
导师张振亚要求组内迁 **VSCode + PlatformIO + Claude Code**，项目已裁定

当时推迟的理由：换构建系统会污染 M5 期间"硬件 or 代码"的判因。

**现在**：M5 主干实测已通过（真机 3 段读取、59/60 成功、连续 60 s 无失败），只剩两个小尾巴（E-02、缺包定性）。
**⇒ 触发条件基本达成，老师那边也在用 PlatformIO ⇒ 顺理成章，窗口到了。**

**做法：并行验证，不整体切换。**

| 步 | 动作 |
| --- | --- |
| 1 | 新建 `platformio.ini` + `src/main.cpp`，**与现有 `01_firmware/esp32c3_gateway/` 的 `.ino` 并存**（不动现有工程，M5 收尾还能用它） |
| 2 | **只编译、不烧录**；比对 Flash / RAM 是否等价、有无新增警告 |
| 3 | 等价后再决定是否切换为唯一构建方式，并同步 `README` / 任务书 / 排障文档 |

**必须锁死三件事**（否则重演 `esp-rv32` 那次排障）：

1. **core 版本** —— ⚠️ **这是最大的坑**：PlatformIO 默认的 `espressif32` platform 用的是 **arduino-esp32 2.x**
   （**正是老师那套**，`esp-idf v4.4.7`），而我们 Arduino IDE 用的是 **3.3.10（IDF 5.x）**。
   ⇒ **一旦迁移，core 会降级，API 可能不兼容**（`configTzTime` / `sntp_*` / `WiFi.setSleep` 等签名有过变化）。
   ⇒ 必须**显式锁定版本**（写死在 `platformio.ini` 里），并**重新编译 + 复跑一遍 M5 验证**，不能"默认就好"。
2. **编译选项要搬全** —— `CDCOnBoot=cdc`（USB CDC On Boot，**必须**，否则 Serial 会占 GPIO20/21）、Flash 4 MB、分区表。
3. **`.ino` → `main.cpp` 的坑** —— `.ino` 由 Arduino 预处理器**自动生成函数原型**；改成 `main.cpp` 后
   **必须自己补前向声明**，否则会出现一堆"未声明标识符"的错误（这与代码逻辑无关，纯构建差异）。

> 附带好处：老师的固件里出现 `Arduino Event Malloc Failed!` ⇒ **他用的也是 arduino 框架，只是构建工具是 PlatformIO**。
> ⇒ **框架相同、只是构建工具不同** ⇒ 复用代码的成本比想象中低。

### 9.5.3 🔴 比下载更重要的发现：**"零差异"这个目标不成立**

| 项 | 我们（Arduino IDE） | `espressif32@7.1.3` 声明要的 |
| --- | --- | --- |
| Arduino core | **arduino-esp32 3.3.10** | **`framework-arduinoespressif32 ~4.20017.0`**（2.0.17 那一代） |

佐证（乐鑫镜像实测）：`esp32-3.3.10.zip` → **404**；`esp32-3.3.0.zip` → 200 但**只有 24.6 MB**
（3.x 把预编译库拆成独立的 `*-libs` 包 —— 这正是本机 `Arduino15` 下那堆 `esp32c3-libs`（200 MB+）的来源）。

> **⇒ 迁到 PlatformIO ≠ 零差异，而是"换 core"（3.3.10 → 2.0.17）。**
> API 会变（§9.5 已预警），**产物必然不同**，且**必须重跑一遍 M5 验证**。
> **⇒ 所以 ② 的真正前置不是"能不能下载"，而是"迁到哪个 core"——这个决定必须由用户 / 总控做。**
> 📌 附带好处：老师用的是 PlatformIO + **arduino-esp32 2.x** ⇒ **他那边和 `espressif32@7.1.3` 的默认是同一代**，
> 所以"找老师拷 `.platformio`"不仅能省下载，**而且正好验证他那个组合**。

### 9.5.4 ✅ ② 已完成：**能编过，但产物不等价**（2026-10-05 22:44）

**结论：PlatformIO 编译通过（`[SUCCESS] Took 47.21 s`，0 error / 0 warning），但产物与 Arduino 不等价。**

| 指标 | Arduino IDE（arduino-cli，**core 3.3.10**） | PlatformIO（**core 2.0.17**） | 差 |
| --- | --- | --- | --- |
| **Flash** | **1 000 967 B**（76%） | **766 588 B**（58.5%） | **−234 379 B（−23.4%）** |
| **RAM（global）** | **38 412 B**（11%） | **40 212 B**（12.3%） | **+1 800 B（+4.7%）** |
| error / warning | 0 / 0 | **0 / 0** | — |
| 产物 | — | `firmware.bin` 785 456 B / `firmware.elf` 11.0 MB | — |

> **⇒ 「迁 PlatformIO 零差异」的答案：不成立（已量化）。**
> 差异来源就是 §9.5.3 说的**换 core**（3.3.10 → 2.0.17）：库更旧更瘦 ⇒ Flash 少 229 KB；静态区更大 ⇒ RAM 多 1.8 KB。
> **⇒ 迁移的正确姿势是"换 core + 重跑全套验证"，不是"零差异切换"。**

**⚠️ 两个必须一并计入迁移成本的点**

1. **"只 include 外部 `.ino`"这种骨架会让 PlatformIO 的 LDF 失效**：`src/main.cpp` 只 `#include "../esp32c3_gateway/esp32c3_gateway.ino"`，
   而该 `.ino` **在 `src/` 之外** ⇒ LDF **看不到它里面的 `#include <WiFi.h>`** ⇒ 报
   `fatal error: WiFi.h: No such file or directory`（框架核心本身编得过）。
   本次靠两处人为改动绕过：`lib_ldf_mode = deep+` + 一条额外 `-I.../libraries/WiFi/src`。
   ⇒ **正式迁移时应当把 `.ino` 拆成真正的 `src/*.cpp`**（届时还要补函数原型，见 §9.5 第 3 条）。
2. **能编过 ≠ 跑对**：0 error / 0 warning 只说明 **API 层面兼容**；**运行期行为差异（NTP / WiFi / 485 时序）完全没验证**。

**✅ 已解决的环境问题（可复用）**

| 问题 | 解法 |
| --- | --- |
| PlatformIO CDN ≈14 KB/s | 改用**乐鑫 CN CDN `dl.espressif.cn`（实测 2.1 MB/s）** |
| 乐鑫给的是原版包，PlatformIO 报 `MissingPackageManifestError` | **离线预置**：`06_tests/pio_cn_seed.py` —— 解压到 `~/.platformio/packages/`，**自动拍平多余顶层目录 + 写 `package.json` / `.piopm`** |
| framework 包主属必须是 **`platformio/`**（不是 `espressif/`），否则 PlatformIO 认为没装 | 已在脚本里更正（`pio_owner="platformio"`） |
| pip 依赖走 PyPI 只有 37 kB/s | 可加 `PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`（清华 PyPI 镜像**是真实存在**的） |

📌 本工程实测体量：`toolchain-riscv32-esp` 908 MB + `framework-arduinoespressif32` 703 MB（解压后），
外加大约 20 个小包 ⇒ 说明**为什么"拷老师那份 `.platformio`"仍然是最快的路**。
