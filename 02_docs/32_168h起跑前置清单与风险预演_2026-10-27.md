## 0. 一句话：什么时候能跑

**不是"烧录完就能跑"。** 起跑要同时满足 **8 道门**（§1），其中 **G-6（旧电脑不休眠）是文档级硬门槛**——
`02_docs/24` §8 Q2 原文："不能禁休眠 ⇒ 168h 不可开跑"。

**最早时间点估算**（假设 USB 线能马上换好）：

| 时刻 | 动作 | 耗时 |
|---|---|---|
| T+0 | 换线、系统识别到 COM5 | —（**当前卡在这里**） |
| T+2 min | 烧录 `0.7.0-batch4` | 2 min |
| T+5 min | 台架 4 项（boot / reconn / 弱网配置页 / 串口日志） | 25 min |
| T+30 min | WDT 注入验（烧测试版 → 验 → 烧回正式版） | 15 min |
| T+45 min | **开跑**（前 8h 兼作 §3.5 门控） | — |

⇒ **线换好的时间 + 约 45 分钟**。今晚 22:30 换好 ⇒ **23:15 可开跑** ⇒ 收工时间 **11-03 23:15**。

## 0.5 旧 8h 门控的适用范围（**能复用一半，不能全复用**）

2026-10-26/27 那轮 8h 跑的是 **`0.6.0-batch3`（加固前）**：M2 = 99.9788%、M3 = 99.9859%、err 0、对账残差 0。
现在要跑的是 **`0.7.0-batch4`**，相对它改了 **10 处**。

| 维度 | 旧 8h 能否覆盖 | 说明 |
|---|---|---|
| **链路 / 环境**（M2、M3、空口丢、路由、DHCP） | ✅ **有效可复用** | 环境没变（同 SSID、同网段、同接收端机器）⇒ "链路能跑到 98%+" 仍然成立 |
| **M-11/M-12 抖动** | ✅ 有效（但结论是 F） | 上轮 82.1 ms / 1205 ms；新固件不会让抖动变小 |
| **Y-4 时钟回跳 `CLOCK_STEP`** | ❌ **完全不能复用** | 旧固件**没有钳位机制**。那次 `CLOCK_STEP = 0` 只说明"8 h 内没遇到回退"（**运气**），推不出"新钳位有效" |
| **Y-7 非人为重启** | ❌ 不能复用 | 新固件多了 WDT（60 s）——**新增了一个会触发重启的机制**，旧数据无法预测 |
| **`reconn` / `boot` / `clk_hold`** | ❌ 不能复用 | 旧固件这些字段要么恒 0、要么不存在 |
| **电量公式（D-10）** | ❌ 不能复用 | 旧固件用错公式，读数差 1000 倍 |
| **`/status` 的 `queue`/`dropped`** | ❌ 不能复用 | 旧发 `0`、新发 `null` |

**结论**：旧 8h 证明了"**这条路能跑通**"，但**证明不了"新固件不会把路走坏"**。
而新固件的核心改动（时钟钳位、WDT、boot 计数）**恰恰全落在"不能复用"那一栏**，且 **Y-4 一票否决**。

⇒ **不必再单独跑一个独立 8h**（那是白等 8 小时），但**新固件必须自己跑一段并过 8h 门控线**。
最省的做法就是并入 168h 的前 8h（见 §5）。

## 1. 八道门（全部满足才允许起跑）

| # | 门 | 判据 | 状态 | 谁 |
|---|---|---|---|---|
| **G-1** | 固件可烧 | COM5 出现，烧录成功，串口打印 `fw=0.7.0-batch4` | 🔴 **阻塞**（COM5 未识别） | 用户换线 |
| **G-2** | boot 计数正确 | 拔电重插 ⇒ `boot=1`；软复位 ⇒ `boot` 严格 +1 | ⬜ 待烧录后验 | 砚青 |
| **G-3** | `reconn` 递增 | 断网 1 min 恢复 ⇒ 心跳 `reconn` 单调增（验 A-1） | ⬜ 待验 | 用户断网 |
| **G-4** | WDT 真会触发 | 注入 `while(1)` ⇒ 60 s 后 `reset=TASK_WDT`、`boot` +1 | ⬜ 待验 | 砚青 |
| **G-5** | 弱网配置页不误杀 | 慢客户端拉 8 KB 页 ⇒ 不重启（验 F-4 的 60 s 是否够） | ⬜ 待验 | 砚青 |
| **G-6a** | 旧电脑不休眠 | 电源计划「从不睡眠」**实际改掉并回显确认** | 🟡 **用户已答"能"**，待实际确认 | 用户/旧电脑 |
| **G-6b** | **旧电脑 IP 不漂移** | 用户已确认 **IP 是 DHCP**（非静态）⇒ 必须做路由器 **MAC-IP 绑定**（首选）或改静态 | 🔴 **必须处理**（见 §1.1） | 用户/旧电脑 |
| **G-7** | 磁盘余量 | 全程 ≥10 GB（Y-9）。估算：1.2 M 行 × ≈500 B ≈ **0.6 GB** + 原始包 ≈0.4 GB ⇒ 约 **1 GB** | ⬜ 待查 | 旧电脑 |
| **G-8** | **启动命令不含 `--key-hex`** | 固件发**明文**、接收端 `decrypt_frame()` 是 **fail-closed**（解不出返 `None`）⇒ 带了这个参数会**把每一个包都丢掉** | 🔴 **必须逐字核对启动命令** | 用户/旧电脑 |


> ⚠️ **G-6 是唯一"软件侧再怎么改都救不了"的项**。DHCP 租约若中途换 IP，UDP 目标不变但**回程不可达**，
> 整段数据断档且无法在事后补救。2026-10-27 21:47 已发生过一次租约到期风险。

### 1.1 G-6b：**IP 是 DHCP** 怎么处理（2026-10-27 用户确认）

风险：租约到期换 IP ⇒ ESP32 的 UDP 目标（**存在 NVS 的 `udp_ip`**）失效 ⇒ **单向黑洞**：
ESP32 照发、`udp_tx` 正常涨，但接收端一个都收不到。这是"看起来在跑、其实全丢"的最坏形态。

| 方案 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A（首选）路由器 MAC-IP 绑定** | 路由器管理页 → DHCP 保留 / 静态分配 → 绑定旧电脑网卡 MAC | 最稳；旧电脑零改动；不影响其他设备 | 需路由器管理权限 |
| **B 旧电脑设静态 IP** | 选 **DHCP 池外**地址（如 `172.16.0.250`），配好掩码/网关/DNS | 不需路由器权限 | 选到池内地址会**撞 IP**；网关/DNS 配错直接断网；改回麻烦 |
| **C 兜底：巡检 + 热改** | 巡检看 IP；变了就连 ESP32 的 AP（`ESP485-xxxx`）→ 配置页 → 改 server → `/save` | 零前置 | 变 IP 到发现之间**必丢数据** |

**关键事实**：ESP32 的 UDP 目标在 **NVS**，用 Web `/save` 改**立即生效、不需要重烧**（批次 3 的设计）。
⇒ 方案 C 是**可恢复**的，不是灾难。建议 **A 或 B 为主 + C 作兜底监控**。

- ⚠️ **禁止 `/reset`**（会清空 NVS，含 WiFi 凭据与 UDP 目标）
- ⚠️ 若旧 IP 被**别的机器**占用，那台机器会收到 ESP32 的包（数据泄漏 + 我们收不到）。
  巡检若见到"`udp_tx` 正常涨但落库为 0"，**优先怀疑这条**

## 2. 判据口径预置（**这类才是"跑完才发现"的重灾区**）


必须在开跑**之前**把下列口径写死，否则 168h 结束当天会为"这条到底算不算 F"吵起来。

| # | 问题 | 现状风险 | 建议口径（待用户/导师确认） |
|---|---|---|---|
| **C-1** | **M-11 抖动 p99 ≤50 ms** | 上一轮 8h 实测 **82.1 ms** ⇒ **必 F** | ✅ **口径已认（2026-10-27 用户确认）**：报告写"**F 但归因明确**"，附 `recv_mono` 中位数 + 直方图，说明是接收端落库时刻（含 Python GIL / 写盘 fsync）而非空口抖动。**不计入中止判据** |
| **C-2** | **M-12 抖动 max ≤200 ms** | 上一轮 **1205 ms** ⇒ **必 F** | ✅ **口径已认（同上）**：报告单列"离群点时刻表"并归因（GC / fsync / DHCP 续租），标注为**离群点而非系统性劣化** |
| **C-3** | **P-6 每日备份数 = 运行天数（≤3）** | 168h = **7 天**，与"≤3"直接冲突 | 168h 应记 **7**。`≤3` 是给 8h/24h 用的。**须改口径**，否则 P-6 必 M |
| **C-4** | **Y-1 M2 ≥96%** vs **§3.5 门控 97.5%** | 两套数字，极易混 | 明确：**96% 是 168h 主判据**；**97.5% 只是 8h 门控放行线**。报告里两个都要写，不得只写一个 |
| **C-5** | **RAW `bad=2000/2000`** | ✅ **已定性（2026-10-27 22:2x）**：根因是 `verify_raw()` 比 `openState` 时**中文 vs HEX 口径不一致**，每行必错 1 个；抽样上限写死 2000 ⇒ `2000×1=2000`，**数值严丝合缝**。`udp_collect.py:2113-2121` 已修复 | **不是数据损坏、不是固件问题**。仍须旧电脑跑 `--verify-raw` **验证修复生效**（`bad` 应≈0）。指令：`04_ai_prompts/14`。⚠️ 必须用 `--verify-raw`，`--report-only` 只读历史快照、不重算 |
| **C-6** | **Y-4 的 `clk_hold` 交叉证据** | lwip 每 3h 自同步会走 `ts` 护栏而非钳位 ⇒ `clk_hold` 可能为 0 而**仍合格** | 已在 `02_docs/30` §5.2 修正：**`CLOCK_STEP = 0` 是唯一必须**；`clk_hold = 0` 不等于未验证 |
| **C-7** | **电量跨 `L` 进位** | `A_L≈58965`，剩 6570 Wh，168h 按 41 W 需 6888 Wh ⇒ **必然跨一次 65535→0** | 新增判据：**进位时刻电量必须连续（+0.001 度），无跳变**。`db_proto.py:220` 已用 `H*65536+L` 拼接值比较，可正确跨进位 ✓ |
| **C-8** | **UDP 是否加密** | **明文**。固件零加密代码（无 `ENC_ON`/AES/TLS）；接收端 `decrypt_frame()`（AES-128-GCM，`--key-hex` 启用）**从未与固件对接** | **168h 一律不加 `--key-hex`**。理由：①固件本就不加密，加了必然全丢（fail-closed）；②加密会引入新变量（CPU 开销、包变大、可能拉高抖动），污染长跑数据；③安全收紧属 **M7**（`02_docs/26:65` 已登记"UDP 明文 + AP 常开 ⇒ 同网段可嗅探/伪造，只在隔离实验网段用"）。**不要用 168h 兼做加密 A/B** |


> **C-1/C-2/C-5 三条是"必 F 项 / 未定性项"，必须在开跑前敲定，否则 168h 跑完当天必然返工。**

## 4. 中止判据（**该停就停，别硬撑**）

出现任一条，**立即停止并排查**，不要"再等等看"：

1. `event_log` 出现**任何** `CLOCK_STEP`（Y-4 一票否决，已废）
2. `boot` 非人为增加（Y-7）
3. `q_drop > 0`（Y-5）
4. 电量出现负跳变（C-7）
5. 旧电脑 IP 变化 / 休眠过（F-3/F-4，数据已断档不可补）
6. 累计缺口 >4%（M2 已无余量，96% 是死线）

> 反之，以下**不必中止**：单次 WiFi 短断、`ts_ok` 短暂 false、M-11/M-12 抖动超标（已知必 F）。
